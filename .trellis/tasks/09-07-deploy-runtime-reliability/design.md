# 部署备份与代理修复设计

## 状态、所有权与边界

本设计对应 `prd.md` 的 R1-R3，当前仅规划，等待最终实施批准。后端业务数据库仍持有题目事实，checkpoint 仍持有执行连续性；备份只导出和恢复，不重写业务状态或增加兼容读取。

主实现留在 `deploy/`：保留 `backup.sh` 作为 cron 稳定入口，内部调用一个仅依赖 Python 标准库的 `backup.py`，集中处理配置读取、归档验证、替换和每日下载。使用现成 Docker Compose、PostgreSQL 客户端、ossutil 和 SSH，不引入备份框架、云 SDK、守护进程或调度平台。Python 3.10+ 是服务器和 Mac 工具前置项，教程明确检查，不假定默认已安装。

## 1. 唯一备份格式

一份 `latest.tar.gz` 就是一套完整恢复点，不把两个库分开作为外部可见的 latest 文件。归档包含：

| 成员 | 内容 |
| --- | --- |
| `manifest.json` | 格式版本、备份 ID、导出时间、应用镜像标识、业务 schema 版本、成员大小与 SHA-256 |
| `business.sql` | 业务库结构和数据 |
| `checkpoint.sql` | checkpoint 库结构和数据 |
| `files.tar` | appdata 卷中本项目的文件 |

- 外层 gzip 压缩；大成员流式写入/读取，不把全库装进 2 GiB 服务器内存。
- 格式固定为 `skill-eval-backup/v1`；拒绝旧的两份松散文件、缺项、重复成员、路径越界或危险链接。验证清单不执行其中任何命令或 SQL。
- 清单以原 `LANGGRAPH_AES_KEY` 计算 HMAC-SHA256 校验值，恢复时核对，既证明使用原密钥，也绑定成员摘要；不把密钥本身写入清单。空 checkpoint 库同样可验证密钥。此校验不代表加密整个备份。
- Mac 日常下载先验证结构、成员摘要和传输完成；真正恢复还必须使用原密钥验证 HMAC 和 checkpoint 解密。不要求每天把密钥重新输入 shell 命令。
- 整份归档包含业务敏感数据，服务器/Mac 目录仅所有者可访问，文件 600，OSS 私有；SSH/OSS HTTPS 保护传输。原 AES 密钥与访问凭证单独安全保存，不写到日志、argv、Git 或普通教程示例。

## 2. 配置与精确目标

- `backup.py` 从明确的 Compose 目录运行 `docker compose config --format json`，解析 API/Worker/PostgreSQL 的已解析环境与挂载。原始 JSON 含凭证，只保留在内存，不直接打印；不 shell source `.env`，不重复发明 env 文件解析器。
- 校验 API 与 Worker 的两库配置和 appdata 卷一致，两库都位于本 Compose 的 `postgres` 服务、名称不同、非默认管理库；DSN 使用结构化解析，禁止 query/host 覆盖绕过。工具只操作已核验的这两个库，不接受任意外部数据库备份目标。
- 备份配置为 `OSS_BUCKET`、`OSS_PREFIX` 和 `OSS_ENDPOINT`，在生产模板中给无密钥占位说明；ossutil 凭证仍由其自身私有配置管理。专用 Bucket/前缀不能是公共根目录或含其他业务内容的默认清理范围。
- 预检 Python/Compose/ossutil 版本、镜像和容器身份、两个库存在性、可用空间、归档目录权限、原密钥形状和 OSS 写入/保留前置条件。失败先于停写；新建库可以暂时没有 checkpoint 表，但不存在该库必须拒绝。
- 备份目录使用固定 `backups/latest.tar.gz`；首次如存在未知文件或符号链接，不自动覆盖。旧日期目录不批量删除或转换，因服务器计划全新部署不存在必须迁移的真实历史。

## 3. 服务器每日生成

保留现有每天 03:00 的 cron 习惯，教程明确主机时区及本地时间；用户每日手动 Mac 下载与此独立。计划只说明如何安装，不在本次开发中创建真实 cron。

1. 对本 Compose 项目取得互斥锁，禁止两个备份并发执行。记录本轮 API/Worker 容器 ID 和原运行状态，写入不含凭证的维护恢复状态。
2. 停止 API 新请求和 Worker 写入，等待退出，核对数据库无其他未授权写入连接；不杀未知进程。不存在确定的停写边界即恢复本次服务并失败。
3. PostgreSQL 容器内 `pg_dump` 依次导出两库；使用已核验 appdata 卷的只读一次性容器导出文件，不能对已经停止的 API 使用 `docker compose exec api tar`。
4. 两库和文件原始导出落到权限受控的本次临时目录后，立即恢复此前运行且本轮停止的服务；不等待压缩、OSS 上传或 Mac 下载。检查启动结果，失败明确报告并保留维护恢复状态。
5. 打包、生成清单、验证候选，flush/fsync 文件并在同一文件系统内用 `os.replace` 整体替换 `latest.tar.gz`；成功后不留上一份日期归档。磁盘空间不足或校验失败则保留原 latest。
6. 更新 OSS。OSS 失败不撤销已成功的服务器最新副本，也不伪称云端同步完成；分别输出安全的备份 ID/时间和两处结果。

普通失败和 SIGINT/SIGTERM 在 finally 中恢复本次停止的服务并清理自身临时资源。SIGKILL/断电无法靠 finally 保证，恢复状态须支持下次启动/人工恢复核查，不能声称所有异常都无停机。正在下载旧 latest 的文件描述符可继续读取旧 inode，下载本身不额外冻结数据库。

## 4. OSS 只留最新成功一套

使用新建私有、未启用版本控制或保留锁的专用备份前缀。已有 Bucket 配置不匹配时失败并要求人工处理，不由脚本静默关闭保护。

- 每个候选使用唯一数据对象名，例如 `<prefix>/bundles/<backup-id>.tar.gz`；`<prefix>/latest.json` 仅存该对象名、ID、大小和整包 SHA-256。稳态一份归档加一个很小的指针文件。
- 上传候选时使用 ossutil 的完整性校验；为避免仅将对象存在性或 ETag 当作整包 SHA-256 证明，发布前通过同地域内网回读候选并流式核对整包摘要。回读会产生请求和流量用量，但按当前同地域内网文档不收流量费；不消耗停写窗口。
- 验证通过后写入完整的 latest 指针。只有确认远端指针已指向新候选，才删除精确的上一对象。对指针更新请求结果不明的情况先回读，不能猜测后删除可能正在使用的对象。
- 候选失败保留旧指针/旧对象；清理失败返回可诊断状态。下一轮先核对并处理专用前缀中本工具拥有的未发布候选与旧对象，避免持续累积；不删除 current 指向对象，不递归清空 Bucket。
- 对本工具未完成的分片做显式终止/清理，并在教程给出专用前缀的残留检查；不把“只看到一个对象”当作无分片或无历史版本收费证据。
- 恢复下载先读 latest，再下载对应完整对象；并发更新导致旧对象已删时重新获取一次最新指针并重试，失败保留目标端旧归档。限制重试次数，不无限下载。
- 不实施对象历史留存、版本恢复开关、7 天过期保留或云端日期目录堆积；短暂两份是更新保护而非长期保留。

## 5. Mac 每日手动下载

`backup.py download` 作为跨平台统一入口，只需本机 Python 和 SSH；不要求 Mac Docker 启动，也不读取 Mac `.env` 或业务库。

- SSH 目标使用用户现有的主机别名；校验主机参数，不关闭 host-key 检查，不把用户输入拼进未转义的远程 shell。远端只读取指定的服务器 latest 归档。
- 下载到本机专用目录的临时文件，完整校验后用 `os.replace` 覆盖 `latest.tar.gz`。日期和 ID 留在清单/输出，不创建按日期长期累积的目录。
- 本机同时下载互斥；断网、磁盘不足、校验失败均保持旧 latest 不变。未曾初始化且已有未知 latest 时拒绝覆盖；只清理本次临时文件。
- 显示本次取到的生成时间、ID 和成功结果，明确这是服务器已生成的版本，不保证包含下载时刻之后或导出后新增的数据。同 ID 再次下载可幂等处理，不因此增加恢复点。
- OSS 恢复下载沿用同格式验证；日常来源是服务器，不自动配置 Mac 常驻任务、通知或自动云端下载。

## 6. 恢复操作

完善 `restore.md`，复用工具的 verify 能力而不新增无人值守破坏性恢复产品。

1. 选择一套可用归档及匹配的原密钥/应用镜像，核对摘要、格式、HMAC 和目标两库；对任何未核实目标停下。
2. 暂停备份调度并取得同一维护互斥锁，停止本项目写入；列明恢复会替换什么，确认后才重建目标两库和恢复专用文件卷，不整盘删除或操作其他数据库。
3. 以受控输入导入两个 SQL，开启 SQL 错误即停，文件解包路径严格校验。修复原 STAMP 未传入容器导致路径不正确的问题。
4. 启动前验证 schema、原密钥解密、线程映射和文件摘要；任一步失败均保持未开放写入，不输出成功。
5. 按受支持的 Compose 入口恢复服务及代理，查看实际业务和任务恢复结果，再恢复调度。副本只留最新，因此更旧镜像若不兼容现存唯一备份，明确不能执行历史数据回滚。

不增加自动 `.bak`、历史库、旧格式兼容路径。操作中的临时文件在完成/明确中止后精确清理，生产实际恢复另需用户对目标环境授权。

## 7. Nginx 地址刷新

使用 Compose 原生依赖重启，不改变 HTTP 路由或更换 Nginx 镜像：在 `nginx.depends_on.api` 与 `.web` 加 `restart: true`，保留 `condition: service_healthy`。

Docker 官方说明该字段自 Compose 2.17.0 可用，显式 Compose 更新或重启依赖时会重启下游服务，不覆盖容器运行时自行重启。文档预检区分 Docker Engine 和 Compose 版本；部署工具支持 Compose 2.20+，实际机器不满足时先停止，不自动升级整机。

发版与回滚按整个 Compose 服务图执行，等待服务健康，再检查 Nginx 请求。手册去掉允许遗漏 Nginx 刷新的操作描述，发布脚本输出与手册一致。API/Web 的新 IP 在 Nginx 重启时重新解析；测试要真的改变 IP，并核对 Nginx 重启发生。手动脱离 Compose 改网络的情况不在保证内。

参考：[Docker 启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)、[depends_on](https://docs.docker.com/reference/compose-file/services/#depends_on)。本轮已读取官方语义，实际容器测试是实施验收门，不冒充已通过。

## 8. 一次性切换、删除与回滚

- 同一任务内移除 `LOCAL_KEEP_DAYS`、按日期保留目录、旧松散两件备份成功判定与过期清理，不增加兼容模式。
- 仅更新维护文档和本任务；归档 Trellis 文档作为历史保留。
- 代码回滚用 Git/镜像版本；涉及数据回滚只能使用仍存在且与版本相容的唯一完整归档。不得承诺已经覆盖的历史恢复点仍可找回。
- 本次规划和后续仓库实现不删除任何真实备份，不更改现有密钥，不连接用户服务器或云资源。新脚本上线前由用户按教程确认实际目标。
