# 简化 Benchmark 场景与题目生命周期

## Goal

把场景收敛为账号私有的 Benchmark 容器，把题目发布变成唯一正式入集动作，并由系统自动维护不可变评测集历史，减少老师重复确认和组集操作。

## Confirmed Facts

- 当前 `Workspace` 是账号私有场景；当前实现仍要求确认场景合同，发布题目后还需手动创建下一版本草稿、加入题目、覆盖审查和冻结。
- 当前已发布题目和 `EvaluationSetVersion` 均是不可变快照，`runtime / judge / provenance` 分区与历史下载能力已经存在。
- 人工评分已绑定不可变题目修订；历史评分依赖已发布修订持续可读。
- 本任务只简化场景、题目和评测集生命周期，不重写已完成的会话、rubric 与人工评分主体。

## Requirements

### R1. 场景是自由 Benchmark 容器

- 场景只要求自由名称和“主要解决什么问题”的描述。
- “一个场景通常服务一个 Skill”只作为培训建议，不保存或强制 Skill 名称、ID、版本或一对一关系。
- 平台不校验题目与场景描述的语义相关性；老师选择目标场景即代表归属决定。
- 新路径取消场景合同作为建题、发布或形成评测集的强制前置条件。

### R2. 单题文本合同

- 一个评测用例由题目标题、老师的任务要求、相关文本输入文件内容、0..N 份可选坏样本及否定原因和一份老师明确认可的标准答案组成；rubric 在平台后续生成。
- 任务要求是老师当时输入给本地 Agent 的原始提示词，必须逐字保存；AI 只能概括题目标题，不能改写任务要求。
- 标准答案是老师最终认可结果的逐字完整正文，Agent 和平台不得摘要、润色或重新生成。
- 原始提示词依赖的必要前文必须进入输入文件内容或由老师补齐，不能静默合并到任务要求。
- 每份坏样本必须有老师明确确认的否定原因；普通中间稿或未选终稿不能自动成为坏样本。
- 坏样本必须是当前真实 Agent 执行中实际产生并被老师否定的结果；AI/Skill 不得合成坏样本。
- 坏样本只保存老师可见的结果正文，不保存系统提示、工具轨迹、private reasoning 或绝对路径。
- 每份坏样本同时保存老师否定原话和老师确认的结构化原因摘要；原话逐字保真，摘要不能替代原话。原话不足以说明原因时必须继续追问或不上传该坏样本。
- 任务要求、输入文件内容、标准答案、坏样本和原因只支持 UTF-8 纯文本或 Markdown。
- 非文本原始资料只能在本地转换为 Markdown 并经老师确认；原文件不进入平台，无法可靠转换的任务不在当前范围。
- 所选文本/Markdown 输入文件默认保存完整原文；只使用部分内容时必须作为老师确认的节选输入，明确标注来源，不能静默摘要或截断。
- 外部 API 与网站手动创建的草稿采用同一可编辑状态；发布前老师可在网站修改全部题目内容，修改推进 draft revision。
- 草稿编辑完成后的唯一主动作是“确认题目并生成打分规则”，同时确认当前题目 revision 并启动 rubric 生成；不再要求先确认、换页后再点击生成。
- rubric 生成失败时保留已确认题目并只提供规则重试；若老师重新编辑题目，则确认与未发布 rubric 失效，重新执行合并动作。

### R3. 坏样本只服务判断

- 坏样本与标准答案进入 `judge` / `provenance`，不得进入未来做题 Agent 可见的 `runtime`。
- 坏样本用于提出扣分点、关键项和一票否决条件，不得退化为措辞相似度或字符串黑名单。
- 老师仍逐项确认最终 rubric；AI 不能自动把一次性偏好固化为规则。

### R4. 确认规则并发布即进入正式评测集

- rubric 审阅完成后的唯一主动作是“确认规则并发布到评测集”，同时确认当前 rubric revision、创建不可变题目修订并进入场景当前正式评测集。
- 新主流程不暴露“规则已确认但尚未发布”的中间状态；老师想暂停时保留可编辑 rubric 草稿即可。
- 不再向老师暴露“下一版本草稿、加入评测集、覆盖确认、冻结”作为日常必经操作。
- 系统在发布事务中自动产生新的不可变评测集版本；第一道题形成 v1，后续发布或修改形成连续新版本。
- 题目发布、当前集合更新和版本历史必须全有或全无；不能出现题已发布但未入集。
- 规则校验、版本包或发布失败时保持 rubric 审阅态，不产生已确认规则、题目修订或半版本。
- 历史版本包和旧 Schema 继续只读可下载，不重新拼装或改写旧 bytes/hash。

### R5. 修改、停用与删除

- 修改已发布用例时，从当前 active revision 派生唯一一个“下一修订草稿”；当前正式评测集继续使用旧 revision。
- 保存新草稿、生成 rubric、审阅或失败都不改变当前正式用例；只有新草稿再次完成“确认规则并发布到评测集”后，新 revision 才原子替换旧 revision 并形成新评测集版本。
- 同一逻辑用例同一时刻只允许一个下一修订草稿；可以继续编辑或放弃，不能并行分叉。放弃后旧 revision 继续有效。
- 停用和删除都会把题从当前评测集移除并自动形成新版本。
- 停用可以恢复；恢复后自动形成新版本。
- 删除不可恢复，但只删除当前可操作用例；历史评测集、旧题目修订、待评结果和评分快照继续保留。
- 停用时未发布的下一修订草稿可以保留和编辑，但不能发布；恢复后可继续。删除时未发布草稿一并作废且不可恢复。
- 停用或删除后禁止提交新的待评结果，也禁止对已有待评结果新增首次评分或重评；已有待评结果和评分历史只读。
- 停用用例恢复后重新允许待评结果和评分写入；删除用例永久保持只读。

### R6. 权限、并发与幂等

- 所有状态变化继续经过当前用户与 Workspace owner 检查。
- 发布、修改、停用、恢复和删除使用 command id、payload hash 与 revision/CAS；重试不能重复生成逻辑变更。
- 同时发布两道题不能丢失其中任何一题；系统串行化或以 CAS 重新读取最新当前集合。
- 版本包构建失败时不产生半发布题或半版本。

## Out of Scope

- 场景成员、组织角色、Skill 安装/运行、自动做题和 Agent 结果回传。
- 复杂文件答案、复杂文件输入的在线解析和 DLP。
- 覆盖率强制门、场景级共同标准、Skill 名称约束和手动版本编排。
- 外部 Agent 鉴权与上传接口；由后续 `benchmark-external-authoring-api` 负责。

## Acceptance Criteria

- [ ] AC1：场景仅凭名称和问题描述即可创建并建题，不要求场景合同或 Skill 字段。
- [ ] AC2：评测用例保存题目标题、任务要求、完整输入文件或明确节选、一份标准答案和多份可选真实坏样本；每份坏样本有老师原话和确认摘要，合成/无充分原因的坏样本被拒绝。
- [ ] AC3：所有题目材料均为 UTF-8 文本/Markdown，非文本原文件不能进入新题目包。
- [ ] AC4：网站手动或外部创建的草稿均通过一次“确认题目并生成打分规则”进入 rubric 处理；重复命令幂等，生成失败无需再次确认题目。
- [ ] AC5：一次“确认规则并发布到评测集”原子确认 rubric、创建不可变题目修订、更新当前正式评测集并产生新版本，无 confirmed-but-unpublished 或额外组集/冻结状态。
- [ ] AC6：修改 active 用例只派生唯一下一修订草稿，旧 revision 保持有效；新 revision 完整发布后才原子替换。停用/恢复/删除自动留史，删除后不可恢复但旧历史可读。
- [ ] AC7：停用/删除用例不能提交新的待评结果或追加首次评分/重评，已有待评结果、评分和旧版本仍可回查；停用恢复后重新开放写入。
- [ ] AC8：并发发布、重复 command、版本包失败和存储失败均 fail-closed，不丢题、不重号、不留半成品。
- [ ] AC9：历史 v1/v2 包保持原 hash/bytes；新 runtime 不含标准答案、坏样本、规则或老师判断。
- [ ] AC10：前端移除强制场景合同与手动组集/冻结主流程，老师发布成功后能直接看到题已进入当前评测集。
- [ ] AC11：`make openapi`、`make test`、`make build`、`git diff --check` 通过，并在合并后的 `main` 复验。
