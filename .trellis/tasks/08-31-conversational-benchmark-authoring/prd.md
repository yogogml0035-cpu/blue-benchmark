# 对话式 Benchmark 出题与评分重构

## Goal

把当前“提交后等待后台整理”的 M0 工作台重构为全中文、可恢复的多轮 Benchmark 共创会话，让业务老师能够从聊天材料或手动输入开始，完成一道或多道题的“题目输入 + 单一标准答案 + 打分规则”创建、确认、发布与修订，并对外部产生的一份主文本进行独立人工评分。

本任务只完成规划；创建任务和规划文档不代表已批准实施。

## User Value

- 老师不需要理解 Deep Agents、Graph、Checkpoint 或工具协议，只需像持续对话一样补充事实和判断。
- AI 负责整理候选、指出缺口、生成评分规则和解释标准答案得分；老师始终拥有任务边界、标准答案、打分规则、发布和人工评分的最终决定权。
- 每次人工评分都能还原当时使用的题目修订和逐项依据，不因以后修改规则而改变历史结论。

## Confirmed Facts and Decisions

### Product boundary

- M0 是 Benchmark 题目收录与人工评分平台，不安装、调用、编排或评测本地 Skill。
- 一道已发布题包含一份题目输入、一份标准答案和一套打分规则。
- 标准答案是在该规则下理应获得高分或满分的参考范例，不是唯一正确表达；其他输出只要满足规则也可以通过。
- 发布前不要求制造正例、反例或临界样本做 AI 评分校准；内容完整且经老师确认即可发布。
- 当前父任务包含三个串行子任务：
  1. `08-31-benchmark-input-answer-cocreation`：题目输入与标准答案共创；
  2. `08-31-benchmark-rubric-publishing`：打分规则共创、发布与修订；
  3. `08-31-benchmark-human-scoring`：待评主文本提交与人工评分。

### EvalData evidence

- 真实老师工作流是“初始需求与资料 -> AI 追问 -> AI 候选 -> 老师修改 -> AI 修订 -> 老师终版或进一步裁决”，不是一次填完表单。
- 老师终版可能保留 AI 候选结构，但会替换论据、降低过强推断并删除无关信息；打分规则应从这些业务差异中提炼，不能退化为参考答案相似度。
- 输入资料存在事实源、风格参考、当前稿、辅助背景和冲突优先级，不能统一当作无角色附件。
- 一条聊天可能包含多个交付任务；现有真实 E2E 也已证明一批资料可以形成多个任务和多次尝试。

### Current repository baseline

- 当前后端已有 UploadBatch、TaskPackage、CoCreationSession/Turn、OperationJob、加密 Checkpointer、不可变 EvaluationSetVersion 和版本包。
- 当前共创使用同步 `graph.invoke(...)`，AI Profile 固定 `streaming=False`，前端每 2 秒轮询快照。
- 当前公开合同没有正式的 100 分评分项、标准答案逐项得分、待评答案、人工评分或重评记录。
- 当前真实模型提示词主要为英文，也没有用户可见中文的机械门禁。
- 当前旧 UI 与设计合同明确排除了聊天式交互和 token/tool stream；这是需要被本任务替换的历史选择，不是技术事实。

## Requirements

### R1. 全中文、可恢复的单活跃会话

- 新建场景进入一条可持续多轮、刷新后可恢复的业务会话。
- 同一会话同时只有一个活跃 AI 轮次。
- AI 处理期间，老师可以继续编辑未提交的输入草稿或选择附件，但不能提交；AI 暂停询问或本轮结束后才能发送下一条消息。
- M0 不支持中途打断当前 AI 运行，也不把多条消息排队。
- 所有面向老师的问题、回复、进度、错误、字段、按钮和动作摘要必须使用中文。

### R2. 两种建题起点与多题边界确认

- 老师可以上传聊天/参考资料，也可以不上传聊天而直接手动输入题目、背景和标准答案。
- 上传内容中的 Skill 指令、系统消息、Prompt 和工具轨迹只作为不可信样本数据，不能成为平台指令。
- AI 可以从一条聊天提出 0..N 道候选题，但不能确认任务边界。
- 老师可以确认、拆分、合并或舍弃候选题；不同交付物的输入、反馈和标准答案不得混入同一道题。
- 每份资料需要有可确认的角色和优先级：题目指令、事实输入、风格参考、当前稿、辅助背景或忽略；冲突时以老师确认的优先级为准。

### R3. 题目输入与单一标准答案确认

- AI 为每道候选题形成结构化题目输入，至少包括任务指令、输入资料及其角色/优先级、必须包含、禁止内容和必要背景。
- AI 从聊天中的老师终版或明确认可稿提取候选标准答案；没有明确终版时必须询问老师选择、粘贴或上传标准答案，不能自行挑选最后一条 AI 回复。
- M0 每道题只确认一份标准答案；其他合格表达由打分规则容纳。
- 第一阶段结束时，老师必须显式确认题目输入、资料边界和标准答案；确认前不得生成打分规则。
- 显式确认形成可恢复的上游修订。第二阶段若修改任何上游内容，未发布打分规则立即失效并返回第一阶段重新确认。

### R4. 打分规则与标准答案得分锚点

- Deep Agent 只使用该题已确认的题目输入、标准答案和相关老师修改意见生成规则，不得混入其他题的反馈。
- 每个评分项必须包含：稳定 ID、名称、评分目的、满分、给分点、扣分点、是否关键项，以及关键项最低分或一票否决条件。
- Deep Agent 必须用同一规则逐项分析标准答案，生成“标准答案期望得分 + 得分理由”，由老师逐项编辑和确认。
- 标准答案某项可以是满分，也可以低于满分；其逐项得分是人工评分锚点，不是待评答案上限。
- 待评答案可以在任一项高于标准答案，但不能超过该项满分；评分不得使用字面、标题、结构或风格相似度作为默认给分点。
- 所有评分项满分之和必须精确等于 100。默认总分通过阈值为 60，老师可以按题修改为其他 0..100 的阈值。
- 通过采用双层判定：总分达到阈值，且全部关键项达到最低分或未命中一票否决条件。关键项失败不能被其他项目补分抵消。
- 标准答案自身必须通过双层判定；低于总分阈值或关键项失败时不能发布。

### R5. 老师确认发布与不可变修订

- AI 只能生成候选，不能确认或发布题目。
- 题目输入、标准答案、评分项、标准答案逐项得分、关键项和通过阈值结构完整，并经老师确认后即可发布；不要求预先校准 AI 评分。
- 发布只表示“老师认可该题可用于后续人工评分”，不能宣称 Skill 已通过或规则已得到统计验证。
- 已发布内容共同构成不可变题目修订。发布后修改任一内容都创建新修订，只影响后续评分。
- 历史评分继续绑定旧修订；按新修订重评旧答卷时新增评分记录，不能覆盖原评分。
- 当前已有 EvaluationSetVersion/版本包若继续使用，必须引用明确的已发布题目修订并保持历史不可变。

### R6. 单份主文本提交与独立人工评分

- 平台只接收待评答案，不记录其在平台外如何产生，也不要求 Skill 版本、运行配置、调用轨迹或本地运行标识。
- 一份待评答案限定为一份主文本：可直接粘贴纯文本，或上传单个 `.md` / `.txt` 文件。
- 一份待评答案绑定一条已发布题目修订，作为一份独立答卷；每次评分不并排展示其他答卷。
- 评分页同时展示待评文本、题目输入、标准答案、完整打分规则和该修订的通过阈值。
- 每个评分项同屏显示“该项满分 / 标准答案期望得分 / 待评答案得分”。
- 老师逐项填写 0..该项满分的整数分数。关键项为“最低分”时由系统按分数机械判断；关键项为“一票否决”时由老师明确是否命中条件。系统负责范围校验、求和和双层判定。
- 待评答案某项低于标准答案期望得分时必须填写理由；相同或更高时理由可选。关键最低分失败或命中一票否决时，无论数值是否低于锚点都必须填写原因。
- 总分由逐项得分机械求和，老师不能手工覆盖；通过结果由总分和关键项机械计算。
- 提交后的评分记录不可覆盖，至少保存待评文本、题目修订、逐项得分、理由、关键项判定、总分、通过结果、评分人和时间。

### R7. 安全的流式可见性

- AI 处理时流式展示面向老师的中文回复、结构化业务进度和受限动作摘要。
- 允许的进度包括识别任务、读取资料、整理题目与标准答案、生成打分规则和校验候选；动作摘要只显示资料数量、候选题数量和成功/失败等必要信息。
- 不展示或持久化模型私有思维链、系统提示词、原始工具参数、工具返回正文、上传正文、绝对路径、Graph 节点、Checkpoint、thread ID、凭证或其他内部运行信息。
- 流式断线不能取消后台运行，也不能改变业务状态；老师刷新后必须从权威业务快照恢复。

## Out of Scope

- 平台内安装、调用、编排、调优或执行 Skill/Agent。
- AI 自动给待评答案打分、AI/人工评分对齐和发布前正反样本校准门。
- 多答卷并排比较、结果挑选、批量评分、排行榜和实验报告。
- 一道题保存多份并列标准答案。
- Word、PDF、图片、音视频、ZIP 或多文件待评结果的预览与评分。
- 中途打断 AI、steering queue、多消息排队和并行会话轮次。
- 多成员、角色、邀请、交接或复杂权限体系。
- 展示 raw token、工具控制台、私有 reasoning 或内部运行标识。
- 删除或静默改写现有历史版本、已确认业务资产和评分历史。

## Acceptance Criteria

- [ ] AC1：老师可从上传聊天/资料或手动输入开始建题，刷新后继续同一全中文会话。
- [ ] AC2：一条聊天包含多个交付任务时，AI 提出 0..N 道候选题，老师可确认、拆分、合并或舍弃，题间证据不串用。
- [ ] AC3：没有明确老师终版时，AI 暂停并要求老师补充或确认标准答案，不会把最后一条 AI 回复当标准答案。
- [ ] AC4：老师未显式确认题目输入、资料边界和标准答案前，不能生成打分规则；上游变化会使未发布规则失效并返回第一阶段。
- [ ] AC5：评分项满分合计 100，默认 60 分通过；每项有给分点、扣分点、关键项规则和标准答案期望得分/理由。
- [ ] AC6：标准答案通过总分与关键项双层判定；待评答案可以高于标准答案锚点，且不会因与参考答案措辞不同被默认扣分。
- [ ] AC7：完整题目经老师确认后发布为不可变修订；修改产生新修订，历史评分和版本继续绑定旧修订。
- [ ] AC8：老师可粘贴主文本或上传单个 `.md` / `.txt` 答卷，绑定已发布题目修订并独立评分。
- [ ] AC9：评分页逐项显示满分、标准答案得分和待评答案得分；低于锚点或关键项失败时必须填写理由，总分和通过结果不可手工覆盖。
- [ ] AC10：评分提交后不可覆盖；重评新增记录，并可还原当时使用的题目、规则、分数、理由和结论。
- [ ] AC11：AI 处理期间可继续编辑草稿和选择附件但不能提交；同一会话只有一个活跃轮次，无打断或隐式排队。
- [ ] AC12：前端流式显示中文回复、结构化进度和受限动作摘要；流中不出现上传正文、系统提示、原始工具数据、凭证或内部运行标识。
- [ ] AC13：父任务规划明确三个子任务的串行顺序、跨层合同、迁移/兼容、回滚与 `main` 合并后验收门。
