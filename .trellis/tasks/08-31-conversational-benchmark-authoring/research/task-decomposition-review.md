# 当前需求的 Trellis 子任务拆分审查

## 判断

当前父任务应规划为三个串行、可独立验收的实施子任务。前两个子任务对应用户原始需求中的两个形成阶段；第三个子任务只接收一份外部产生的待评主文本并完成人工评分，不关心文本如何在平台外生成。

### 子任务一：题目输入与标准答案共创

完整交付：

- 全中文、可恢复的建题会话；
- 上传聊天/资料与手动输入两种起点；
- 从一条聊天提出 0..N 道候选题；
- 老师确认、拆分、合并或舍弃任务边界；
- 区分 prompt、事实资料、风格参考、当前稿、辅助背景及其优先级；
- AI 提取候选标准答案，缺失时追问老师补充或确认；
- 老师确认每道题的题目输入和高分参考答案。
- 第一阶段以老师显式确认为唯一完成门；确认前不得启动评分规则生成。

该子任务完成后得到可稳定引用的“题目内容修订”，但题目还不能发布为可评分 Benchmark。

若第二阶段开始后老师修改题目输入、资料边界或标准答案，未发布打分规则失效并返回子任务一重新确认，不能让旧规则继续引用新内容。

### 子任务二：打分规则共创、发布与修订

以上一子任务确认的题目输入和标准答案为唯一上游，完整交付：

- Deep Agent 从题目、标准答案、聊天修改意见中生成评分项；
- 每项包含满分、给分点和扣分点；不可补偿的事实、合规、资料泄漏等要求可设为带最低分或一票否决条件的关键项；
- Deep Agent 用同一套规则逐项分析标准答案，给出标准答案在每项的期望得分和理由；
- 标准答案每项可为满分或非满分通过分；期望得分是人工评分锚点而非待评答案上限；
- 汇总满分、参考答案期望总分和通过条件；
- 各评分项满分之和固定为 100，默认 60 分通过；老师可按题调整阈值，但发布后调整产生新修订；
- 通过采用“总分阈值 + 全部关键项通过”的双层判定，标准答案自身也必须满足；
- 老师编辑、确认并发布；
- 发布后修改创建新修订，历史评分仍绑定旧修订。

该子任务完成后，一道题才成为可供后续人工评分使用的已发布 Benchmark。

## 为什么可以独立验收

- 子任务一的产物是稳定、老师确认的题目与参考答案；没有它，评分规则没有可信输入。
- 子任务二只消费已确认修订，可以独立测试规则生成、自洽检查、发布和版本化。
- 两者虽然在用户体验上属于同一条会话链，但业务确认点和失败恢复点不同，适合串行分支闭环。

## 为什么不按前端 / 后端拆

两个阶段都涉及 Backend Schema -> OpenAPI -> 前端生成类型 -> 会话 UI -> 测试的完整跨层合同。按技术层拆会产生无法单独验收的半成品，也违反项目“一项稳定业务职责一个短生命周期分支”的闭环原则。

### 子任务三：待评文本提交与人工评分

完整交付：

- 老师粘贴一份主文本或上传一个 `.md` / `.txt` 文件作为待评答案，并绑定一条已发布题目修订；
- 一次提交只对应一道题的一份独立答卷，老师独立完成评分，不并排比较其他答卷；
- 平台展示该修订的题目、参考答案、评分项、关键项与通过阈值；
- 老师逐项录入人工得分和关键项判定，系统校验范围、汇总 100 分总分并执行双层通过判定；
- 评分页逐项并列显示满分、标准答案期望得分和待评答案得分；低于标准答案锚点或关键项不通过时强制填写理由，相同或更高时理由可选；
- 评分记录保存待评答案、题目修订、逐项得分、关键项结论、总分、通过结果和老师说明；
- 再次评分或按新题目修订重评时新增记录，不覆盖历史。

该子任务不安装、调用、编排或自动识别 Skill，也不保存 Skill 版本、运行配置、调用轨迹或本地运行标识。M0 不支持 Word、图片、ZIP 或多文件待评结果。
