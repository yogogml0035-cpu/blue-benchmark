# 第一性原理与对抗审查：M0 收题链重新对齐

## 真正问题

业务老师需要把本地 Agent 工作中已经形成的真实任务标准低摩擦地沉淀到平台，而不是把平台变成必须手工上传、再次拆题、再次组集和再次冻结的流程工具。

## 不可约减事实

1. 平台必须知道题目输入、允许材料、标准答案和评分规则，才能重复评测。
2. 老师是业务标准的最终确认者，Agent 和平台 AI 只能整理候选。
3. 账号与场景归属必须由服务端鉴权决定，不能依赖 Skill 记忆或客户端租户字段。
4. 当前结果与历史版本是不同需求：日常操作应简单，系统仍需自动保留不可变历史。
5. 未来做题端不能看到标准答案、坏样本和 rubric。
6. 评测可复现依赖原任务不被改写；任务要求必须逐字保存原始提示词，缺失上下文进入输入内容而不是静默补写。

## 被推翻的旧假设

- “场景必须有一套所有题共同继承的合同”不是 M0 必需事实；它阻止自由题库并带来级联复核。
- “发布题目”和“加入/冻结评测集”需要两次老师确认没有新增业务判断，属于重复操作。
- “平台应重新理解本地 Agent 已整理的材料”会产生双重解释和标准漂移。
- “一个场景必须绑定明确 Skill 身份”限制了题库复用，不是当前价值所需。
- “普通删除必须抹掉历史”与平台的可追溯目标冲突。

## 采用的最小机制

- 场景：自由名称 + 问题描述 + 账号隔离。
- 本地收题：一个评测用例、文本-only、完整标准答案、可选带原因坏样本、老师上传预览确认。
- 外部 API：只严格校验并保存草稿，返回精确网站链接，不启动平台 AI。
- 平台网站：老师打开草稿后再生成 rubric 候选并审阅。
- 发布：一次动作，自动进入当前集合并留下新版本。
- 生命周期：停用可恢复；删除不可恢复但保留历史。
- 外部接入：场景绑定最小权限 token；平台 API独立于具体 Agent。

## 对抗检查与修正

### 跨租户错投

- 风险：Skill 传错 Workspace ID或读取另一个账号场景。
- 修正：token 固定 user/workspace，上传不信任租户字段；每次预览显示服务端当前场景名。

### 双重解释

- 风险：本地 Agent 整理后平台再次拆题，标准答案发生漂移。
- 修正：本地上传 canonical 单题；外部 API 只机械校验和保存草稿，老师进入网站后才按正常流程生成 rubric。
- 草稿不是不可变历史：老师可在网站修正任意题目内容；外部上传 receipt/hash 保留来源，Skill 本身不能再读写草稿。
- 题目确认与启动 rubric 没有两个独立业务判断，合并为服务端命令；生成失败只重试规则，重新编辑才使确认失效。
- rubric 确认与发布入集也没有两个独立业务判断，合并为服务端命令；失败保持可编辑规则草稿，只有完整成功才产生题目修订和评测集版本。

### 半成品堆积

- 风险：缺题或缺标准答案也创建平台草稿。
- 修正：本地继续追问并阻止上传；服务端再次机械校验。

### 坏样本污染规则

- 风险：普通中间稿被当 Bad Case，或措辞被机械禁用。
- 修正：坏样本必须带老师确认原因；只作为判断证据，rubric 仍由老师确认。
- 坏样本只能来自真实执行记录，不能为了丰富规则由 AI 合成；所选输入文件默认完整保存，节选必须显式标注和确认。
- 坏样本否定原因保留老师逐字原话；Agent结构化摘要必须确认且不能替代原话，原话含糊时继续追问。

### 发布/版本半成功

- 风险：题已发布但未入集，或包生成失败留下可见版本。
- 修正：staging/hash/ready + 数据库 CAS；读取只认 ready，失败可 reconciliation。
- 已发布用例修改只产生唯一下一修订草稿；当前 revision 在新草稿完整发布前持续生效，避免编辑过程污染正式评测集。

### 删除破坏历史

- 风险：物理删除 revision 导致旧待评结果和评分无法解释。
- 修正：业务墓碑，当前集合移除，历史 revision/score 保留。
- 停用/删除后的历史 GET 与新的 evaluation write 分流：前者保持可读，后者包括新待评结果、首次评分和重评全部拒绝；停用恢复后才重新开放。

### 跨修订评分错配

- 风险：新规则评分却用旧 criterion 展示，或复制待评结果造成历史分叉。
- 修正：一份不可变 submission，每条 score 自带 revision，历史按各自 revision 渲染；目标 revision 必须与原用例共享 `question_draft_id`，另一个用例必须新建待评结果。

### 凭证泄漏

- 风险：外部 token 进入日志、Git、URL 或获得过大权限。
- 修正：高熵 token、只存 hash、固定单 Workspace `draft:create` scope、主动撤销/重新绑定失效、URL 不携带 token。长期 token 不定期自动过期，以最小权限换取低摩擦；一次性连接码仍短时过期。

## Task Split Rationale

- 跨修订评分只触及 Submission/Score/read model，独立可验收。
- 生命周期简化触及场景、题目、rubric、版本和评分门禁，是独立领域变更。
- 外部 API 依赖稳定生命周期，但凭证与客户端合同可独立验收。
- `ai-eval-push` 是独立软件和远程仓库，应在真实 API 合并后单独管理。
