# Benchmark M0 后端接口与上传 Skill 重构

## Goal

把当前仓库从包含临时前端的完整工作台，重构为以后端业务能力和外部收题接口为核心的 M0 工程；移除不再继续维护的现有前端实现，并在仓库根目录 `skills/` 下提供一个可由业务老师本地 Agent 调用的题目上传 Skill。

最终目标不是“删掉一个目录”，而是形成一条可验证的最小链路：本地真实工作过程经过老师确认后，被整理为结构化评测用例草稿，通过受控接口进入指定场景；平台后端继续负责业务事实、权限、幂等、状态、版本和后续规则生成。

本任务当前只处于需求与设计规划阶段，尚未批准实施。

## Background and confirmed facts

### 最新业务构想

- M0 首要解决真实业务问题如何沉淀为评测用例，而不是先建设完整运营平台。
- 本地 Agent/Skill 负责从真实交互中整理结构化材料，不要求老师导出完整聊天记录后再手工上传。
- 一个外部上传的评测用例草稿包含六类材料：
  - AI 概括、老师确认的题目标题；
  - 老师逐字原始任务要求；
  - 完整输入文件原文，或有来源标记并经老师确认的节选；
  - 可选的真实坏样本；
  - 老师反馈原话和经确认的原因摘要；
  - 老师逐字认可的标准答案；
  - 本地 Agent 在此次任务中实际读取并应用的记忆材料。
- “老师反馈”不作为脱离上下文的独立顶层材料：每组反馈必须绑定一个具体坏样本，保留“哪个实际结果因为什么被老师否定”的因果关系；一道题可以有 `0..N` 组坏样本与反馈。
- 坏样本只能来自真实执行且被老师明确否定的结果；Skill 不得合成坏样本。
- Skill 只负责显式整理、预览确认和上传草稿，不替老师生成规则、确认题目或发布。
- 原始完整聊天、系统提示、私有推理、工具参数、Checkpoint、主机路径、凭证等不应进入平台收题载荷。
- 记忆材料只收集当前任务实际读取到的内容，不扫描或上传本地 Agent 的整个记忆库，也不把“可能相关但此次未读取”的记忆伪装成本次输入。
- 记忆材料保存本次实际读取到、且经老师确认的原始记忆条目或片段；可以附带安全的来源标签和 AI 摘要，但摘要不替代原文，来源不得包含本地主机路径。
- 用户已明确把后续前端设计与实现交给其他老师，当前仓库里的临时前端不再作为继续演进的基础。
- 用户负责本阶段的后端、数据库与上传 Skill；新的正式前端由其他老师后续基于后端数据库和 API 实现。
- 删除旧前端后允许存在一段无正式用户界面的过渡期：本阶段只保证后端 API 与上传 Skill 可用，不要求普通老师在没有新前端时完成规则确认和发布。
- M0 的首次授权由管理员完成：管理员针对一个业务场景创建专属凭证，再把该场景连接配置给上传 Skill；新建或切换场景时，创建新的场景凭证并替换 Skill 当前配置。
- 一个凭证只能绑定一个稳定场景 ID，不允许由 Skill 在上传请求中任意指定或跨场景覆盖。
- 最终对接平台接口的 Skill 必须放在仓库根目录 `/Users/hsikey/Company/skill-eval-platform/skills` 下。

### 当前源码事实

- 当前仓库已经实现外部收题能力，并非从零开始：
  - 网站账号为指定场景创建一次性连接码；
  - 本地客户端兑换为固定绑定账号和场景、仅含 `connection:read` 与 `draft:create` 权限的 Bearer token；
  - `POST /api/external/evaluation-case-drafts` 幂等创建待审阅草稿；
  - 当前请求 schema 已覆盖任务要求、输入文件、坏样本、老师反馈和标准答案。
- 当前外部收题响应仍返回依赖前端地址的 `draft_url`；后端设置、CORS、测试和 README 也存在前端 URL 假设。
- 当前 `Makefile` 的 `start-all`、`test`、`contract-check`、`typecheck`、`build`、`openapi` 均直接依赖 `frontend/`。
- 当前 OpenAPI 合同生成的一份 TypeScript 客户端保存在 `frontend/src/lib/api/generated.ts`；删除前端后必须重新定义 OpenAPI 漂移检查的后端所有权，不能连合同门禁一起误删。
- 当前后端不只是“上传题目接口”，还实现了登录/场景、建题会话、AI 共创、rubric 生成与发布、评测集版本、待评结果和人工评分等能力。
- 当前后端业务事实由 SQLAlchemy/Alembic 数据库和服务层持有，AI Runtime、Operation Worker 与 Checkpointer 只承担受限 AI 执行和连续性，不应因前端重构而改变权威边界。
- 当前 `main` 工作区干净；本任务与已有但无关的服务器部署规划任务分开管理。

## Requirements

### R1. 前端删除必须按依赖边界完成

- 删除当前产品前端实现及只为该实现服务的构建、测试、生成物和运行脚本。
- 在删除前识别并保留仍属于后端公共合同、未来前端接入或 Skill 使用所需的能力。
- 不得留下名义上已删除前端、实际上仍要求 Node/pnpm/Next.js 才能完成后端测试或 API 合同验证的半删除状态。
- 不得因删除前端而误删后端 API、业务状态机、数据库迁移、真实 AI Worker 或后端验收脚本。

### R2. 后端 API 成为当前仓库的核心交付物

- 明确 M0 对外支持的 API 边界、认证方式、幂等规则、错误合同、资源标识和状态查询方式。
- 外部收题只能创建绑定目标场景的待审阅草稿，不得直接确认、生成规则、发布或修改已有正式用例。
- 服务端继续校验 payload 大小、文件保真、坏样本真实性边界、私有运行信息泄漏和重复命令。
- OpenAPI 必须成为 Skill 与未来前端共同依赖的权威合同，并有不依赖现有前端实现的漂移检查。
- 后端数据库必须持久化前端未来展示所需的结构化评测用例内容；前端只消费后端公开合同，不读取或推断数据库内部结构。

### R3. 仓库内提供题目上传 Skill

- Skill 放在根目录 `skills/<skill-name>/`，遵循标准 `SKILL.md` 结构；只有实际需要时才增加脚本或 references。
- Skill 应在用户显式要求把当前真实工作沉淀/上传为评测用例时触发。
- Skill 必须在上传前向老师展示结构化预览并取得确认；缺少标准答案或关键材料时继续追问，不得静默补写。
- Skill 不得改写老师原始任务要求和标准答案，不得静默截断文件，不得合成坏样本，不得上传完整聊天或私有 Agent 运行信息。
- Skill 对成功、幂等重放、认证失效、连接撤销、校验失败、限流和网络失败给出可操作反馈。
- 凭证不得写入 Skill 源码、Git、日志或普通输出。
- “绑定到 Skill”只表示 Skill 从本机私密配置读取当前场景的 API 地址和访问凭证；明文凭证不得进入 `SKILL.md`、脚本默认值、版本控制文件或上传 payload。
- M0 一次只使用一个当前场景连接；切换场景由管理员显式替换本机配置，不要求 Skill 内置多场景选择器。
- Skill 可以从本地 Agent 当前可见的会话上下文自动提取六模块候选，但不承诺覆盖已被压缩、截断或不可访问的完整历史。
- 上传前必须展示结构化预览并由老师确认；最终上传事实以老师确认后的预览为准，而不是以 Agent 对历史上下文的自动推断为准。
- Skill 必须单独列出此次任务中实际读取到的记忆材料候选；读取不到、无法证明本次读取或老师不确认时，记忆材料为空，不得为了凑齐模块而补造。
- Skill 不得上传整个记忆文件、记忆库索引、其他任务片段、其他用户信息、凭证或本地主机路径。

### R4. 重构必须明确删除和保留的产品范围

- 不能把“前端暂时不在本仓库实现”自动推导为“所有只能通过前端操作的后端能力都应删除”。
- 必须在设计阶段逐项裁决登录、场景管理、连接码、建题会话、rubric、发布、评测集版本、人工评分等现有后端能力是：保留为正式 API、延期但保留、还是删除。
- 不提供无依据的历史兼容层；若最终决定替换现有合同，需要明确迁移/清库边界、回滚方法和验收环境。

### R5. 无前端过渡期的可验收边界

- 本阶段不提供替代前端，也不要求上传 Skill 承担规则审阅、发布或后台管理职责。
- 后端中供未来前端使用的登录、场景管理、草稿读取/编辑、规则确认和发布 API 可以保留并独立验证。
- 过渡期通过 OpenAPI、后端自动化测试、真实 HTTP 验收脚本和数据库读取结果验证业务闭环，不以浏览器页面作为当前完成条件。

### R6. M0 评分维度采用三字段最小模型

- 平台 AI 根据已确认的六类评测材料生成 `1..N` 个评分维度初稿。
- 每个评分维度的业务字段只有：
  - `name`：维度名称，字符串；
  - `description`：维度说明，字符串；
  - `pass_score`：及格分数，数字。
- 三个字段的初始值都由 AI 建议；业务老师可以新增、删除和修改任意维度后再确认。
- 不把现有后端中的 `max_score`、独立给分点、独立扣分点、关键项模式、标准答案预期得分和预期理由继续暴露为 M0 评分维度业务字段。
- 维度说明必须在一段文本中清楚表达该维度判断什么、达到什么表现可获得较高评分、哪些表现会降低评分；不因减少结构化字段而允许空泛描述。
- 每个维度的固定满分、总分换算和整题通过算法属于系统级规则，不作为老师逐项编辑的第四类字段。
- 每个维度固定为 10 分满分；每一个维度都必须达到自己的 `pass_score`，任意维度低于门槛时整题不通过，其他维度的高分不能补偿。
- 100 分制换算只用于结果展示，不改变逐维度必须及格的判定。
- 发布时冻结老师确认后的维度列表及三字段内容；之后修改必须形成新的规则草稿或题目修订，不能覆盖已发布历史。

## Out of scope for the current planning baseline

- 由本任务重新设计或实现新的正式前端。
- 让 Skill 从平台拉取题目、执行被评 Skill、回传待评结果或自动评分。
- 用 Skill 直接发布评测用例或绕过老师确认 rubric。
- 把完整本地聊天记录、系统提示、私有推理或工具轨迹上传到平台。
- 在规划得到最终确认前删除产品代码、运行 `task.py start`、建开发分支或提交实现。

## Acceptance Criteria

- [ ] 明确删除清单、保留清单和未来前端接入合同；不存在模糊的“前端相关都删掉”。
- [ ] 删除现有前端后，仓库安装、启动、测试、OpenAPI 生成和合同漂移检查不再依赖 Node/pnpm/Next.js。
- [ ] 外部收题 API 的认证、场景绑定、schema、幂等、限流、撤销、错误和成功响应均有可执行合同与测试。
- [ ] `skills/` 下的 Skill 能以真实 API 完成一次老师确认后的评测用例草稿上传，并正确处理幂等重放和失败路径。
- [ ] Skill 上传内容符合原始任务、文件、坏样本、反馈和标准答案的保真与隐私边界。
- [ ] Skill 能区分并上传“此次任务实际读取到的记忆材料”，且不会扫描或泄漏整个本地记忆库、其他任务或其他用户内容。
- [ ] 后端 OpenAPI 是未来前端和 Skill 的单一接口事实源，并能在 CI/本地独立校验。
- [ ] 评分维度数据库、API、AI 输出和未来前端合同统一为 `name + description + pass_score`，不残留依赖旧复杂 rubric 字段才能工作的评分或发布路径。
- [ ] 业务老师可以对 AI 建议的评分维度执行增、删、改，并在发布前看到最终确认结果。
- [ ] 评分结果严格执行逐维度及格：任意一个维度低于 `pass_score`，整题不通过；100 分换算不改变该结论。
- [ ] 使用真实业务样本完成不泄漏正文的验收；真实 Provider 相关能力必须区分为实际运行证据和未验证部分。
- [ ] 实施任务按独立可验收子任务拆分，每个子任务遵守任务分支、质量检查、提交、合并 `main`、`main` 复验、归档和安全删分支的闭环。

## Delivery split

1. 后端领域模型与 API：六类材料、三字段评分维度、逐项及格、迁移、AI 输出、发布快照和评分链。
2. 后端工程收敛：删除旧前端和 Node/Next.js 依赖，保留并验证后端 OpenAPI、启动与测试入口。
3. 上传 Skill：仓库内 Skill、私密配置、结构化预览、确认上传、失败反馈和真实 HTTP 验收。

三个子任务必须串行完成；前一项合并并在 `main` 复验后，才能开始下一项。
