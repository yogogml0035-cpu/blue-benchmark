## 为什么保留一个跨层切换子任务

- 新评分结果增加分档和依据，且完整消息/执行状态持久化后必须支持完整删除；这些读写合同、页面行为和旧入口删除具有共同的完成条件。
- 如果把只改 DTO、只改后台或只改页面分别作为可发布子任务，现有保存/删除链路可能缺字段或遗留原文，并诱发临时转换/双轨。
- 因此 C3 的内部步骤可以分模块执行，但其验收和合并是同一个完整语义单元；不新增允许半迁移进入 main 的例外。
- C2 是被 C3 直接复用的底层能力，不提前注册第二个生产入口；C2 之前保留旧产品路径不等于提供兼容层，生产替换只在 C3 发生。

## 启动、分支与 main 门禁

1. 本轮不 commit/merge/start。后续取得任务树实施批准后，先在当前规划分支按项目质量门提交并集成任务文档基线，使从 main 创建的子 worktree 能读取完整规划；这一步不是启动父任务做业务开发。
2. 按用户实际批准范围推进；只批准某个子任务时不得顺带启动其他子任务。父任务不通过 task.py start 进入业务实施；启动拥有下一交付物的子任务。
3. 每个子任务开始前验证依赖的完成/归档记录及实际交付 commit 已包含在最新且已复验的 main 中；仅有目录、状态字段或 meta.depends_on 不足以通过。
4. 每个子任务从该 main 创建独立 codex/<slug> 分支和外部 worktree，重新检查 pwd/分支/status/worktree，再复制主工作区 .env 并覆盖独占测试目标。子任务真实 branch/worktree_path 在实际创建后登记，不能共用父任务规划分支。
5. 仅在相应子 worktree 执行 task.py start；不得绕过非空 context、实施批准或前置交付门禁。
6. 每个子任务都完成分支质量门 -> 提交 -> 串行合并 main -> main 复验 -> Trellis 收尾 -> 自有 worktree/分支清理。main 前进时先同步并重验，不 force/reset 或挪用其他工作区改动。
7. C3-C4 合入的是已用新建验收库验证的新代码，不是旧演示库迁移。C5 前不把现有旧两库接入新合同或自动重载部署；需要隔离/停用旧演示进程时只管理身份已确认的本项目进程，禁止以旧数据兼容兜底。
8. C5 的 reset 工具本身先在隔离资源验证并合入 main、复验，再按一次性授权操作当前两库；main 代码验收与实际环境切换分别留证。
