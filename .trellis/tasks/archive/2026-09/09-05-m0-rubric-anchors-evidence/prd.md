# M0 评分维度：分档辅助、可核查依据与生成链路重构

## 状态与决策来源

- 状态：2026-09-06 实施批准已获得。业务决定已收敛；按 task-map.md 顺序启动 C1-C5。
- 本文是需求的当前唯一口径，依据本次对话最新确认；D01-D23 与被否决方案保存在 `research/decision-log.md`，不再把已确认事项列为开放问题。
- 最终审阅入口为 `review.md`；技术未知项在获批后按验收门验证，不以文档通过冒充产品、真实模型或数据库验证完成。
- 本任务现为父任务，拥有共享需求和跨子任务验收；C1-C5 的职责、前置条件与一次性切换边界见 `task-map.md`。用户本轮批准拆分，不代表批准实施。

## 目标

让老师在 M0 审改评分维度时，理解建议通过分对应的表现要求，并能核查维度与建议通过分的材料依据；保留老师对全部题目内容和最终标准的修改权。

## 范围

- 包含：基于六类题目材料生成候选维度、分数锚点说明、建议通过分，以及支持维度和建议通过分的简短依据；老师查看、勾选、编辑、保存和发布这些内容。
- 包含：以最新正式 Deep Agents 优化本题材料核查和完整候选生成；选型对照只用于验证，不形成多套生产生成路径。
- 包含：Deep Agents 后台生成期间的加载状态、真实阶段和可读流式反馈；允许较长等待，不仅显示静态提示或旋转图标。
- 包含：完整公开生成过程的持久保存/回看、同一道题运行上下文的保存与执行恢复；以当前 Docker PostgreSQL 为持久化目标，为 M1 对话和中断恢复准备运行基础。
- 包含：当前项目旧测试数据的一次性清理、新合同下的重新上传验证，以及从 `.local-samples` 真实会话整理可追溯测试数据并完成集成、冒烟与 main 复验；不以用户重构后自己测试替代开发验收。
- 包含：沿用现有确认门禁删除题目，同时清除该题全部在线生成过程、上下文和受管理副本；清理未完成时不显示删除成功。
- 不包含：M1 拉题与新稿生成、对新稿或标准答案实际打分、人工评分提交、跨题能力汇总、自动优化被测 Skill、重新引入旧共创或版本包流程。
- 不包含：自动检索相似题、自动将其他题作为参考、跨题标准继承或全局老师偏好学习；本次不增加跨题参考入口。
- 不包含：自动到期清理仍存在题目的历史、原始样本销毁、自动备份产品或旧题恢复入口。

## 业务场景

### 场景 1：生成本题的候选维度

- 根据题目、参考样例、Bad case、绑定反馈、标准答案和记忆材料生成本题的候选维度。
- 标准答案是老师已认可的正向依据；Bad case 和反馈表达真实被否定的结果及原因。不得用外部通用写作偏好推翻老师已明确的业务标准。
- 文案评测研究用于检查可能遗漏的关注方向，不直接把所有通用维度套入每道题；具体评判要求必须能回到本题材料。
- 维度应包含本题具体的评判要求，而不是仅生成“准确性”“新颖性”等孤立标签。

### 场景 2：分档说明辅助老师设定通过分

- 每个维度固定满分 10 分；AI 建议通过分始终是 0–10 中的一个整数，老师也可修改为该范围内任意整数。
- 保留现有“勾选是否纳入本题评分项、编辑维度内容、修改最低通过分”的主操作，不改成选择档位来决定分数。
- 分档说明以明确分数对应具体表现的方式辅助理解。例如有 4 分和 6 分的说明，不妨碍老师填 5 分。
- 初始生成提供少量关键分数描述，并包含 AI 建议通过分对应的表现说明；不要求列满 0–10 的全部 11 个整数。未列出的分数由老师参照相邻描述判断。
- 分档不是建议通过分的范围，也不是可填分数的白名单。AI 先建议一个整数，再确保生成内容解释这个分数，不是从预设锚点中挑通过分；老师之后仍可填没有独立描述的整数。
- 老师普通改分不自动补档、改写或覆盖原有描述；继续保留内容并提示核对关联说明。
- 不同维度可有不同的最低要求。新颖性可以被纳入维度但通过分很低，不引入加权总分或跨维度补偿。
- 分档说明属于 M0 的规则制定与审改辅助，不是 M1 的评分执行。

### 场景 3：按需查看简短依据

- 每条候选维度提供“查看依据”交互；默认不强迫老师展开或阅读全部依据。
- 依据由后端生成，并与维度一起保存；不是前端临时补写，也不是仅首次生成时可见的提示。
- 展示支持材料的来源、相关内容以及简短说明，使老师能核查，而不是只看到“根据老师反馈”等笼统理由。
- 依据同时解释两件事：为什么生成该维度；材料体现了什么最低要求，为什么 AI 建议该通过分或对应表现水平。
- 明确区分“老师明确表达的要求”和“AI 根据材料作出的推定”；不能将推定伪装成老师已经确定的标准。
- 依据是可供核查的简短说明，不展示模型私有推理过程；不能把有引用或有解释等同于结论已经正确。

### 场景 4：老师可以修改全部内容

- 在现有允许编辑、审改的状态下，题目及材料、维度内容、分档说明、通过分和依据均可修改；AI 不拥有不可修改的最终结论。
- 老师决定哪些维度被保留；保存确认后的内容是最终规则。
- 修改维度内容后，保留原分档和依据并继续允许编辑，同时提示老师核对关联内容。
- 普通编辑不触发后台自动重写，不覆盖老师已经作出的修改；老师可一起修正后再保存确认。
- 本次不因“全部可编辑”而绕过现有已发布题目的重新打开审改门禁。

### 场景 5：主动修改材料并重新生成

- 保留现有“保存并重新生成”的语义；仅修改识别标题不触发材料重新生成。
- 老师主动修改题目材料并选择重新生成时，可以作废并整套替换原维度、分档和依据，包括此前的人工修改。
- 执行前明确提示会替换上述内容，老师确认后再执行；取消确认不应提交材料或启动生成。
- 普通编辑与主动确认后整套重新生成必须清楚区分。
- 不新增用户可见的历史版本、旧新双轨或隐藏兼容入口。

### 场景 6：长时间生成也能看见实际进展

- 用户接受生成等待很久，前提是老师能持续看见任务正在生成、当前到了哪一步，以及过程中可读的流式反馈。
- 加载体验参考 Codex/ZCode 的过程可见性，不要求另做桌面端或聊天产品；反馈展示在当前题目的生成加载区域。
- 展示实际工作阶段和可公开的过程说明，而不只是一直不变的“正在生成”。无新内容、连接异常、重试、失败、完成须可区分，不能用动画或假百分比冒充工作进展。
- 生成中的内容不是已确认评分规则；完整结果保存后，仍进入原来的勾选、编辑、整数通过分设定和确认流程。
- 生成完成后保留可回看的完整公开流式内容和过程记录，不能仅存最后结果或一段摘要；上下文记忆也需要可靠保存，不因页面关闭或进程重启而丢失。
- 保留过程不等于公开内部推理或增加旧评分标准的恢复入口；公开范围、访问权限与题目业务状态保持清楚。

### 场景 7：恢复本题运行，不重新丢失上下文

- 已处理的材料、生成中的工作上下文和待继续的步骤需要持久保存；恢复时继续本题的逻辑运行，而不是无条件从头生成。
- 页面重连、后台执行恢复和主动整套重生成是不同动作。材料已经替换或运行已经过期时，不能用旧上下文覆盖新的题目和老师修改。
- 未完成的模型请求可能重试，但已公开过程应保留并说明中断/重试，不伪装成没有发生过。

### 场景 8：为 M1 的交互连续性准备基础

- 后端设计需要容纳后续 M1 的中断、询问用户、收到回复后恢复和多轮聊天，不能把 Agent 固定为只接受一次输入、返回一次结果的黑盒。
- 本次 M0 仍不增加新稿、评分执行或聊天业务入口；运行基础、消息与恢复机制提前设计并在本次重构中验证。
- 同一题目/会话内的上下文保存已确定；本题要求不自动影响其他题，自动相似题参考明确不在本次范围内。

### 场景 9：本题要求独立于其他题目

- 老师确认的要求只作用于当前题目，不因题库扩大而不断继承其他题的要求。
- 本次不自动引用其他题的材料、维度、分档、通过分或老师修改；不能仅因题目相似、同属一个场景或出自同一位老师就认定标准通用。
- 新增或修改 B 题，不应自动修改 A 题已保存的标准，也不应成为 A 题下次生成的隐藏输入。本题材料不变不代表模型每次逐字输出相同，但不应增加由其他题变化导致的隐性影响。
- 现有的参考样例和记忆材料仍属于本题输入。若老师明确把旧内容整理进本题材料，按本题所提供的内容处理，不建立对旧题的隐式动态继承，也不自动把参考升级为硬性要求。
- 本次明确不做自动查找相似题或将其他题带入生成，也不新增旧题候选展示入口；未来如需复用，另行确认使用场景和标准适用边界。

### 场景 10：清理旧测试数据后按新合同重新上传

- 用户确认目前项目数据库全部是测试数据，可随本次重构一次性删除，不要求保留旧题、旧维度、老师对旧测试题的修改或旧运行记录。
- 仅处置当前本地项目数据库；不删除原始 `.local-samples` 文件、其他项目数据或整个 Docker 存储，也不将授权延伸至未来新上传的数据。
- 切换后不兼容、不转换或补写旧题合同。用户可按新流程重新上传；原有数据库内的账号会话和上传凭证随清理失效，按现有首次注册和场景凭证流程重新建立。
- 数据清理授权已明确，但实际清理在最终计划获实施批准后按切换步骤执行，不在这轮访谈立即执行。

### 场景 11：用真实会话验证重构结果

- 开发过程中必须基于 `.local-samples` 下的会话日志和附件生成测试数据，保留题目、材料、Bad case 与对应反馈、标准答案之间的真实关系。
- 真实回放与派生反例清楚区分；不能截掉关键上下文、编造老师认可的答案，或用生成器自己的输出反过来充当验收标准。
- 原样本保持不变；样本缺失或解析失败时明确说明，不能静默换成占位样例后声称真实数据验收通过。
- 用真实数据验证上传、生成、可读进度、分档/依据审改、保存发布及执行恢复；集成测试、冒烟测试和 main 合并后复验均属于交付要求。

### 场景 12：删除题目不遗留生成原文

- 用户确认删除题目时，一并删除该题的完整生成过程和运行上下文，不仅从列表隐藏或只删除题目行。
- 保留现有权限和版本校验：生成中不可删除，已发布必须先重开审改，曾发布题目仍须输入当前完整标题确认；取消或校验失败不清理关联内容。
- 删除覆盖该题历次生成/重生成的过程、上下文、工作文件及系统管理的在线副本，不仅覆盖最后一次运行；不影响其他题、共享场景/凭证或原始 `.local-samples`。
- 处理中、失败及可重试状态真实可见，全部关联清理完成后才显示删除成功。清理期间不允许继续修改、生成、发布或恢复该题，失败不能让原文永久留在后台而界面却声称成功。
- 删除后不能通过详情、生成历史或恢复入口读回原文，也不能被迟到运行写回。最小的无原文幂等回执可以保留，但不构成旧题恢复能力。

## 验收口径

- 老师仍通过原来的勾选、内容编辑和整数输入完成维度审改，不被限制为仅选择某些档位分数。
- AI 的建议通过分和老师修改后的通过分均是单个 0–10 整数；即使 5 分没有独立锚点，老师仍可填写 5。
- 分档说明描述本维度的可观察表现，能辅助理解建议分数，不只用“差、一般、好”等词凑档位。
- 初始 AI 结果用少量关键分数解释表现，并为所建议的整数通过分提供对应描述；老师随后修改通过分时，不因缺少该整数的独立描述而无法保存，也不自动补写或重生成。
- 老师能按需查看维度和建议通过分的简短依据，核查对应材料，并识别明确要求与 AI 推定。
- 老师可以修改并保存全部题目内容、维度、分档、通过分和依据；刷新或重新打开后不丢失已保存内容。
- 修改维度后原关联内容被保留，老师获得核对提示，没有后台静默重写或覆盖。
- 主动重新生成在执行前说明替换范围；取消不会产生提交或生成，确认后整套重新生成。
- 页面和接口不新增新稿、实际得分或评分执行步骤，M0/M1 边界保持清楚。
- 使用实施时最新正式发布的 Deep Agents；不能为迁就旧示例而降级，版本和流式 API 的实际验证结论可核查。
- 老师在较长生成期间能看到真实阶段和不断到达的可读反馈；不得先等后端全部完成，再用前端打字动画假装实时。
- 连接等待、任务运行、重试和失败不混成同一种无限加载；完成状态以完整结果成功保存为准。
- 生成完成后能够回看完整公开过程；模型上下文被压缩或后台恢复后，公开历史仍可读取，不能只剩摘要。
- 同一运行的上下文/工作状态持久化到当前 Docker PostgreSQL；恢复能力有真实执行证据，不以环境变量或检查点表存在冒充接入成功。
- 后台重启不会无条件重复初始输入或覆盖更新的题目；异常中断的可见内容保留并清楚标识。
- 新增、修改或删除 B 题，不会自动修改 A 题标准、触发 A 题生成或改变 A 题生成时读取的材料范围；重连、摘要、重试和恢复同样保持本题隔离。
- 最终选定的新合同一次性替换旧的“两字段即完整维度”合同；相关维护文档、生成文件和测试同步，不保留旧新两条可执行路径。已授权清理的当前项目测试数据按切换方案重建，不增加旧数据迁移或兼容入口。
- `.local-samples` 两组真实来源均有可追溯测试覆盖，原文件未被修改；来源不完整、模型失败或检查未通过必须单列，不得用跳过或占位答案报全通过。
- 真实数据集成、冒烟和浏览器闭环有本次运行证据；证明实际 production Worker、PostgreSQL 检查点和生成中的真实增量均经过验证，不能用 SQLite/fake 测试或一次 Provider 调用替代。
- 删除确认门禁保持；成功后直接核查该题所有在线材料、过程、历次上下文和受控缓存已清除。清理中断后能够重试完成，不因页面跳转或 404 就判为删除验收成功，不影响其他题或源样本。

## 实施验证与审阅

- 业务决策已收敛：原先关于分档、跨题记忆、旧测试数据和日常删除的开放问题均已进入对应业务场景；本轮不再重复提问。
- 最新 SDK 与网关的真实流式/工具/结构化输出、持久化恢复、跨库清理和工程安全预算须在实施阶段验证；这些技术门未通过时不能宣称交付。允许长等待，不据此默许无限费用或重试。
- 本次范围不新增自动过期与自动备份产品。题目存在期间完整记录保留，显式删除按场景 12 清理；一次性回滚备份和原始源文件不是在线题目历史入口，不能通过回滚重新暴露已删除内容。
- 本文完成收敛整理后，与 design、runtime-design、implement 一起由 `review.md` 汇总供用户审阅。只有用户后续明确批准最终摘要才进入实施；本任务仍为 planning。
- 父任务不直接启动业务实现；获批后只启动满足前置条件的子任务，每个子任务使用自己的分支/worktree 并完成 main 复验。父任务在所有子任务完成后进行总验收。
