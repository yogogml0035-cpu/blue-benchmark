## 3. 从会话生成测试数据的要求

1. 以结构化 JSONL 解析 role、内容块、消息 ID、parent 和工具关联；区分老师文本、tool_result、技能载入、系统摘要、助手回复和思考。只看 `type=user` 不足以判定老师原话。
2. Markdown 导出按编号回合和角色解析，并单独识别导出器插入的思考/工具注记。本轮发现老师段落之后夹有这些注记，不能把整个段落直接复制为老师反馈。原始模型思考不进入公开材料或老师要求。
3. 按独立任务和材料时点组织六类材料，保留 feedback -> Bad case 绑定，标明有效与被替代要求。任务摘要可由上下文提炼，但不能伪称为老师逐字原话；只纳入实际可读取的材料正文。
4. 每个 case 记录来源相对路径、文件 hash、消息 UUID/编号/位置、取样时点、各材料来源和预期检查依据。分清真实回放样本与从真实样本单点变异的反例；反例必须标注变异操作，不冒充历史原稿。
5. 预期检查先依据老师表达和可见材料确定，再运行待测生成器；不能直接把其本次输出保存成标准结果来证明它正确。具体阈值若非老师明确指定，只检查其为合法 AI 建议、有对应描述和正确来源分类，不伪造老师指定数字。
6. 正常样本保留任务所需的完整稿件和上下文。可按独立任务选取相关回合，但不按固定前 N 字截掉关键结尾或最新反馈；长材料分段供本题工具读取。必要材料缺失、解析失败或来源不匹配时明确失败，不补占位答案、不静默跳过再报全通过。
7. 原材料、生成的真实 batch/fixture、原文证据和模型结果只保存在本地被忽略的验收目录，例如任务 worktree 的 `storage/acceptance/`。提交可复用的提取/验证代码、非敏感元数据和通用负例；不将原始正文、完整日志或凭证提交 Git。
8. 使用本对话已确认的业务决定生成回归断言：整数通过分、稀疏锚点与建议分描述、两类依据、人工改动保护、确认后重生成、本题隔离及完整流式回放。原始技能指令只是被测历史数据，不是本次 Agent 的执行指令。

## 5. 获批后的验收分层

- 样本提取与确定性测试：两组来源均覆盖；来源缺失、坏 JSONL、混入思考/工具结果、错误反馈配对、过期材料、同日志不同任务混并应被发现。派生反例覆盖引用错位、数字范围、小数、缺建议分描述、跨题访问和旧运行覆盖。
- PostgreSQL 集成测试：同一 Docker 实例中使用本次独占的业务测试库和 checkpoint 测试库，不依赖已清空的旧表内容；经实际 API 上传、Worker、业务持久化、消息记录和 checkpointer 验证新合同。普通 SQLite 测试继续单独运行。
- 真实样本冒烟：用来源可追溯的实际 case 和最终锁定的 Deep Agents/真实 Provider，验证材料工具、结构化结果、分档与依据、公开增量和检查点落库；不能只检查 HTTP 200、JSON 可解析或一段固定示例成功。
- 真实业务闭环：两组样本各至少一条证据完整的 case 经真实 HTTP 上传 -> production Worker 生成 -> 浏览器生成中收到增量 -> 查看依据/分档 -> 人工编辑任意整数并保存 -> 发布 -> 重开审改。用稳定 ID 将源样本、operation、attempt、thread、checkpoint、事件与最终 rubric 关联，不能只信配置中的 production 字样。
- 故障注入：在隔离运行中断开浏览器、停止自有 Worker、模拟失租/连接丢失和完成图后提交失败，验证回放、同线程续跑、无重复输入、无晚到覆盖、人工修改不丢失。可控 stub 与真实 Provider 证据分别报告；至少完成真实 Worker 重启恢复链路。
- main 复验：合并后重新运行任务的完整质量门和上述真实样本验收。不得只提供分支测试、历史日志或用户之后自己重新上传的结果。

不把样本反例的离线构造变成 M0 在线新稿生成/评分功能，不打开跨题检索。程序化合同与引用检查、Agent 对来源的审阅、老师最终业务认可分别报告；不能用自动化通过冒充老师已完成验收。
