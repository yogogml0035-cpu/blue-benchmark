# Agent 运行基础：消息、检查点、后端与恢复

状态：planning / 未获实施批准。用户要求已从“生成中有反馈”扩展为“保留完整过程和上下文，并准备 M1 的恢复和对话基础”。本文件替代此前“不新增 checkpointer、只保留简短过程”的提案；不改变 M0 只生成/审改评分维度的业务边界。

父子任务分工：C2 实现/验证受限 Agent、事件接口、Saver/StateBackend、锁/连接和无模型清理等底层原语；C3 将其接入业务 thread、消息表、Worker/SSE、前端和完整删除；C4 扩展故障验收。当前项目旧库切换只由 C5 执行，父任务不直接启动实现，详见 task-map.md。

## 1. 六个对象分别负责什么

| 对象 | 责任与存放 | 不承担什么 |
| --- | --- | --- |
| 题目与 rubric | 业务 Service / skill_eval；保存材料、最终维度、老师修改及发布事实 | 不以图状态或模型自述直接替代业务结果。 |
| OperationJob | 现有队列、lease、attempt、调度与幂等 | 不把心跳当进度，不把未来等待用户当失败重试。 |
| Agent thread | 服务分配稳定 ID，绑定目标、材料 revision、Agent/Prompt/schema 身份及运行命令 | thread_id 不是权限凭证，也不是一条数据库连接或一个 Worker。 |
| 完整公开消息/事件 | skill_eval 中的持久日志，按 thread、operation、turn、attempt、sequence 关联 | 不只留摘要，不用 checkpoint history 冒充完整 UI 对话。 |
| Checkpointer / StateBackend | skill_eval_checkpoint 保存图状态、messages、工作文件/摘要、待执行节点和中断；StateBackend 提供线程内虚拟文件 | 不保证从半次模型请求的最后一个字继续，不自动跨题共享记忆。 |
| Store / StoreBackend | 本次不接入跨题 Store；未来跨线程共享另行立项并明确范围 | 不把同题持久化误当成必须具备跨题学习，也不默认开放全部历史聊天。 |

业务状态、图执行状态和展示状态有关联，但只能由各自事实拥有者更新。UI 读取统一投影，不自己依据某条“完成了”的模型文字宣布成功。

## 2. 本轮最小可用基础与 M1 边界

本轮实施获批后应实际完成：PostgreSQL 检查点、稳定 thread 绑定、完整公开消息持久化、线程内上下文/工作文件恢复、进程重启后的续跑、消息流回放和独占执行保护。不能只添加字段或配置就称基础已完成。

M1 预先定义消息/中断/恢复协议及测试情形；本轮不把聊天框、主动询问工具、新稿生成、实际评分或 M1 占位路由上线到 M0。恢复执行的基础现在做，新的业务交互后续按阶段启用。

本题运行中的连续性必须实现。2026-09-06 用户明确确认不做自动相似题参考；本次只使用本题材料与本题上下文，不接跨题 Store。该范围已收敛，但不构成实施批准。

## 3. 复用当前 Docker PostgreSQL

- 使用当前运行中的 PostgreSQL 17 实例，保留业务库 skill_eval 与已有专用库 skill_eval_checkpoint；连接目标来自应用配置，不复制明文 DSN 到任务、日志或前端。
- 当前代码尚未消费 CHECKPOINT_DATABASE_URL / LANGGRAPH_AES_KEY。本任务按新运行语义接入并补设置、启动检查、文档；不是恢复旧 AI Profile/共创链、旧线程 DTO 或历史转换路径。
- 当前 Worker 同步执行，优先设计同步 PostgresSaver 配合同步 Event Streaming；SSE 可以异步读取消息存储，无需为此把整个 Worker 改成异步。异步方案未来替换时独立验收，不同时保留两套未验证路径。
- Checkpointer 连接生命周期必须覆盖整次图调用，不能在工厂的 with 块退出后继续使用已经关闭的 saver。连接建立、驱动参数、池及 serializer 以所锁发布版本验证。
- setup/schema 准备作为获批后的显式部署步骤，不在打开页面时运行。后续用户已授权本次重构清理当前全部项目测试数据，包括专用库的旧 checkpoint；之前 4,415 行是只读核查时的历史计数。按 design.md 第 7.1 节先核对目标并备份，再清理重建，不转换或重放旧线程，本轮仍未执行。
- 新线程不读取旧产品线程；用服务维护的 runtime/schema 指纹判断能否恢复，图合同不兼容时明确拒绝并提示重新开始，不增加旧格式转换器。checkpoint_ns 保持框架图/子图语义，不拿它替代租户范围或随意塞 attempt 名称。
- 检查点序列化可沿用已配置密钥来源并启用 EncryptedSerializer，实施前验证实际格式和重启解密；不自动换密钥。checkpoint 加密不代表消息日志和 Store 也被自动加密，三者访问和敏感字段策略分别验证。

## 4. Thread、命令与 attempt 的关系

- 一个逻辑 Agent 会话拥有稳定 thread_id；一个业务生成命令绑定一个 operation，技术重试不新建另一段无关对话。
- 新上传题目/确认后整套重生成创建新的逻辑 thread，并绑定新的材料 revision。原材料被替换后旧 thread 不可继续写当前题目；过程回看不等于恢复旧评分标准。
- 浏览器重连只恢复消息读取游标。Worker 恢复读取同一 thread 的 checkpoint。用户主动重生成是新 thread。这三个操作不得混同。
- 初次输入带服务分配的 command/turn/message ID；如果 checkpoint 已记录该输入，重试用恢复调用，不再次追加全量历史或相同初始消息。图中 messages 使用框架 reducer 的正常协议。
- 服务保存 thread 与目标、revision、运行指纹的映射；不得接受前端任意 thread_id 访问检查点。已有管理端可见性由现行登录/场景规则决定，不擅自新增“只有创建人可看”的私有题库语义。
- 未来 M1 的正常用户回合与技术 retry 分开计数，不能让三次正常回复耗尽当前 max_attempts。共享队列调度一次可运行的回合；等待用户期间不占 Worker、数据库事务或模型请求。

## 5. 恢复执行，而不是重新生成全部内容

```text
服务接受命令、记录 thread/输入 ID、创建现有队列 job
  → Worker 取得 job 和该 thread 的独占执行权
  → 验证材料 revision / runtime 指纹 / 当前 checkpoint
  → 无已应用输入：提交本次初始输入
  → 有未完成 checkpoint：从保存的执行点续跑
  → 图已完成但业务未提交：校验保存的完整结果，重试业务提交
  → 业务 CAS 原子保存并记录终态
  → UI 从权威状态切换到审改
```

- 优先验证 durability="sync"，使下一步开始前当前步骤检查点已完成写入；选取一致性而不是仅在退出时才保存。该参数须在最终流式调用链实际生效，不能只写在文档。
- 恢复不是保存远端模型的内部计算状态：崩溃时未完成的模型请求可能重新发起。此前已公开的片段保留并标为中断 attempt，新尝试不能悄悄拼成同一段看似连续的内容。
- checkpoint 与业务库不共享原子事务。覆盖 checkpoint 已完成但业务未保存、业务已保存但 SSE 完成事件未到达等窗口；不能用再跑一次模型来处理所有失败。
- 材料保持本题输入边界。运行恢复时验证当前材料 revision/内容指纹仍匹配；材料已换则旧运行过期，不借恢复重新引入 WorkingSet 或用户可见历史版本。

### 同一线程单写者

- 现有 job fencing 只保护业务提交，不自动保护 checkpoint。为稳定 thread 建立数据库级单写者控制；锁失败时不得开始模型调用或继续写同一图状态。
- 候选实现：在检查点库上持有 thread 级 PostgreSQL session advisory lock，锁与 PostgresSaver 使用同一专属、固定的连接，执行期不自动换连接。连接断开后旧执行不能换一条未持锁连接继续写；新执行在取得锁后恢复。该设计需要并发故障注入验证。
- 使用 autocommit/session lock，不跨整个模型调用保持业务数据库事务。等待用户的图调用退出后释放执行连接和锁；重新获得合法命令后再取得。
- Worker 失租必须向运行上下文发停止信号，不仅停止续租线程；旧进程的公开事件和最终提交继续受 attempt/revision fencing 约束。正在阻塞的模型请求即便迟到返回，也不得继续保存。
- 若连接池被采用，checkout 的物理连接在一次执行内保持固定，释放前确保解锁；不能把带 session lock 的连接归还给其他任务，也不能只用进程内锁冒充跨 Worker 保护。

## 6. 完整消息与可控模型上下文

### 公开记录

- 公开给老师的流式内容、工具/阶段事件、重试、失败和完成原文完整保存；以后用户回复和中断问题进入同一逻辑会话。不能只保留最终一句摘要。
- 不必逐 token 一行写库：可短间隔合并相邻 delta，但不丢字符、不改变顺序或消息关联。先持久化公开片段再向 SSE 发送，避免已被用户看见的内容因进程退出而无法回放。
- 统一事件模型包含稳定 message/turn/attempt/sequence 与事件来源；重连幂等回放，重复事件不重复显示。UI 可以分页/虚拟化，不因此截断底层原文。
- 原始私有 reasoning、系统 Prompt、密钥、未授权工具数据不是公开记录。框架/协议必需的内部消息字段按受控 checkpoint 保存，不能直接把 get_state/get_state_history 返回给浏览器。
- 完整保留的是已授权公开的内容；超过单条大小应分段，不以悄悄截断替代完整留存。题目存在期间不新增自动到期清理；用户已确认删除题目时一并删除该题的完整过程和上下文。现有删除确认门禁保留，具体可恢复清理合同见第 11 节，本轮不执行清理。

### 模型输入

- 完整公开记录不等于每次调用把全部历史重新塞进模型。优先复用框架上下文管理/摘要，把本轮目标、明确要求、AI 推定、材料定位、待办和必要近期消息保留在 checkpoint 状态。
- 压缩模型上下文不改写公开历史；摘要里的老师明确要求和 AI 推定仍分开。材料按本题读取，不因为出现 Store 就自动检索其他题目。
- 保留 AI tool_call 与对应 ToolMessage 的关联，不能只截一边；未完成工具调用、待恢复中断及协议必需字段不被通用裁剪丢掉。
- 能力状态放 AgentState 并经 checkpoint 持久化；连接、客户端、凭证、progress sink 和授权上下文在 Runtime/服务依赖中，不放进可序列化状态。OmitFromSchema 隐藏输入/输出不意味着该字段不会进入 checkpoint，不能当秘密保护机制。

## 7. Deep Agents backend 与长期记忆

- `/materials/`：仅本题材料、只读、受服务定位与 revision 约束。研发使用的本地 LangChain Skills 不自动挂载成业务 Agent 可读文件。
- `/workspace/`：StateBackend 线程内工作文件，配合 PostgresSaver 跨进程恢复；不落宿主机任意目录，不开放 shell。
- 框架的 `/large_tool_results/`、`/conversation_history/` 等内部工作路径也应留在本线程 StateBackend；按实际 harness 权限验证授权读取，不能只开放 workspace 后把内置工具结果存放/摘要恢复堵死，也不能让默认路由落入宿主机目录。
- 不挂载跨题 `/memories/`，不接 PostgresStore/StoreBackend，也不为未来预建全局偏好表、跨题向量索引或后台记忆提炼任务。同题工作文件持久化保留；旧数据库清理依独立的一次性授权，不从“禁用 Store”推导额外删除权限。
- 当前 API 尚无完整的私有老师记忆归属模型；不能直接照抄 server_info.user.identity 示例。本次不新增长期跨题记忆读写，也不为已排除的能力先建设新的归属模型。
- `memory=` 是加载记忆文件的配置，不会自动解决记忆提炼、事实真假、适用范围或同意问题；不将所有聊天自动提升为权威规则。

### 7.1 本题独立与相似题参考的判断

- 第一性原理：本轮制定的是本题的通过标准；具体要求的适用权来自本题材料和老师确认，不来自另一道题被认可、发布时间较近或文本相似。一般评测方法可以辅助构造规则，但不能隐式继承其他题的业务要求和数字门槛。
- “题量大所以不能参考”不是充分理由。检索可以只选择少量相关候选，而不把全部题目送进模型；然而候选相关性不能证明标准适用性。即便只取一题，也可能把危机回应的克制要求迁移到同品牌新品宣传。
- 仅在输入里标注“只供参考”不能保证没有影响；只要旧题进入模型上下文，就可能改变候选维度、锚点或分数建议。若目标是其他题不自动影响本题，当前最清楚的边界是不自动检索或注入旧题内容，而不是检索后假定模型一定忽略不适用要求。
- 本题 `memory_materials` 是收题时已提供的材料，当前 `build_generation_input(row)` 只读取当前行；它既不是平台的跨题记忆库，也不是运行时 checkpoint。继续保留其来源及“明确要求/AI 推定”区分。
- 教师明确把旧内容整理进本题已有材料时，可按本题快照处理；不增加隐式外键追随或自动随旧题更新。此能力不要求新增跨题搜索 UI，也不授予生成 Agent 全题库读取权限。
- 本题隔离不等于模型没有通用知识、不等于每次生成完全确定，也不改变材料 revision/过期运行约束。可验证的边界是：B 题变化不会触发 A 题更新或改变 A 题实际获取的材料、记忆与恢复状态。
- 若未来提出主动复用，先验证确有材料准备重复等业务损耗，再考虑“适用范围过滤、相似候选、来源展示、明确纳入本题材料”。这是备选方向，不是已批准的接口、Store 或 RAG 实施清单。

### 7.2 已确认的隔离验收

- 构造同场景的 A/B 题，在 B 写入与 A 明显不同的要求；新增、编辑或删除 B 时，不排入 A 的生成作业、不改写 A 的标准。
- 对同一 A 输入比较提供给 stub 模型的初始材料、工具可读内容和 checkpoint 归属；它们不包含 B 的内容或新建的跨题偏好。不能仅凭一次真实模型输出看似相同宣称无污染。
- 检索范围固定在本题服务定位符内，重连、恢复、上下文摘要和技术重试也不能扩大范围；复用 middleware 实例不应共享运行中的消息、老师身份或偏好缓存。
- 本节随用户“明确不做”自动相似题参考的答复成为已确认验收范围；本题隔离需在获批实施后验证，范围确认不等于实现或验收已完成。

## 8. 中间件采用什么 hook 风格

推荐以少量 class-based AgentMiddleware 组织多 hook 的运行观测/上下文策略；纯粹一个无状态规则才用装饰器。先复用 Deep Agents 已有上下文/文件/限制能力，不再造一个万能中间件框架。

| hook / 位置 | 合适职责 | 禁止或注意 |
| --- | --- | --- |
| 服务/Worker 外层 | 授权、thread 锁、lease、幂等、公开消息持久化、最终业务提交 | 这些不能只靠模型 middleware 或 Prompt 保障。 |
| before_agent | 校验这次 invocation 的运行上下文，标记开始/续跑 | 每次恢复也可能进入，不重置历史、消息或运行预算。 |
| before_model | 需要持久化的轻量状态更新；配合内置摘要管理上下文 | 用明确 state update；不重复实现第二套上下文压缩器。 |
| wrap_model_call | 真实调用开始/结束、耗时/用量、允许的请求上下文调整 | 不吞中断或取消，不嵌套无界重试；不假定直接修改 request.state 会保存。 |
| wrap_tool_call | 工具生命周期、允许的本题范围校验、公开进度及失败分类 | 不透传原始敏感结果；外部副作用须幂等；不把 interrupt 当普通工具错误。 |
| after_model | 必要的状态归整、候选检查信息 | 这里只是一次模型返回，不是 rubric 已完整保存。 |
| after_agent | 本次图调用收尾观测 | 不在此把题目发布或盲目写成成功；中断、图完成和业务完成不同。 |
| 原生 Event Streaming + sink | 消息 delta、工具关联和自定义业务事件的持续传递 | before/after hook 不能代替流式 token 通道。 |

- 同步 Worker 使用同步 hook；异步执行时必须完整实现对应 async hook，不混入阻塞数据库调用。当前不为了未来而同时维护两条未验收实现。
- before 顺序、after 逆序、wrap 嵌套；实际合成顺序通过记录型测试确认，包括 Deep Agents 内置 middleware。权限/范围在 backend/服务也强制校验，不依赖“我以为这个 hook 最外层”。
- middleware 实例只放不可变配置；运行中计数、消息和用户身份不放 self 共享字段，避免多线程串数据。状态键明确所有权，避免多个 middleware 覆盖或在并行工具中竞争同一个标量。
- 临时 request override 与持久 state update 分开；wrap_model_call 确需更新 state 时采用当前官方 ExtendedModelResponse + Command，测试 retry 之后更新是否符合预期，不能直接返回普通字典替代 ModelResponse。

## 9. M1 提前固定的中断/聊天合同

- 自定义询问用 interrupt(payload)，同一 thread 的有效回复使用 Command(resume=...)；普通新消息和恢复命令不同。工具审批 middleware 的 decisions 结构按其合同使用，不能当所有问答通用格式。
- 图暂停后 checkpoint 持久化待处理 interrupt，服务投影“等待用户”；停止模型调用并释放 Worker 执行资源，而不是一直 loading、一直占 lease 或当作失败重试。
- 回复请求携带独立 command/message ID 与目标 interrupt，校验当前状态、访问权限和是否已消费；重复请求幂等，过期回复拒绝，不重复执行工具。
- M1 一次可调度回合的完成不等于业务任务全部完成。正常等待用户不消耗技术失败次数；回复到达后安排新的可运行回合，保留原 thread。
- interrupt 恢复会从节点开头执行，之前的副作用必须拆成可重放安全步骤或有幂等键；不可假设 exactly-once。观察中间件让中断信号透传。
- 本轮可用隔离 runtime 测试证明“暂停→重启→收到回复→恢复”协议可行，但 M0 生产 profile 不先增加询问工具和聊天入口。是否在 M0 增加聊天须另获明确业务批准。

## 10. 验收和切换门禁

- 真实测试来源改为用户最新指定的 `.local-samples`，按 research/real-sample-validation.md 生成有来源的输入与独立断言；两组数据均覆盖真实业务闭环，不能用历史其他目录、固定样例或占位答案替代。

- 验证原文回放、分页/重连、模型上下文压缩后原文仍在、同线程工作文件恢复、不同线程/材料 revision 隔离。
- 在隔离库和可控 Provider/stub 中中止 Worker：证明从 checkpoint 续跑，不重复初始输入；未完成模型调用重试有明确标记；已完成图结果只重做未完成业务提交。
- 同线程双执行、失租、连接丢失、晚到事件、锁归还、事务/连接泄露必须有测试；只测最终 CAS 不够。
- 覆盖模型 tool-call 消息协议、middleware 顺序与状态更新、中断不被吞、重复回复、旧 interrupt 和暂停时资源释放。
- 验证内置大工具结果存放/读取、历史压缩工作文件的正确路由与恢复，不仅测试自定义 workspace 文件。
- 删除验收必须覆盖同题全部历史 thread、公开消息、checkpoint/工作文件和受控缓存均清除，跨库故障后可恢复清理；不能只看题目 GET 变成 404 就宣布删除通过。

## 11. 删除题目及其全部在线运行数据

业务决定已由 D23 确认；以下是待最终审阅的实现方案。目标是完整清理，而不是永久保留一套只对 UI 隐藏的软删除数据。

### 11.1 范围和现有门禁

- 保留现行鉴权、content_revision 检查；生成中不允许删除，已发布先重新打开审改，曾发布题目必须输入当前完整标题并按现有 NFC/strip 规则匹配。确认取消或门禁拒绝不得先清消息或 checkpoint。
- 删除对象包含本题材料与维度、全部公开消息/增量/快照、所有生成 jobs/attempts、所有历史重生成 thread 的完整 checkpoint、pending writes、状态 blobs、StateBackend 工作文件和摘要，以及系统管理的本题缓存/派生产物。
- 原始 `.local-samples`、用户自己保存的源文件、其他题目、共享场景与凭证不在单题删除范围内。当前批次回执只含 hash、case/question ID 与状态，不含正文；保留其最小幂等作用，不删整个批次或让旧命令重放重新创建已删除题目。
- 允许保留无材料/标题/引用/消息原文的最小清理回执，用于幂等、故障恢复和删除完成核验。回执不是旧题可读取或可恢复的兼容层。

### 11.2 复用 OperationJob 的持久清理

两个库不共享普通事务，不能在业务表 DELETE 后 fire-and-forget 清 checkpoint。方案采用一个持久清理命令，复用现有队列/lease/attempt，而不增加第二套队列或数据库两阶段提交框架。

1. API 在同一业务事务中验证原门禁、以 CAS/行锁冻结该题的写入、登记清理意图与本题全部 thread 定位符，并创建专用删除 OperationJob。控制记录只保存 ID、revision、阶段和状态，不复制材料正文或确认标题。
2. 删除受理后，该题及所有旧运行停止接受材料修改、审改、发布、重生成与 resume；终止相关 SSE 订阅/回放的新增读取。UI 保留可见的删除处理中/失败重试入口，不把受理当成删除完成。所有写路径必须检查删除冻结，不能只禁用按钮。
3. 清理 Worker 在取得执行权和同线程独占控制后，通过所锁 SDK 的公开删除 API 清除全部 thread。验证 delete_thread 覆盖各 checkpoint namespace、pending writes、blobs 与 StateBackend 内容；缺连接或未拿到锁时重试，不静默跳过。只清这道题，不清全库迁移表或密钥。
4. checkpoint 与其他受控运行副本清理成功后，在同一业务事务中删除题目、公开消息/快照、线程映射及生成 jobs/attempts，并将删除作业提交为成功。删除作业不能被“删除生成历史”的查询一并删掉，避免丢失最后的完成回执和重试定位。
5. 客户端看到删除完成后才确认成功并离开当前题目，清除本题草稿/事件缓存。完成后材料、公开历史、直接 thread 查询和恢复入口都不可读取；同题以后的重新上传使用新的 question/thread ID，不复活旧运行。

- 拟沿用原 DELETE 路径和确认字段，补稳定 command_id，改为返回已受理的删除 operation；新增仅含状态/错误/ID 的进度查询。OpenAPI、前端 API 和 handleDelete 同任务切换，不保留“204 即题目行删除成功”的旧早退路径。
- 拟使用有实际 M0 用途的删除处理中投影及专用 job kind/target_type。只保留一个处理中的题目生命周期状态，失败原因由删除作业投影；不另建通用 workflow 引擎。
- 当前 Worker 的通用异常与终态投影偏向 rubric_generation；接入清理作业时按 kind/target 分派错误归属，不能把清理失败标成评分生成失败。清理控制记录使用独立 target_type，避免现有生成历史删除查询删掉自身。
- 清理作业只依赖业务库与 checkpoint 后端，不调用模型。Worker 当前在 production_worker 入口统一构造模型；实施时按任务职责调整初始化，不能因生成 Provider 不可用或模型构造失败而永久阻塞已经受理的删除，也不能让未配置的生成任务被误当作正常生成消费。
- 不跨整个清理任务持有业务长事务。冻结意图先持久化，外部清理幂等，最后业务删除/作业成功原子提交；故障期间不可重新开放该题编辑或恢复执行。
- 崩溃或重试只重做未完成/可幂等的清理步骤；最终删除失败必须可见并可重试，不让原文在后台永久遗留，也不让清理回执出现 succeeded 而原文仍在。

### 11.3 防止迟到写入和残留

- 删除冻结与既有 revision/attempt fencing 联合阻止迟到事件、图写入和业务提交。每个 thread 必须纳入单写者控制；原 Worker 失去连接/执行权后不得重连绕过锁写回已经删除的 checkpoint。
- 清理枚举的是该题全部历史 thread，不只是 active_operation_id。历史 thread 映射在全部外部清理完成前不能先删除；同线程内的文件/摘要与完整 checkpoint 一起验证。
- 拒绝新的正文读取与 SSE 回放后，前端停止订阅并清除受管理的本题状态。浏览器此前已接收的网络字节、用户另存文件或 Provider 自身日志不由平台远程抹除；不声称这是全介质安全擦除。
- 不新增保留材料原文的外部托管追踪、自动备份或历史恢复产品。已有一次性旧测试库回滚备份保持非运行时可读；如恢复含已删除题目的备份，必须在重新开放服务前应用删除清单，否则拒绝恢复上线，不能把原文重新暴露。

### 11.4 删除测试门禁

- 原鉴权/revision/生成中/已发布/曾发布标题校验及取消确认均保持；每条拒绝路径证明两库和消息数据未被清理。
- 从真实 case 产生多次重生成与多段公开历史后删除，查询本题所有 messages、events、snapshots、thread/checkpoint/writes/blobs 和工作文件均无残留；兄弟题与批次幂等回执不受影响。
- 在冻结后、部分 thread 清理后、全部 checkpoint 清理后和最终业务提交前中止自有 Worker，证明重启后清理完成，无过早成功、无迟到写回或恢复旧题。
- 覆盖 checkpoint 库不可用、重复删除命令、网络断开重连、清理失败后重试，以及清理作业自身不会被生成历史级联删除。
- 覆盖模型 Provider 不可用及模型初始化失败时仍可执行已受理清理；证明删除路径没有模型请求，清理错误不被投影成评分生成错误。
- 真实浏览器确认提示原门禁不变；处理中/失败不伪装为完成，删除成功后无法从详情、历史回放或恢复接口读回原文。必须核查存储，而不只断言页面跳转或 404。
- 获批后使用最新 SDK、当前 Docker PostgreSQL 的隔离验收目标，最终经过实际 Worker/Provider/API/代理/浏览器验收。已有检查点表、文档、fake、HTTP 200 都不是本功能已接入的证据。
- 本任务一次性替换无连续性的生成路径和只保留摘要的方案；不恢复旧共创/版本包/旧线程读转换。代码与数据回滚依靠版本、备份和部署回退，当前旧检查点数据保持原样。
