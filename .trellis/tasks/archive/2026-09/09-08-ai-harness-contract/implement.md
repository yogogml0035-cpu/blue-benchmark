# 父任务编排与最终验收

状态：planning。父任务不直接实施产品、不运行父任务的 `task.py start`。总技术合同见 [design](design.md)，任务边界见 [task-map](task-map.md)。

## 批准后的执行顺序

1. 用户审阅并明确批准最新父子计划；本次“按需要拆分”只授权规划变更，不授权真实模型调用或产品实施。
2. 检查主工作区/所有 worktree/main/远端状态，先将最终批准的计划材料按规划分支的质量与合并门交付到 main，保持父任务 planning。后续子任务从已验证 main 创建各自工作区，不携带父 worktree 的未提交材料。
3. 创建并启动 [C1](../09-08-ai-harness-capability/implement.md)，完成能力探针、真实工具/结构化/流式/恢复验证及 C1 分支/main 复验，交付脱敏报告并归档 C1。
4. 人工核查 C1 完成/归档、全部 C1-AC 通过、PASS 报告和交付提交都在最新已验证 main，并核对配置/SDK 前提仍有效；失败或证据过期时不得开始 C2。
5. 创建并启动 [C2](../09-08-ai-harness-cutover/implement.md)，一次性完成统一合同、协议、恢复身份、错误与诊断、旧路径删除和全部真实系统验收，不留下拆开合并的半成品。
6. C2 完成完整分支门后串行合并，在 main 重跑同一任务的完整质量门及目标真实验收，再归档/清理本子任务。
7. 父任务核对总需求和跨子任务证据，全部满足后才能完成与归档父任务、清理父规划 worktree；不会因为 C1 探针通过就宣称原问题已修好。

当用户的实施批准已覆盖两个子任务时，依赖门满足后可以按授权继续 C2，无需重复索取同一批准；重大兼容性/产品边界变化仍须回到计划审阅。

## 父任务验收清单

- [ ] C1 的能力证据来自当前目标模型/端点/medium、真实工具、完整 schema 和持久化恢复；没有普通对话、Mock 或失败报告冒充 PASS。
- [ ] C2 使用同一生产装配，C1 探针已删除局部候选构造，没有两套生效合同。
- [ ] 父 PRD AC1–AC8 全部通过，T/P/L 矩阵每项有可定位结果和精确 Git/SDK/配置身份。
- [ ] Chat-only `_generate`、旧分散指纹、通用可重试包装、raw traceback、失效文档/测试及临时验证构造均已按父 design 删除。
- [ ] 真实 Worker 与 PostgreSQL/浏览器恢复、原子提交、公开流安全和模型不可用清理都有最终 main 证据。
- [ ] 所有提交包含于 main，工作区清理只针对已闭环的本任务；不顺带 push 当前 main 的历史未推送提交。
- [ ] 主环境切换、原题重试、共享数据操作或现有服务重启没有被自动验收脚本擅自执行。
