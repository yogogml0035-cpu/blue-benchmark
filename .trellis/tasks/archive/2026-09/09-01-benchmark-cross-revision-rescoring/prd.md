# 按新题目修订重评旧待评结果

## Goal

让同一份不可变待评结果可以按后续发布的题目修订追加人工评分，同时保证正文、旧评分、评分依据和历史结论均可还原。

## Confirmed Facts

- 当前 `EvaluationSubmission` 保存一份不可变待评结果正文及其原始 `question_revision_id`。
- 当前 `HumanScore` 虽然也保存 `question_revision_id`，但数据库复合外键和 Service 都强制它等于待评结果原修订。
- 当前评分历史前端使用待评结果原修订解释所有评分项，因此跨修订后会显示错误的名称、满分和锚点。
- 人工评分主链已经合并到 `main` 并通过相关测试、完整 `make test` 和生产构建；本任务只补跨修订能力，不重写待评结果存储与评分算法。

## Requirements

### R1. 不可变待评结果

- `EvaluationSubmission` 继续代表一份不可变待评结果正文；跨修订重评不得复制、替换或重新上传正文。
- 待评结果保留最初提交时绑定的题目修订，首次评分只能使用该原修订。

### R2. 每条评分自带题目修订

- 后续重评只能选择与待评结果原用例共享同一 `question_draft_id` 的已发布修订；`question_draft_id` 是同一逻辑用例的稳定身份。
- 每条 `HumanScore` 必须保存本次实际使用的题目修订；逐项校验、总分、关键项和通过结论全部按该修订计算。
- 新修订的评分项、阈值和关键项不能与旧修订混用。

### R3. 线性历史

- 同一待评结果只有一条线性 parent-linked 评分历史；新增重评必须基于当前最新评分。
- 旧评分、旧题目修订、逐项分数、理由和结论不得覆盖。
- 历史读取必须按每条评分自己的题目修订还原标准答案、评分项、满分、锚点和通过线。

### R4. 前端重评

- 默认“重新评分”继续使用上一条评分的题目修订。
- 老师可以显式选择另一条允许的已发布修订；选择后整个评分表按目标修订重建，不能保留旧 criterion 输入。
- UI 不显示内部 UUID、存储键或运行元数据。

### R5. 权限与兼容

- 未发布、未知、跨 Workspace 或属于另一道逻辑题的修订必须在写入前拒绝。
- 旧客户端未传目标修订时保持当前同修订重评行为。
- 现有待评结果、评分和 API 读取保持可用；迁移不复制正文或改写历史分数。

## Out of Scope

- AI 自动评分、批量评分、多待评结果比较和 Skill 运行信息。
- 复制待评结果形成新的 submission lineage。
- 使用同一待评结果跨不同逻辑用例评分；另一个用例必须创建新的 Submission。
- 修改题目发布、停用、删除或自动评测集版本策略。

## Acceptance Criteria

- [ ] AC1：首次评分仍只能使用待评结果原修订；同修订重评继续追加 parent-linked 记录。
- [ ] AC2：同一 `question_draft_id` 的新修订可以作为后续重评目标，服务端按其 rubric 重新计算，正文和旧评分不变。
- [ ] AC3：未发布、跨 Workspace、未知或属于另一道逻辑题的目标修订被拒绝且不写入评分。
- [ ] AC4：每条历史评分可还原自己的题目修订、评分项快照、逐项依据和结论。
- [ ] AC5：切换修订后前端清空不兼容输入并展示目标修订的完整标准；390px 窄屏可用。
- [ ] AC6：客户端伪造总分、漏项、跨修订 criterion 或陈旧 parent 均 fail-closed；同 command 重放幂等。
- [ ] AC7：迁移前后的旧待评结果与评分均可读；用户界面统一使用“待评结果”；`make openapi`、`make test`、`make build`、`git diff --check` 通过。
