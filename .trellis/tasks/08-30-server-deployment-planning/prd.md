# 服务器部署与发布方案

## Goal

为当前 Skill Eval Platform 形成一套适合初学者理解和维护、可按常规主流方式部署到服务器并供目标用户使用的正式方案。方案必须以当前源码的真实运行边界为基础，区分 Docker、服务器部署和 CI/CD 的职责，并在需求对齐后给出可实施、可验证、可备份和可回滚的项目修改计划。

## Background

- 用户是服务器部署初学者，听说过 Docker，但还不清楚 Docker 的作用、其他部署方式以及 CI/CD 是否等同于部署。
- 用户希望通过逐轮访谈挖掘真实目标、假设、局限和遗漏；每轮只处理一个最高价值问题，直到对需求和目标达到约 95% 的理解置信度。
- 用户已同意创建 Trellis 规划任务。本阶段只写规划材料，不修改业务代码、不运行 `task.py start`、不实际购买或操作服务器。

## Confirmed Repository Facts

- 前端是 Next.js 15 App Router，生产形态需要执行构建后运行 `next start`，并通过同源 `/api/*` Rewrite 访问后端。
- 后端是 FastAPI；生产不能使用 README 中带 `--reload` 的本地开发命令。
- 后台任务由独立的单消费者 Worker 处理；只启动网页和 API 会导致异步任务一直等待。
- 业务数据使用 SQLAlchemy/Alembic 管理的 PostgreSQL。服务启动前需要显式执行迁移和 schema 检查。
- 生产共创流程还需要与业务库职责分离的 PostgreSQL Checkpointer 数据库和 16、24 或 32 字节加密密钥。
- 用户上传、证据和冻结版本包当前保存在服务端本地文件系统，因此部署必须提供持久存储、备份和恢复边界。
- 生产真实 AI adapter 需要单独配置和验证；默认模式仍是确定性的 Fake。
- 当前常驻 Worker 只调用 `default_worker()` 并继续使用模块级 Fake adapters；虽然代码已有 `production_adapters(...)`、Anthropic 模型构造器和加密 PostgreSQL Checkpointer 工厂，但它们尚未接入常驻 Worker 生命周期。因此仅设置模型环境变量不能实现真实 AI 上线。
- 当前仓库没有 Dockerfile、Compose、反向代理或 CI/CD workflow，服务器部署能力尚未实现。
- 写请求有同源保护；公网 HTTPS 部署时需要正确配置 `FRONTEND_URL` 并启用 Secure Session Cookie。
- 已有一台运行中的阿里云 Linux 服务器，区域为华北 2（北京），镜像预装 Docker 26.1.3，配置为 2 vCPU、2 GiB 内存和 40 GiB ESSD，并具有公网地址。规划文档不记录具体公网 IP 或实例 ID。
- 用户将把实例内存升级到 4 GiB；目标部署基线因此为 2 vCPU、4 GiB 内存和 40 GiB ESSD。

## Requirements

- 用初学者可理解的方式解释服务器、进程、Docker、Docker Compose、反向代理、数据库、持久化和 CI/CD 之间的关系。
- 首版通过公网对外开放，预期早期使用人数和并发都较低，但访问者不限定为已知用户。
- 保持现有应用内注册和登录逻辑，允许任何能够访问注册页的人自由注册，不因部署方案重做账号体系。
- 首版被定位为公网临时演示和测试环境，而不是安全的正式生产服务；用户明确选择普通 HTTP，暂不启用 HTTPS 或 Secure Session Cookie。
- HTTP 演示仍必须具备最小端口暴露、密钥隔离、服务器加固和基础备份等不依赖 TLS 的安全底线。
- 首版不使用域名，用户只通过固定公网 IP 访问；域名、DNS 和 ICP 备案延后处理。
- 基于目标用户、暴露范围、预算、数据敏感度、维护能力和可用性要求，对比至少以下路线：服务器原生进程、单机 Docker Compose、托管 PaaS/容器平台。
- 给出明确推荐，不把“大家都用 Docker”当作选择依据；每个新增组件都必须对应当前项目的真实运行需求。
- 最终技术方案必须覆盖前端、API、Worker、业务数据库、Checkpointer、文件存储、域名与 HTTPS、密钥、迁移、健康检查、日志、备份、恢复和回滚。
- 演示环境必须执行真实 AI 共创，不得用 Fake adapter 的确定性结果冒充真实模型验收。
- 实施方案必须补齐生产 Worker 的真实 adapter/Checkpointer 生命周期接线、配置缺失时的启动失败、Provider smoke、真实中断恢复和进程重启恢复验收。
- 即使是临时演示环境，数据恢复目标仍为最多丢失最近 24 小时的数据，发生服务器故障后允许停机数小时完成恢复。
- 业务数据库、Checkpoint 数据和上传文件至少每日自动备份一次；可靠备份必须存放在故障域之外，不能只复制到同一台服务器，并需要有可重复的恢复验证步骤。
- 明确 CI 与 CD 的边界，决定首版采用手动部署、半自动发布还是自动发布，并提供与用户维护能力匹配的故障处理路径。
- 形成项目级 `design.md` 和 `implement.md`，列出需要修改或新增的部署文件、实施顺序、验证命令、风险点及回滚点。
- 所有部署成功结论都必须由真实运行路径验证，不能用镜像构建成功、端口监听或 HTTP 200 冒充完整业务验收。

## Resolved Decisions

- 站点是公网开放产品，任何发现站点的人都可以访问和注册；用户明确接受陌生人注册。
- 预期早期用户量很小，当前不以高并发扩容为首要目标；低预期流量不是访问限制。
- 应用注册登录逻辑保持不变，不增加邀请制、白名单或外围访问认证。
- 可接受最多丢失最近 24 小时的数据，并允许故障后停机数小时恢复；不要求首版高可用或近零数据损失。
- 部署目标优先使用现有阿里云 Linux 服务器，而不是重新选择托管平台；除非后续容量或合规条件证明该实例不适合。
- 用户同意将服务器内存从 2 GiB 升级为 4 GiB；方案按升级后的配置设计。
- 首版明确不配置域名，只使用阿里云实例的固定公网 IP 访问；方案不能把域名或备案当作首次上线前置条件。
- 首版明确使用普通 HTTP，只用于临时演示和测试；用户接受不提供传输加密，并暂不要求浏览器可信的 IP HTTPS 证书。
- 用户选择跳过是否强制一次性测试密码、脱敏资料和页面风险提示的决策；该问题暂不作为部署阻塞项，也不视为风险已经得到缓解。
- 服务器演示必须使用真实 AI；Fake 模式只保留给自动化测试或显式的本地开发，不作为服务器业务验收路径。

## Risk Notes

- 公网自由注册会带来扫描、垃圾注册和资源滥用风险。首版不因此改变注册产品逻辑，但部署设计必须保留限流、监控和后续治理的扩展点。
- 数据库记录与本地文件存在一致性关系，备份和恢复不能只覆盖数据库或只覆盖文件；每日备份满足当前恢复目标，但仍需验证恢复后的业务路径和版本包完整性。
- 2 GiB 内存需要同时容纳容器运行时、Next.js、FastAPI、Worker、PostgreSQL 和反向代理，生产余量偏紧；若保持该配置，应避免在服务器内构建镜像，并需要限制并发、设置资源边界和监控内存压力。
- 4 GiB 适合当前低流量单机部署，但仍不是无限资源；首版应采用一个 PostgreSQL 实例承载职责分离的两个数据库、单个 Worker 和轻量反向代理，避免为了未来扩容预建集群或 Kubernetes。
- 裸 IP 的明文 HTTP 会暴露注册密码、Session Cookie 和上传内容，不满足公网真实用户的安全底线。Let’s Encrypt 已在 2026-01-15 将 IPv4/IPv6 地址证书设为正式可用，但这类证书有效期为 160 小时，部署必须使用支持 `shortlived` ACME profile 的客户端并验证自动续期；不能依赖手工换证。
- 当前选择接受上述 HTTP 风险的前提是环境只用于临时演示和测试。若允许真实密码、真实业务资料或长期公网使用，必须回到规划阶段，将 HTTPS 和 `SESSION_COOKIE_SECURE=true` 恢复为上线门禁。
- 由于测试密码、脱敏资料和页面提示没有得到用户确认，最终方案必须将其列为未缓解风险，不能宣称 HTTP 演示环境适合敏感资料或安全凭证。
- 真实 AI 生产接线当前尚未实现；这是部署前必须修改并通过真实 Provider smoke 的产品代码缺口，不是 Docker 或环境变量可以自动解决的问题。
