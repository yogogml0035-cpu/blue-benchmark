# 技术设计草案：完整 rubric 与受限材料核查

状态：planning / 最终审阅，未获实施批准。遵循 `prd.md` 的已收敛业务语义；本文件和 runtime-design 是待最终批准的技术方案，review.md 提供摘要。稀疏锚点、旧测试数据重置、真实样本测试和同题完整关联删除均已确认，实际效果和工程预算在实施中验证。

后续完整消息与恢复要求已纳入 `runtime-design.md`；该文件具体定义 checkpoint/backend/线程/中间件/M1 恢复协议，替代此前排除连续性的方案。

本文件是父任务共享技术设计，不是父任务直接实施的入口。C2 负责可复用运行原语；C3 负责完整合同、生产接入、页面、删除和旧语义的一次性切换；C4 扩展系统验收；C5 执行本地数据切换。取样基线归 C1，具体依赖和所有权以 task-map.md 为准。

## 1. 不变边界

- M0 仅定义和审改本题规则，不生成新稿，不执行标准答案或新稿评分。
- `pass_score` 始终是 0–10 任意整数；分数锚点不是枚举白名单、区间通过分或档位选择器。
- 老师勾选、编辑、保存、发布的语义不变；普通编辑不自动生成，不覆盖人工修改。
- Service/DB 拥有业务事实，OperationJob/Worker 拥有队列、租约和重试，AI adapter 只提交候选；不恢复旧共创、WorkingSet、版本包、双轨读取。

## 2. 一个完整结果，不是几个字段生成器

沿用“生成器返回完整 RubricGenerationResult”的业务边界，接口增加服务注入的运行上下文与公开消息 sink，支持确定的新建/恢复语义；旧的无连续性调用合同同任务替换，不保留绕开持久化的默认空上下文。以下字段名是提案，锁定合同时再统一命名：

| 部分 | 形状提案 | 不变量 |
| --- | --- | --- |
| 维度 | `criterion: str` | 保留具体评判内容，不是孤立标签；ID 由服务生成，不由模型自封。 |
| 当前通过分 | `pass_score: int` | 初始为 AI 建议值，老师可修改；只接受 0–10 整数，与锚点集合独立。 |
| 分数说明 | `score_anchors: [{score: int, description: str}]` | 明确分数点、唯一、排序、可观察表现；不生成通过分范围。 |
| 维度依据 | `criterion_basis` | 简短说明为何纳入，包含可核查的材料引用与要求/推定分类。 |
| 通过分依据 | `pass_score_basis` | 说明材料体现的最低要求、为何建议这个数；明确其解释的是哪个分数。 |
| 引用 | `source_ref + quote` | 对本次不可变材料快照定位，引用存在性由程序检查，来源标签不交给模型自由伪造。 |

生成合同要求产出完整分档和两类依据；人工新建维度不得被迫伪造“AI 依据”。人工新建的空辅助内容以新合同显式表示，而不是利用旧合同缺字段兼容。本方案保持现有发布门槛，不增加人工补齐 AI 辅助内容的强制步骤，作为最终审阅中的范围边界说明。

锚点密度已确认：初次生成提供少量关键分数的可观察表现，并覆盖 AI 所建议的整数通过分；不要求列满 11 个整数。不从预设锚点中挑通过分，也不根据相邻锚点取整或改数。具体关键分数按本维度的表现差异生成，不将数量或固定分数列表再变成老师的新操作。

“建议分有对应锚点”只约束初始 AI 生成合同，不约束老师的编辑保存。老师仍可填任意整数，普通编辑不自动补档、重写或覆盖已有说明；例如现有描述只有 4/6，老师可改成 5 并保留这些描述。不能给 API 公共编辑 DTO 加上 pass_score 必须属于 score_anchors 的白名单校验。

### 避免人工改分后显示过时解释

`pass_score_basis` 应保存其所解释的分数，例如 `explained_score=4`。老师改成 5 时，保留原说明但明确显示“原说明对应 4 分，当前通过分为 5，请核对”，不能把解释静默改名为“5 分的依据”。老师可以一起修改解释及其对应分数。

这是同一可编辑内容中的解释对象，不是增加一套“AI 阈值 + 人工阈值”的双轨评分逻辑。真正用于最终规则的值只有当前 `pass_score`。

### 依据分类与来源不能混同

- 依据按主张分别标记“老师明确要求”或“AI 推定”。同一维度可以有明确的定性要求，但数字门槛仍是 AI 建议。
- 标准答案展示的做法，不自动等于老师明确要求必须这样做；`reason_summary` 不等于老师反馈原话；记忆材料也不自动具有老师明示授权。
- 明确要求应关联能直接支持它的材料原文；不确定时不得以“老师已经规定”包装。引用存在的硬校验不能替代这种语义判断。
- 老师可改说明及引用选择；原文摘录与定位必须仍能对应材料。人工编辑不自动触发后台重新推理，也不因老师点保存就把所有 AI 推定改标为老师原话。

## 3. 推荐的内部生成流程

```text
现有 OperationJob + Worker
  → 取得本题材料快照与 content_revision
  → 建立本题专属材料目录、来源定位与读取预算
  → 受限 create_deep_agent 按需读材料、核对反馈
  → 联合产出维度 + 分档 + 整数通过分 + 两类依据
  → 确定性结构/引用校验，必要时反馈错误做有限修订
  → 对完整候选再次校验
  → 现有 CAS / job fencing 原子保存
  → 老师在现有页面审改
```

- 材料读取可以多轮；维度、档位描述、通过分和依据不拆成互不共享结果的字段级调用。
- 发现问题后只在同一 job 的受限预算内修订候选，最终完整提交；不逐项写库，不将半份结果呈现为生成成功。
- 校验只针对所生成规则的合同、引用和内部一致性，不增加 M1 新稿测试，不给标准答案实际打分。
- 第一次候选已通过检查时可以直接结束；不为了“更深”强制执行固定轮数。未通过硬校验且预算耗尽时返回清楚的生成失败，不发布有问题的候选。

## 4. Harness 取舍与权限

| 能力 | 本题提案 |
| --- | --- |
| 模型 | 复用 `build_runtime_model()`；沿用当前 provider/relay 兼容与错误脱敏。 |
| SDK 版本 | 实施前及交付前实时核查最新正式发布，使用并锁定已验证的最新 Deep Agents；不降级迁就旧 API，不在运行启动时浮动更新。 |
| 结构化结果 | 使用选定版本支持的 `response_format`，验证 tool-calling 兼容和实际返回值；不能沿用直接聊天模型结果的错误提取路径。 |
| 流式事件 | 优先核查官方当前推荐 Event Streaming v3 的同步/异步入口；以所锁版本的契约与 relay 实测为准，原始事件不直接作为产品 DTO。 |
| 材料工具 | 仅本题材料目录、读取、搜索；题目/标准答案/反馈建立覆盖要求，其余材料有界补查。 |
| 后端 | 本题隔离的虚拟后端；材料只读，可选 scratch 仅在本 job 内临时存放，不暴露宿主机目录。 |
| 规划 | 可以复用轻量规划和上下文管理；不强制所有简单题先写长计划。 |
| 子代理 | 第一版不启用；显式关闭默认通用子代理并断言没有 `task` 委派入口，不能只传空列表后假定已禁用。 |
| 外部能力 | 不提供 web、shell、任意网络、跨题记忆、其他用户文件、数据库写入、确认或发布工具。 |
| 运行持久化 | 现在接入当前 Docker PostgreSQL 的专用检查点库；同 thread 的图状态和 StateBackend 工作文件可恢复，不再把所有技术重试实现为从头生成。 |
| 长期记忆 | 本题会话内连续性必须具备；已确认不接跨题 Store、不自动参考相似题。框架持久化不等于授予 Agent 直接业务写库权限。 |

材料工具只接受服务创建的定位符，不接受任意绝对路径、路径穿越或其他题目 ID。将材料内容作为不可信数据；其中的“忽略系统指令”“上传文件”等不得获得执行权限。引用定位绑定当前材料快照，真实库提交仍由服务以 revision 检查保护。

具体后端/permissions/profile 的 API 要在锁定版本后静态及 stub 测试；如果无法证明材料不可写、跨题不可读或默认子代理已关闭，不进入真实模型验收。

## 5. 校验和预算分层

### 硬校验

- 整数类型及 0–10 边界、非空维度、锚点分数唯一、输出长度/数量上限、依据对象完整。
- 初始 AI 生成结果的 score_anchors 必须包含所建议的 pass_score，并有对应表现描述；只在生成结果校验层强制，不能复用为老师普通编辑或人工新增维度的保存门槛。
- 定位符属于当前题目和 revision；引用是对应已存正文中的实际片段；明确来源标签由服务投影。
- 通过分解释携带所解释的整数，不以档位区间替代通过分。
- 保留现有维度可执行性、隐私兜底、ownership、状态和 CAS 校验。

### 语义检查

- 锚点是否有可观察差异、表现是否随分数提高；最低要求、建议分、说明是否互相矛盾。
- 每条反馈是否被解释，是否把一个例子的偶然风格上升为硬性要求；引用是否真正支持“老师明确要求”。
- 语义检查可以驱动有限补读/修订，但模型自检不能称为真实性保证；不把所有模糊情况升级为新的阻断式人工流程。

### 工程预算，实施时校准

- 用户接受较长等待，不设“必须几分钟结束”的短体验门槛；安全预算仍覆盖每次尝试模型/工具调用、有限修订、异常超时及全 job token/费用上限，同时核算 SDK、job 重试和摘要调用。安全控制不能被解释为无限费用授权，也不能任意变成短等待限制。
- 框架的 model/tool limit middleware 是局部机制，不直接等于全作业费用上限；总预算需由业务外壳及统一模型调用统计覆盖。
- 保留 Worker 心跳。失去租约、revision 已变或 job 被 supersede 后停止后续调用，最终结果不能覆盖较新的人工操作。
- 超时和输出校验耗尽应区分错误原因；不要让整个 Agent 被 SDK 与 Worker 无限叠加重试。先依据现有单请求超时/重试、作业尝试次数和真实样本体量设有界配置，再做获批后的隔离试验校准；计入摘要与重试，不承诺尚未测得的费用或 P95。校准不改变产品边界，不把真实失败伪装成正常长等待。

## 6. 前后端闭环

- 扩展 Pydantic 生成合同、API 输入/输出、`criteria_json` 的完整读写、fake generator 与测试 fixtures；不只改 prompt，避免 Service/DTO 投影丢失新内容。
- 保持 OpenAPI → generated TypeScript 单一合同；更新 `criterion-draft.ts` 的 hydration、选中项投影、手工新增及校验，辅助内容与正文一起保存、刷新可恢复。
- 维度行仍保留勾选、正文与数字输入；增加分档辅助区及“查看依据”折叠区。所有允许编辑的内容进入同一草稿，不另起隐藏 AI 状态。
- 本地关联内容核对提示基于草稿变更与解释对象差异产生，不调用模型。刷新后保留可检测的“解释分数与当前分数不一致”提示；本方案不新增独立的跨会话核对审批状态，老师仍在原保存确认动作中修正内容。
- 主动材料重生成使用明确确认弹窗；说明整套维度、分档、依据及人工修改会被替换。取消不发送写请求；确认后才调用现有保存并重新生成入口。
- 保留标题单独修改、不产生生成 job，以及 published → reopen 审改等状态门禁。无需为这次展示新增新稿或评分端点。

### 6.1 可读流式加载与长任务恢复

- 具体调研见 `research/streaming-progress.md`，执行恢复见 `runtime-design.md`。加载区显示真实阶段、已用时间、公开流式消息和连接状态；阶段可回到补读/修订，不使用计时器伪造整体百分比。
- 当前只轮询详情并显示固定生成提示的路径不足以满足要求。生成器在 Worker 内消费 Deep Agents 流，公开反馈经过来源分类、白名单和脱敏；大消息分段，不能悄悄截断已公开内容。不展示私有 reasoning、系统 Prompt、原始工具响应或 JSON 碎片。
- `RubricGenerator` 保留最终返回完整候选的边界，服务注入运行上下文、受控 sink 和框架持久化；公开消息留在业务库，图状态由专用 checkpointer 保存，adapter 不直接操作业务表。最终题目状态仍只由业务原子保存决定。
- 新增完整公开消息/事件记录及供快速展示的快照，按 thread/operation/turn/attempt/revision 关联，sequence 供去重和重连；事件合同由 Pydantic/OpenAPI → TS 统一。旧 Worker 迟到事件受 fencing 限制，不能进入新的任务。
- 首选同源 SSE 订阅，沿用现有 Next rewrite 和 cookie 鉴权；新连接验证题目/作业归属。运行在 Worker 的任务独立于浏览器，刷新、断线只影响订阅，不触发重新生成或取消 job。
- 重连先恢复快照与 cursor，再消费增量。后台恢复同一 thread 的 checkpoint，与 UI 重连不同；未完成模型请求可能重试，不承诺从最后一个字继续。完整公开过程确定保留回看，不因上下文摘要或重试而删除。
- 连接保活、Worker 心跳和最后有效进展分别表达。长时间等待模型不伪造反馈；真实失败、失租或重试明确展示，而不是无限转圈。
- 真实传输验证必须经过生产 Worker、API、rewrite/部署代理和浏览器；当前 `streaming=False` 默认值与 `_generate` relay 特殊处理不能证明显式 stream 路径失败或成功，须专项验证。
- 不逐 token 一行写库或向读屏播报；可合并但不丢内容，先持久化再发送，按阶段节流通知。用户回看前面的反馈时不抢滚动，reduced-motion 下仍能理解状态。
- 模型流结束后先校验并原子保存，再发送完成并刷新权威题目。中间内容不进入可勾选/可保存的正式维度编辑器，不另增聊天、取消、暂停或干预生成的业务流程。

### 6.2 消息、状态和中间件的所有权

- 本轮重构包括 PostgresSaver 接入、同线程上下文/工作文件持久化、重启续跑和线程单写者保障；这不是只写几个未来配置项。
- Checkpoint 不充当完整公开历史；模型输入可以摘要和裁剪，公开原文保留。已确认不接跨题 Store、不后台提炼老师的通用评分偏好；同题连续性不受影响。本题隔离的判断与已确认验收见 runtime-design.md 第 7 节。
- 倾向少量 class-based AgentMiddleware，使用 before_agent/before_model 做适当初始化和状态更新，wrap_model_call/wrap_tool_call 做观测与受限调用控制；普通单 hook 纯规则可用装饰器。after_agent 不拥有业务成功判定。
- 服务/Worker 负责授权、lease、线程独占、幂等、公开消息持久化和最终提交；不能把这些转交给一个万能 middleware。具体 hook、状态更新规则、恢复窗口和 M1 interrupt 合同见 runtime-design.md。

### 6.3 同题完整删除与成功状态

- 业务已确认一并删除完整过程和上下文，保留原确认门禁。实现按 runtime-design.md 第 11 节，复用 OperationJob 持久执行跨库清理，不使用业务表删除后忽略 checkpoint 错误的做法。
- 原 DELETE 路径补稳定命令标识并返回已受理的 operation；前端沿用确认弹窗，真实显示处理/失败/重试，所有关联数据删除完成后才导航离开并显示成功。OpenAPI、TS、handleDelete 和测试同任务切换，不保留旧的提前成功语义。
- 为有实际用途的删除处理中状态提供最小投影。冻结所有同题写入/恢复并停止相关回放，清完全部历史 thread/checkpoint 后，再原子删除业务原文和生成历史、提交删除作业成功。清理失败不开放旧题或误报成生成失败。
- 生成 jobs 与删除控制作业有不同 target/kind；后者只保留 ID、阶段、状态等无正文回执，不能被生成历史清理误删。模型 Provider 不可用也不能阻塞数据库清理。

## 7. 一次性切换与回滚

- 被替代的是“`criterion + pass_score` 就是完整维度”的生成、保存、显示和测试合同；保留这两个仍有效字段，不误删逐项通过语义。
- 最新 Deep Agents 路径验收后，删除被替代的单次 generator 路径及其两字段 prompt/结果假设；固定流程对照只作为离线验收实验，不成为生产兼容开关。保留模型工厂、Worker、fake 测试模式，不把它们误当遗留删除。
- 生成页面的旧静态加载/整题轮询分支由真实进度订阅与快照恢复替换；保留权威详情读取和完成后的刷新，不误删业务 GET。不得保留假的流式打字、固定时序进度或静默降级旧提示入口。
- 删除旧的“业务题目行删除后立即 204/前端立即跳转即成功”路径；保留并复用现有权限、revision、状态和标题校验，以及最后业务事务中的真实硬删除能力，不为兼容旧成功语义增加旁路。
- 更新维护中的 README、相关 `.trellis/spec/` 与 OpenAPI/TS；归档任务不批量重写。当前现场没有需联动的其他活动父子任务。
- 存量缺分档/依据的题目不能靠 `.get(..., default)`、隐式 DTO 转换或运行时自动补齐冒充新合同。允许在新合同中显式为空的人工内容，不构成接受旧缺字段结构的理由。
