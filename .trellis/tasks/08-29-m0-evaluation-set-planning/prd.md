# M0 评测集交互与后端规划

## Goal

从业务老师真正要沉淀、并在 M2 用来判断 Skill 是否可靠的资产出发，规划当前 M0 的完整产品闭环、前端交互与后端领域边界。M0 必须能够独立产生可验证价值，同时只为 M1 知识库和 M2 Skill Agent 保留必要边界，不提前实现后续里程碑。

## Background and Confirmed Facts

- 外部构想资料把路线暂分为：M0 建业务场景评测集，M1 为场景绑定知识库，M2 绑定能加载 Skill 的 Agent 并多轮在线评估。资料自身标注为“待业务确认”，因此它是需求证据，不是已批准规格。
- 当前仓库已经实现的是一条内存 Stub walking skeleton：登录 → 创建私有场景 → 上传单条真实案例 → AI Stub 整理或追问 → 老师审改 → 定稿并保存 `candidate_case`。现有合同明确 `candidate_case` 不会自动进入评测集，也不会触发评测（`docs/architecture.md:11-28`）。
- 当前 `case-builder` 已为单条题保存任务目标、输入摘要、输出要求、禁用错误、参考结果与理由、来源事实与判断、AI 候选标准、证据缺口、能力、评分维度和标签；评分维度分为硬门禁、必达质量和诊断项（`docs/features/case-builder.md`、`backend/app/features/case_builder/schemas.py`）。
- 当前实现没有评测集实体、集合成员关系、版本冻结、发布、评测运行或报告；持久化、真实文件存储、真实模型和 LangGraph 也尚未落地。
- 最近一轮已把老师定位为“题的作者”，界面采用“场景 / 题稿 / 题 / 定稿”词表，并把审改设计成一屏一节的聚焦阅读。该资产继续保留，但需要扩展到批次、任务分组、场景合同、下一版本草稿和冻结历史。
- 当前技术基线是 Next.js App Router 前端、FastAPI 后端和后端 Pydantic/OpenAPI 作为跨层接口事实源。
- “会议录音 16”提出 M0 只直接使用 Deep Agents 的假设。三轮对抗审查后的当前结论是：Deep Agents 是唯一 AI Runtime，应用层不额外创建 LangChain Agent 或手写 LangGraph；FastAPI、确定性规则和 PostgreSQL 业务表负责业务权威。多轮共创的 `standard_cocreator` 使用 PostgreSQL Checkpointer 保存 thread 级执行状态和中断游标；`batch_analyzer`、`coverage_reviewer` 不保留跨轮 thread；M0 暂不使用跨 thread 的 Store/Memory。
- M0 当前只面向主观型文案与新闻稿业务，不要求用 RSVP、名单或其他客观任务证明跨类型通用性；客观任务的确定性断言仍保留为未来模型边界，不纳入本次产品验收声明。
- 已静态检查两份真实主观样本：财报媒体供稿 JSONL 是包含 310 条事件、单一会话、工具调用、初稿、老师反馈与终稿的原始 Agent 事件流；MEGA ZIP 包含讲稿 v2、拍摄指引和完整对话导出三份 Markdown，体现材料更新、多轮修改和最终稿形成。它们是两个独立真实写作任务，可作为同一主观新闻稿场景的两道 M0 验收题候选。
- 另提供的《理想汽车2026年第二季度财报-媒体沟通文档.md》是 424 行业务 Brief 与事实材料，应作为任务包中的 Markdown `runtime` 输入候选，而不是独立题或默认 `judge` 答案。所有文件角色仍需 Deep Agent建议并由老师确认。

## First-Principles Problem Statement

业务老师需要把隐性的业务判断转成一组可复用、可追溯、可在未来重复执行的评测资产，使同一个 Skill 的不同版本或多次运行可以在同一把尺子下比较，而不是只完成一次内容整理。

## Requirements

### R1 — 当前里程碑边界

- 本任务只规划 M0 的可交付闭环。
- M1 仅保留“场景或题未来可引用知识资产”的边界，不实现知识库上传、索引或检索。
- M2 仅保留“稳定评测资产未来可被 Agent 执行”的输入、输出和评分合同，不实现 Skill 上传、Agent 运行、多轮评估或报告。

### R2 — AI Native 共创

- 业务老师不应被要求先懂评测工程或手写固定 JSON。
- AI 应帮助老师从真实业务证据中识别任务输入、期望输出、硬性错误、质量标准和缺口。
- AI 只能提出候选内容；最终业务标准必须由老师显式确认。
- 新场景不采用纯空白问答，也不直接批量导入。老师先说明评测目的并提供至少一个代表性真实案例，AI 基于两者起草“场景评测合同”。
- 老师确认场景评测合同后再继续导入和整理更多案例，避免在没有共同尺度时逐题生成互不一致的评分规则。
- 场景评测合同在评测集冻结前可以继续演进，但任何变化都必须可见、由老师确认，并在冻结时成为该评测集版本所引用的确定快照。
- 场景合同、单题规则和判定依据包都通过老师与 AI 的逐轮沟通动态形成；系统不要求老师预先理解底层结构或一次填完固定长表单。
- 动态只属于形成过程：AI 可以持续追问、归纳、指出缺口和提出候选内容，但老师确认后的题、场景合同快照和冻结评测集版本必须是静态、可回查的事实。
- 冻结后出现的新判断或 AI 建议只能形成新修订和新评测集版本，不能动态改写历史版本。
- AI 每轮只提出一个当前最高价值问题，并说明该问题要补齐的事实、判断、规则或风险缺口；老师回答后，AI 基于最新上下文选择下一问。
- AI 可以温和但明确地指出前提错误、证据不足、逻辑矛盾、替代解释和遗漏信息，并给出如何修补当前构想的建议，不能只质疑不建设。
- “理解内心深处”“潜意识”或模型自报的信心百分比不能作为产品完成条件；完成条件必须落到结构完整性、证据、阻塞缺口和老师确认上。
- 初始化场景合同所使用的代表性任务包在合同确认后，默认沿用同一份证据继续生成该场景的第一道候选题；不要求老师重新上传。
- 老师可以把代表性任务包标记为“仅用于场景初始化”，停止生成或放弃该候选题。即使继续生成，它仍需完成单题共创、老师定稿、显式组集和版本冻结，不能因承担初始化作用而自动成为正式题。

### R3 — 评测可信度

- 输入、参考输出、评分规则和老师判断必须可区分、可回查，不能把 AI 推测伪装成业务事实。
- 后续任何版本或执行结果不能静默覆盖已确认历史。
- M0 的最终资产不是一批松散的候选题，而是一个由老师显式组集、检查并冻结的评测集版本。
- 冻结版本必须不可变并可回查；后续增题、删题、改题或调整评分规则只能形成新的草稿和新版本，不能改写旧版本。
- 当前 `candidate_case` 只代表可供选择的已定稿题；只有被老师纳入并随某个版本冻结后，才成为该版本的正式评测题。
- 评测集版本冻结不设固定最少题数或强制覆盖率。不同业务场景的价值取决于真实能力和风险覆盖，不以堆叠同质题达到数量门槛。
- 冻结的硬完整性门至少包括：场景合同已确认；至少选择一道已定稿题；所有入选题已基于当前合同修订完成复核；任务包、判定依据、来源证据和主要保护能力完整；不存在阻塞缺口、必需但不可读取的文件或未确认角色；版本快照和说明可完整生成。
- Deep Agent 在冻结前生成能力、评分维度、失败模式、任务类型、重复题和明显空白区的覆盖摘要。覆盖不足只形成风险提示，不自动阻塞；老师明确确认后可以冻结，风险摘要与确认记录随版本保存。
- 界面必须把“已冻结”和“覆盖充分”分开表达，不能以发布成功暗示该版本已经成熟或全面。
- M0 中每个场景只有一条正式评测集版本线，按 `v1 → v2 → v3` 连续演进；候选题池属于场景，不为同一场景复制多套独立评测集和合同。
- 未来的冒烟集、完整集或特定风险集应作为某个冻结版本上的筛选视图或运行子集，不复制题和标准；若两组任务无法共享同一场景合同，应拆成不同场景。
- 最新冻结版本保持只读。后续新增题、修改题、停用题或修改场景合同，都进入唯一一个从最新冻结版本派生的“下一版本草稿”；冻结时才获得下一个连续正式版本号。
- 题池中的候选题可以独立共创和定稿，但只有被老师显式加入下一版本草稿才改变未来正式评测集。修改已入集题产生新修订，停用只从下一版本移除，历史版本快照不变。
- 下一版本草稿可以整体丢弃并重新从最新冻结版本派生。M0 不支持并行版本分支、分支合并或多套下一版实验方案。
- 冻结评测集版本时，系统必须原子生成并保存一份不可变、自包含、机器可读的版本包；数据库快照、下载内容和版本 API 必须指向同一份 Manifest 和整体校验值。
- 版本包至少包含 Schema 与评测集版本、场景合同快照、覆盖摘要、每道题的任务描述、允许输入、判定依据、来源与文件哈希，以及冻结人、时间和覆盖风险确认。
- 版本包不包含 Deep Agent内部思考、Checkpoint、系统提示词全文、被忽略文件或上传批次中的无关内容。打包失败或校验不一致时，冻结操作整体失败，不留下半冻结版本。
- M0 提供版本包下载和机器可读 API；未来 M2 必须按版本包整体校验值引用并消费，不得从可变业务表临时重新拼装历史版本。
- 自包含版本包在物理结构和 Manifest 可见性上强制分离三类视图：`runtime` 只含被测 Agent 原本允许看到的任务、Brief 与输入；`judge` 保存参考结果、确定性断言、评分标准和门禁；`provenance` 保存老师判断、来源定位、AI 候选来源和确认历史。
- M2 的被测 Skill/Agent 只能获得 `runtime` 分区，不能直接挂载或读取完整版本包；评判器和老师按授权读取 `judge`，`provenance` 只用于审计解释。
- 三个分区分别计算哈希。冻结前若任一文件或字段的可见性未确认，硬性阻塞冻结；老师下载完整包时，界面明确标识哪些内容不得交给被测 Skill。

### R4 — 当前用户与权限边界

- 延续当前单用户、私有场景的产品边界；M0 不预建成员、角色、邀请或权限体系。
- M0 采用运营前提：使用者是经过培训的内部业务老师，只上传已整理、允许交给平台 AI 分析的材料。当前不建设自动敏感信息扫描、DLP、脱敏预览或按片段授权流程。
- 该前提是用户明确接受的阶段性风险假设，不表述为“敏感内容技术上不可能出现”；上传仍保持私有隔离，应用自身凭证不得进入上传材料、模型上下文、日志、错误或测试制品。

### R5 — 场景合同与单题规则分层

- 场景评测合同定义本场景所有题共享的任务边界、输入输出结构、评分维度和硬门禁。
- 单题保存具体任务、输入材料、参考结果与只对本题成立的补充规则。
- 单题补充规则只能让共同标准更具体或更严格，不能覆盖、删除或削弱场景级硬门禁；若共同规则不适用，应修改场景合同并形成新修订，或拆分为不同场景。
- 前端必须清楚区分“继承自场景”和“本题补充”，不能把两层规则混成一份无法追溯来源的文本。
- 后端必须分别保存场景合同和单题增量，并在冻结评测集版本时保存可复现的合同快照与每题有效规则。
- 场景合同的每次修改产生新修订，不得静默改变已经定稿的题。
- 合同修改后，系统必须列出所有受影响题并标记为“待复核”；题经过逐题复核，或满足批量确认“无冲突”的条件并由老师确认后，才能进入引用新合同的评测集版本。
- 同一冻结评测集版本不得混用未经复核的不同场景合同修订。
- 合同影响审查采用三层责任边界：确定性规则判定结构和硬约束冲突；AI 只提供语义差异、疑似影响、证据与修订建议；老师拥有最终放行权。
- AI 无权自动解除题的“待复核”状态。只有确定性规则证明没有实质影响的题，才可进入由老师触发的批量“确认无冲突”；其余题必须人工复核。
- 日志中提取的每条老师批注默认只作为本题证据保存。Deep Agent可以建议其范围为“仅本题”“候选场景标准”或“暂无法判断”，但不能自动改变场景合同。
- 场景标准升级提案必须展示原始批注、候选规则、长期性理由和受影响题；只有老师明确选择“升级为场景标准”才创建合同新修订并触发影响审查。跨任务重复出现只增强推荐理由，不产生自动升级权。

### R6 — 必填的判定依据包

- 每道正式评测题都必须具备可冻结的“判定依据包”，但不强制存在唯一标准答案。
- 判定依据包根据任务类型采用不同的判定方式：客观任务可使用期望结果、结构化断言或确定性检查；主观任务可使用一个或多个参考结果、认可或否定原因、硬门禁和最低质量标准；混合任务可组合使用。
- 无论采用哪种方式，都必须能回答“什么算通过、依据是什么、哪些错误不可接受”，并保留来源证据和老师确认记录。
- 判定方式与具体内容由 AI 根据任务和证据提出候选，通过与老师逐轮沟通补齐和修正，最终由老师确认。
- M0 的实际实现和验收重点是主观判定包：参考稿或多版结果、老师认可与否定原因、事实和表达硬门禁、最低可用质量线、任务特有修改意见，以及从多轮反馈中提出的长期标准候选。

### R7 — 双重完成门

- 系统使用确定性规则检查所选任务类型对应的必填结构、有效证据、场景继承规则、判定方式和阻塞缺口。
- AI 负责识别尚未结构化表达的语义歧义、矛盾和风险，并在每轮只选择一个最高价值问题；AI 可以建议“信息已足够，可以进入定稿”，但不能自行结束会话或确认内容。
- 老师可以把未知标记为阻塞或非阻塞；只要存在阻塞缺口，就不能进入最终定稿或冻结。
- 结构门通过且不存在阻塞缺口后，由老师主动进入最终审阅并确认；老师确认才结束当前共创阶段。

### R8 — 聚焦问答与渐进可见

- `/workspaces/{id}` 是唯一场景工作台。上传、后台处理、任务边界确认和场景标准共创是“当前”中的渐进阶段，不按后端实体拆成独立页面；独立深链只保留聚焦题详情和只读版本详情。
- 场景内稳定信息架构只保留“当前 / 题 / 版本”三类：当前承载唯一下一步和正在处理的工作，题承载题稿与已定稿题，版本同时承载下一版草稿与冻结历史。不得把过程、资产、状态和历史混成四种并列导航。
- 系统根据持久化业务状态给出唯一 `next_action`；前端不猜测流程，也不同时摆出多个同级主操作。老师刷新或重新进入场景后，应回到同一项未完成工作。
- 共创主区域每次只呈现一个最高价值问题、提问原因和回答入口。回答处理完成后展示紧凑的“本轮更新”，至少区分新增、修改、删除和仍有疑问，不能静默更新结构化内容。
- 场景标准、单题判定依据、未解决缺口和已完成问答过程通过按需检查器查看，默认关闭；桌面使用侧 sheet，窄屏使用全屏 sheet，不形成永久双栏或三栏工作台。
- AI Native 由行为而不是装饰表达：从真实证据起步，AI 主动提出有出处的候选变更，老师只审阅差异和后果，系统自动给出下一步并可恢复。界面禁用聊天气泡、机器人头像、魔法棒、发光球、渐变光晕、token/tool 流和“AI 正在思考”等拟人化表演。
- UI 只使用“资料、任务、场景标准、题稿、题、下一版、历史版本”等业务词。`UploadBatch`、`TaskPackage`、`runtime/judge/provenance`、hash 和 revision 等技术词只存在于合同或折叠技术详情；三视图面向老师分别叫“给 Skill 的材料、评分依据、形成记录”。
- 高级感依靠一个焦点、克制的文字层级、较少容器和稳定留白。默认画面不做卡片墙、卡中卡或大面积品牌色；主要动作使用中性深色，蓝色只用于链接、焦点和当前态，语义色只用于状态。
- 现有 30 字预算只约束页面副标和被动 hint。任务分组、标准升级、合同影响和冻结确认可以使用简短多行后果说明，再通过渐进披露收起细节，不能为了少字牺牲可理解性。
- 生产界面不提供 JSON 编辑器，机器错误码和版本哈希默认隐藏在“技术详情/复制问题编号”中；Preview 或开发工具可以保留。
- 结构门通过且老师选择结束共创后，进入独立的逐节审阅与定稿模式；问答阶段和最终确认阶段职责分离。

### R9 — 完整任务包与异构证据

- 一条代表性案例或正式题的原始输入是“完整任务包”，不是单个文件。任务包至少可承载任务 Brief、允许使用的输入材料、参考结果或判定证据、老师补充说明；每个部分都可以是文本或多个文件。
- 老师可以一次上传多个文件或一个包含完整执行证据的压缩包，包括多次调用 Skill 产生的结果、对话日志和相关附件。
- 系统先安全解包、建立文件清单和来源标识，再由 AI 推断每个内容的角色、重复关系和候选关联；老师必须确认或调整角色后才能进入场景合同或单题共创。
- AI 解析产生的摘要、角色和关系都是候选解释，必须保留到原始文件或日志位置的引用，不能替代原始证据。
- 只服务单道题的 Brief、输入和执行记录属于 M0 任务包；会被多道题或实际 Agent 反复检索的历史资料属于 M1 知识库。
- M0 对压缩包中的 `SKILL.md`、脚本、代码和其他可执行内容一律只读解析，绝不在宿主机或沙箱中执行；实际加载和运行 Skill 属于 M2。
- 安全解包、路径穿越与符号链接拒绝、文件数量与展开大小限制、格式识别、哈希、去重和清单生成必须由确定性代码完成，不能交给 AI 自由执行命令。
- AI 只能读取经过安全处理和权限过滤的证据视图；任何文件内容都视为不可信数据，不能把其中的提示词或指令当成系统指令执行。
- 系统必须为任务包中的每个文件保存确定性解析状态，例如已解析、不支持、损坏、加密、超限或被安全规则拒绝；Deep Agent 只能对实际可读内容建议角色和相关性。
- 老师必须把未成功解析或角色不确定的文件明确标记为“本题必需”或“明确忽略”。必需文件未解析、文件角色未确认，或判定依据引用了不可读取内容时，阻塞共创完成、定稿和冻结。
- 老师明确忽略文件后可以继续，但冻结版本必须保留文件名、哈希、解析失败原因和忽略理由；Deep Agent 无权替老师把未读取文件判定为不重要。
- 一次上传是一个 `UploadBatch`，可以包含零个、一个或多个真实任务。Deep Agent 根据任务目标、核心输入、上下文和调用记录提出 `TaskPackage` 分组，老师必须确认、合并或拆分任务边界后才能进入单题共创。
- 同一真实任务的多次 Skill 调用、不同模型结果、反复修改和老师取舍保留在同一个任务包内，作为多次尝试与判定证据；任务目标或核心输入不同的记录拆成不同任务包，并分别生成候选题。
- Deep Agent 无权根据分组自动创建正式题。分组确认后，每个任务包独立进入逐轮共创、定稿和组集；一个上传批次可以最终产生零道、一道或多道候选题。

### R10 — 受限 Deep Agents AI Runtime

- M0 对所有已通过安全解包和清单校验的任务包统一使用 Deep Agents，不让老师选择“简单或复杂”模式，也不维护另一套非 Agent 分析路径。
- 为降低大 Schema 与职责混杂风险，运行时创建三个同 AI Profile、相互无委派关系的命名 Agent：`batch_analyzer`、`standard_cocreator`、`coverage_reviewer`。它们不是子代理，不暴露 `task`，每个只承担一个小型 Pydantic `response_format`。
- M0 不实现确定性快速分析路径。业务场景和证据包高度异构，当前优先验证通用理解、来源完整性和老师可用性，不在缺少真实数据时预建双路由。
- Deep Agents 最低版本必须支持按名称替换内置 `FilesystemMiddleware` 和文件工具 allowlist。`batch_analyzer` 只读当前批次证据，`standard_cocreator` 只读当前任务包证据，`coverage_reviewer` 只接收已确认的结构化快照且不暴露文件工具；三个 Agent均关闭默认 general-purpose subagent，不启用 Skills、Memory、Todo、写入、执行、联网和业务数据库工具。
- 生产环境不把 `FilesystemBackend` 直接指向 Web/Worker 宿主文件系统。应用提供只读 `EvidenceBackend`，按服务端 `AgentRunContext` 把 `/evidence/**` 映射到当前运行获准的 canonical evidence view；写入方法固定返回拒绝。开发 Spike 可以用独立临时目录验证 `FilesystemBackend(virtual_mode=True)`，但不能把该形态默认为生产安全边界。
- 需要文件访问的 Agent同时使用工具 allowlist 和 first-match-wins 权限：先允许读取各自 `/evidence/**`，再拒绝其他所有读取，最后拒绝 `/**` 写入；任何未匹配权限不得依赖默认 allow。替换内置 `FilesystemMiddleware` 时，`backend` 与 `permissions` 必须直接传给替换实例，不能只传给 `create_deep_agent()` 后假设会自动继承。M0 不注册会绕过内置权限的自定义/MCP 文件工具。
- 分析必须受模型调用数、工具调用数、总时长、上下文和输出大小限制，并强制返回带来源定位的结构化候选结果。
- `Evidence Analyzer` 保持独立接口，用于隔离 Deep Agents 版本、测试替身、失败恢复和未来证据驱动的替换；保留接口不代表 M0 需要路由。
- 未来只有真实运行数据证明某类规范化任务包能以更低成本获得等价质量时，才评估替换实现或新增快速路径；该可能性不纳入 M0 范围，也不做永久禁止。
- M0 只直接集成 Deep Agents 作为唯一 AI Runtime，不额外创建第二个 LangChain Agent，也暂不手写自定义 LangGraph；Deep Agents 对 LangChain 和 LangGraph 的内部依赖不构成应用层的第二套编排。
- Deep Agent 负责证据理解、语义检查、结构化候选变更、下一条最高价值问题和“可以定稿”的建议；它不能成为业务事实、权限、结构完整性、状态转换、幂等、版本冻结或审计的最终权威。
- `create_deep_agent(response_format=...)` 的输出只从 `structured_response` 读取。真实 capability Spike 已将当前 AI Profile 固定为 ToolStrategy；ProviderStrategy/AutoStrategy、自由文本 JSON 和未经验证的模型路由不得进入生产配置。
- 每个 Agent 使用小型、分阶段 Schema。若指定模型/供应商不能稳定返回有效工具调用与结构化结果，实施必须停下更换模型或适配器，不静默退化为自由文本 JSON。应用仍对 Pydantic 结果做证据 locator、归属、阻塞缺口和状态前置条件复验。
- EvidenceRef 使用服务端文件 ID 与已验证 locator，不信任模型输出的宿主路径。长文件必须先读 manifest/行数，再用显式 `limit` 和 `offset` 分页至 EOF；不得依赖 `read_file` 默认 100 行后宣称完成分析。
- FastAPI 业务服务、确定性规则和 PostgreSQL 业务表是 M0 的业务事实源。只有老师的显式操作才能完成定稿或冻结；模型私有 reasoning、Checkpoint 和消息历史都不是业务证据。
- `batch_analyzer` 与 `coverage_reviewer` 每个业务 retry 使用新的 `AgentRunAttempt` 和 thread，从确定性输入重跑，只有完整验证结果才提交；M0 不为它们维护稳定跨轮 thread。
- `standard_cocreator` 的每个 `CoCreationSession` 使用一个服务端生成、少于 255 字符的稳定 `thread_id`，并接入生产级 PostgreSQL Checkpointer。Checkpoint 保存短期消息、工具调用配对、临时工作文件、pending interrupt 和恢复游标；业务表保存当前草稿、老师回答、确认、revision、`next_action` 和不可变历史。
- 每次开始或恢复共创前，Service 必须从业务表校验 workspace/target 归属、业务 revision、`ai_profile_version`、Graph Schema 版本和证据 scope；这些可信字段通过 typed `AgentRunContext` 重新传入，不由模型生成，也不由浏览器提交。Runtime context、凭证和数据库连接不得塞入 Checkpoint。
- 共创优先使用只读 `ask_teacher` 工具形成一个 ask-user 型中断，并将其 `interrupt_on` 决策限制为 `respond`。一次中断边界只能存在一个待答问题；老师答案先幂等写入 `CoCreationTurn`，再由 Worker 使用同一 thread 和明确的已接受 Checkpoint 恢复。
- 若真实模型/Adapter 无法稳定组合 `interrupt_on + response_format`，M0 允许使用同一稳定 Checkpointer thread 的完成式问答：Agent 返回唯一下一问后结束当前 invoke，下一轮把老师回答作为新消息追加到同一 thread。该降级不能退回无 Checkpointer，也不能改变前端和业务状态合同。
- `CoCreationSession` 必须记录当前已接受的 Checkpoint 指针、业务 revision、AI Profile/Graph Schema 版本和待答 interrupt 标识。任何 resume 都从已接受 Checkpoint 开始，而不是盲目使用 thread 的最新分支；每场共创同一时刻最多一个有效运行。
- Graph 到达新中断或完整结果后，Adapter 先验证结构、EvidenceRef 和业务前置条件，再由业务事务以 revision CAS 提交投影，并同步推进已接受 Checkpoint 指针。Checkpoint 已推进但业务投影失败时，优先从已产生的 Checkpoint 重建投影，不重复调用模型；陈旧分支标记为 superseded，不能覆盖新 revision。
- Checkpoint 使用加密序列化、独立迁移和明确保留/清理策略；业务确认或冻结后，即使清理 Checkpoint，题、合同、版本与形成记录仍必须完整可用。Checkpoint、原始 Agent messages、自动摘要和恢复游标不得进入版本包或前端合同。
- M0 暂不启用 LangGraph Store、StoreBackend Memory 或 MemoryMiddleware。跨场景、跨 thread 的业务事实继续进入领域表；未来只有出现明确的用户偏好或 Agent 长期知识需求时才单独设计 namespace、写权限和提示注入防护。
- M0 默认只使用内置 `ModelCallLimitMiddleware`、`ToolCallLimitMiddleware` 与有限 `ModelRetryMiddleware`。不对文件工具配置 ToolRetry，不配置 fallback、动态模型、动态工具或动态系统提示词。结构化结果与业务前置条件在 Adapter/Service 中校验，不放进 `after_agent` 自动改业务状态。
- 安全 HarnessProfile 只在进程启动时按精确模型键注册，用于关闭 general-purpose subagent 等全局不变量；不得在请求处理中重注册或用同一全局键承载会话级 `ai_profile_version`。Agent 图实例按 `ai_profile_version` 缓存或构建，middleware 实例必须无共享可变计数器。
- 只有 Spike 证明 Deep Agents 的 Checkpointer/HITL 组合无法表达当前单问题暂停、恢复和结构化输出时，才评估在应用层直接下沉到自定义 LangGraph；M0 不预建第二套图编排。
- M0 由平台统一管理一个带版本的 AI Profile，至少固定模型、系统提示词、只读工具集、输出 Schema 和 Analyzer 版本；老师界面不提供模型选择，也不做动态路由。
- 每个上传分析和共创会话在开始时绑定一个 `ai_profile_version`；共创 session 同时绑定 Graph Schema 版本。后续回答、失败重试和恢复继续使用相同版本，不能静默切换模型、提示词、Graph 结构或备用供应商。
- 新会话使用平台当前 Profile。模型不可用时进入明确、可重试的失败状态；未完成共创若必须迁移，由管理员显式从业务投影创建新 thread，记录旧/新版本和 continuity reset，不能直接用新 Graph 恢复旧 Checkpoint。
- 已由老师定稿的题不会因 AI Profile 升级自动失效，但每次 AI 候选变更都保留其 Profile 版本作为内部来源记录。
- M0 前端不消费 Agent token、tool 或 reasoning stream；模型调用默认非流式，页面进度只来自持久化业务 job state。

### R11 — 统一持久化操作状态

- 安全解包/批次分析、场景或单题共创的一轮 AI 更新、覆盖审查和版本包冻结都可能超过普通 HTTP 时限，统一通过一个数据库任务表和单消费者执行；不能只把上传异步化、却让问答或冻结继续阻塞请求。
- 命令接口在验证权限、revision 和幂等键并保存用户意图后返回 `202` 与完整业务投影；老师可以离开、刷新或稍后返回，仍能读取真实状态并继续。
- 前端只消费持久化业务投影：`revision`、唯一 `next_action`、当前 `active_operation`、最近 `receipt`、阻塞项和可重试信息。Agent messages、ToolMessage、Checkpoint、raw trace 和 Worker Job record 不进入前端合同。
- 前端只保留输入草稿、sheet 开关、选中节和“命令正在提交到 202”为止的瞬时状态；服务端快照一到即覆盖本地猜测。M0 不为此引入 Redux/Zustand 等全局状态库。
- 前端通过仅在 `active_operation` 存在时启动的可见性友好轮询展示真实阶段，不伪造精确百分比。至少区分等待处理、读取资料、AI 整理、等待老师、冻结中、失败和完成。
- 同一 target/revision/command id 的重复提交、刷新和重试不得启动第二个并发操作；失败在原业务对象上显式重试，服务重启后能够识别租约过期并重新接管。
- Worker 开始共创 resume 前和提交结果前都必须比较 target revision、已接受 Checkpoint 指针和操作前置条件；若对象已被丢弃、替换、推进或 thread 分支已改变，旧运行标记为已过期且不得覆盖当前投影。
- M0 不实现 SSE、WebSocket、Token 流式输出，也不要求 Celery、Redis 或独立任务队列。未来若增加推送，也只能推送同一套持久化业务投影事件，不能新增第二套前端状态语义。

## Out of Scope

- M1 知识库格式、上传、索引、检索和引用实现。
- M2 被测 Skill Agent 的格式校验、Skill 加载、执行沙箱、多轮运行、聚合评分和报告；M0 使用的只读 Deep Agents AI Runtime 不等于进入 M2 执行范围。
- 客观任务类型的确定性断言生成、客观 Judge 实现与跨主观/客观任务类型的通用性验收；M0 只声明主观文案/新闻稿标准共创能力。
- 多成员协作、角色权限、审批流和组织级治理。
- 上传内容的自动敏感信息识别、DLP、PII 脱敏和按片段授权；若未来开放给未培训用户、跨组织使用或进入生产合规范围，再单独设计。
- LangGraph Store/StoreBackend Memory、MemoryMiddleware、跨场景长期记忆、自定义业务 middleware 和 Agent event/token streaming。`standard_cocreator` 的 PostgreSQL Checkpointer 与 ask-user 中断属于 M0；其他 Agent 不保留跨轮 thread。
- 在新的最终规划摘要获再次批准前修改产品代码、运行 `task.py start` 或启动实施。
