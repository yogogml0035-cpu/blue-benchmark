# 评测集平台 · 设计系统

Skill Eval Platform 前端的设计系统。改 UI 前先读这份，值已经定好了，照用不要重新推导。

实现位置：`frontend/src/app/globals.css`（token 与基础件）、`frontend/src/components/ui/`（跨 Feature 原件）、
各 Feature 目录下的 `*.module.css`（组合件）。

> 2026-08-29 第二轮改版：第一次改版（fc3a104）token 对了但版式名不副实——文案当合同写、每屏容器成叠。
> 本轮定稿：核心产出物叫**题**，详情页的阅读与确认改为一屏一节的**聚焦**阅读，签名收尾。
> 本文件是唯一事实源，旧方向（纸墨审校台、第一次改版的多卡片详情页）的任何元素不得复活。

## 1. 方向与语气

**标准工作台**：业务老师把一次真实交付沉淀成一条白纸黑字的题。核心叙事——
「我在把我们『什么算好』写成题」；平台自述——「用你的题，验证 Skill 每次改版」。

- 使用者：PR/传播口的业务老师，不是开发者。刚做完一次真实交付，想把「什么算好」固定下来。
- 老师是**出题人**，不是档案管理员。界面每一屏都应让她觉得「我在写我们业务的题」。
- 核心动词：**定稿**。老师是权威，AI 是必须给出处的整理者。
- 语气：安静、清晰、可信。像读一份写好的题，不像聊天工具，更不是配置台。
- **只做浅色**。`color-scheme: light`。

反面清单（刻意避开，不要退回去）：

- 纸墨隐喻的任何残留：卷宗、校样、落章、印章、牛皮纸标签、楷体、墨线、引注边栏、案号、第 N 校；
- 通用 SaaS 仪表盘（侧边栏+顶栏外壳；本闭环只有四条路由且流程线性，题卡片上的进度就是导航）；
- 把草稿塞进一个 JSON `<textarea>`（JSON 只作折叠逃生口）；
- 居中转圈的加载态（用撑住最终版面的骨架）；
- 装饰性图标、胶囊圆角（999px）、处处显示的状态徽记；
- **把合同说服力写成页面文案**——「逐条审阅，可直接修改」「AI 只能提出带出处的草稿」这类话不出现在界面上；
- **一屏叠多个卡片容器**——详情页聚焦模式下每一屏只有一张卡。

## 2. 词表

界面用词与代码/API 词分两层：**API 契约词永远不动**，界面说人话。

| 界面词 | 代码/API（不动） | 说明 |
|---|---|---|
| 场景 | workspace | 私有业务空间 |
| 真实案例 | case / SourceCase | 一次真实交付 |
| 材料 | attachment | 案例附件 |
| 题稿 | draft | AI 整理的待确认草稿 |
| 需要补充 | pending_question | AI 向老师提的唯一问题 |
| **题** | candidate_case | 定稿后的产出物；API 字段名不动 |
| 题 v N | draft_revision | 版本号 |
| 案例编号 | case id | 地址栏与验收用 |
| 评测集（未来） | regression set | 题加入评测集属后续阶段 |

生命周期：真实案例 →（AI 整理题稿 → 需要补充 → 审改）→ 定稿为题 → 评测集。

八个状态的界面标签：parsing=解析中 · parse_failed=解析失败 · ready_for_ai=待整理 ·
generating=AI 整理中 · waiting_for_input=需要补充 · waiting_for_confirmation=待你定稿 ·
ai_failed=整理失败 · confirmed=已定稿。

关键动作：创建场景 · 上传并解析 · 提交回答并继续 · 定稿。

## 3. 颜色

中性灰骨架 + 唯一强调色。语义色只表达状态，不做装饰。

```
底色     --bg        #f5f5f7   页面
         --surface   #ffffff   卡片
         --surface-2 #f5f5f7   卡片内嵌区域/输入底
文字     --text      #1d1d1f
         --text-2    #6e6e73
         --text-3    #86868b
发丝线   --hair      rgba(0,0,0,0.10)
         --hair-soft rgba(0,0,0,0.06)
主操作   --accent    #0071e3
语义     --amber     #b25000   需要补充/证据缺口
         --red       #d70015   失败
         --green     #1d8a4b   已定稿/成功
```

规则：

- 主操作（创建场景、上传、提交回答、定稿）一律 `--accent`；页面上同时只有一个主按钮。
- 提示卡用语义色 8–10% 透明度做弱底色，文字用上表深档；全站禁用大面积饱和色块。
- 输入控件底色 `--surface-2`，比卡片暗一档。
- 顶栏与画布同色（`--bg`），只用一条发丝线分隔。
- 全部文字色对白底满足 WCAG AA；新增文字色先算对比度。
- 维度类型（hard_gate / required_quality / diagnostic）**不用颜色区分**，用纯文字后缀（见 §7）。

## 4. 字体与层次

```
--font-ui   -apple-system, BlinkMacSystemFont, "SF Pro Text", "PingFang SC",
             "Hiragino Sans GB", "Microsoft YaHei", sans-serif
--font-mono "SF Mono", ui-monospace, Menlo, Consolas, monospace
```

全站无衬线、无楷体。层次靠 **字重 + 字号 + 灰阶** 三根杠杆：

```
页面标题   28 / 650 / -0.02em     每屏一个
题卡节标题 20 / 650 / -0.01em     聚焦阅读时的当前节名
分组标题   13 / 600 / --text-2    仅在需要分组处使用
正文       15 / 1.6 / 400         表单与列表
阅读正文   17 / 1.75 / 400        聚焦阅读时的题稿正文
次要说明   13 / 400 / --text-2
mono       12 / tabular-nums      ID、编号、时间戳、错误码、数字
```

所有动态数字加 `tabular-nums`。

### 文字预算（硬性）

文字多是第一次改版被判失败的主因，按预算执行，不再靠自觉：

- 一屏最多**一句**说明性文字（`--text-2`），没有需要的就不写；标题自身能表达时不写副标。
- 说明句**不超过 30 字**，写到第二句就删第一句。
- 合同的保证（幂等、出处、只读、权限）用结构表达，**不用句子解释**；
  唯一允许解释的场合是错误面板，且只写一句原因。
- 列表与条目不加「这里有 N 条」之外的旁白；计数用 mono 数字，不写句子。
- 副标、页脚注释、字段 hint 三处同屏最多出现两处。

## 5. 密度、间距、圆角、深度

- 间距基准 8px：区块内 12–16px，卡片内 20–24px，区块之间 32px；聚焦阅读的节之间 40px。
- 圆角（连续圆角矩形，**不是胶囊**）：卡片 16px · 聚焦卡 20px · 按钮/输入 10px · 小徽标 6px。全站禁 999px。
- 页宽：`.page-narrow 480` 登录 · `.page-mid 720` 列表/上传 · 聚焦阅读卡 `max-width 640`。
- 深度：默认靠发丝线 + 灰阶分层；卡片允许 `0 1px 2px rgba(0,0,0,0.04)` 极浅影；
  弹层 `--lift-pop`。按钮、卡片内部一律不加阴影。

## 7. 签名元素 ①：题卡与聚焦阅读

案例详情的「待你定稿」状态是**一张题卡，分节阅读**：

```
┌──────────────────────────────┐
│ ▪▪▪▪▪▪▷  进度刻度（已读灰/当前蓝/未读浅） │
│                              │
│  3 / 7                       │
│  判定维度 · 事实准确性        │
│  文中每个产品参数都能在        │
│  素材包参数表中找到完全一致的数值 │
│                              │
│  上一节           下一节 →    │
└──────────────────────────────┘
最后一节是定稿卡：以上 N 节，题 v N · 签名行 · [定稿]
```

- 一屏一节。刻度可点击跳节；`→/空格` 下一节，`←` 上一节。
- 节的正文按 §4 的阅读正文规格（17/1.75）；节标题 20/650。
- 当前节内的字段可直接修改（无边框文本域，hover/focus 时才出现弱底）。
- 每张题卡的最后一节永远是**定稿卡**：一句「以上 N 节，题 v N」+ 签名行（用户名纯文本 + 时间）+ 唯一主按钮 `定稿`。
- 完整度检查项**不陈列**：只在「定稿」不可点时，按钮下方写一句缺什么（「还差：参考结果」）。
- JSON 编辑收进定稿卡的折叠逃生口，默认合拢。
- 出处（evidence_refs）不在正文里占行：节正文末尾一个安静的 `原文` 文字链，点击展开行内的 locator + quote，再点收起。`evidence_refs` 永远只读。

维度类型用**文字后缀**表达（`事实准确性 · 硬门槛`），不做徽标。

## 8. 签名元素 ②：来源分组

题稿按来源分四个分组，老师一眼看清「是谁说的」——这是老师行使定稿权的信息基础：

```
事实（输入里明确存在）
你的判断（你已表达的）
AI 推断的候选条款
证据缺口
```

- 分组标题纯文字（13/600/--text-2），不用彩点不用线——分组本身就是来源信号。
- 每个条目只有一句正文；行号、摘录、引注边栏一律不要。
- 出处细节收进条目末尾的 `原文` 行内展开（§7 同一规格）。
- AI 不得把候选条款伪装成事实——四分组正是这条合同的前端执行。

## 9. 签名元素 ③：追问卡

「需要补充」是 AI 和老师的唯一对话接口，任一时刻只允许一个待答问题。单行提示卡，琥珀弱强调：

```
┌────────────────────────────────────────────┐
│ ● 需要补充                                  │
│ 这份案例里，哪一个结果是你最终认可的？        │
│ 为什么问：缺少参考结果，无法形成可验证的通过条件 │
│                                            │
│ ┌────────────────────────────────────────┐ │
│ │ 你的回答…                                │ │
│ └────────────────────────────────────────┘ │
│                          [提交回答并继续]    │
└────────────────────────────────────────────┘
```

- 琥珀 8% 底 + `--amber` 文字点；提交期间输入和按钮一起禁用。
- 不做对话气泡、不做聊天流——这是出题的地方，不是聊天工具。

## 10. 动效

- 时长一律 < 300ms。按钮 110–140ms，入场 220ms，聚焦卡换节 260ms。
- 只用 `cubic-bezier(0.23, 1, 0.32, 1)`；不用 ease-in，不写 `transition: all`。
- 只动 `transform` / `opacity` / 颜色。
- `.enter` = opacity + translateY(4px)。聚焦卡换节用同一 `.enter`，**切换本身不另外加动画**。
- 骨架用 1.5s 横扫；`generating` / `parsing` 的圆点用 1.4s 脉冲。
- `prefers-reduced-motion` 下全部退化为近零时长。

## 11. 状态是一等公民

每个页面必须覆盖 loading / empty / success / error / unauthorized：

- 加载态用**撑住最终版面**的骨架，不用转圈。聚焦阅读的加载态 = 一张刻度骨架 + 一张节卡骨架。
- 空态要有设计：场景列表为空时创建表单**升为这一屏的焦点**；有内容时退回成可展开的动作。
- 报错/越权/不存在共用安静的面板：一个语义色圆点 + 一句原因 + **等宽的机器码** + 唯一的下一步。
- 错误码永远以 `mono` 原样展示（`403 · FORBIDDEN`、`PARSED_CONTENT_EMPTY`、`retryable · false`），
  验收时直接对照合同。
- 会话没读完之前不显示任何身份信息（用户名纯文本 ≥14px，不用 chip 包裹）。
- 状态预演：`?preview=` 把页面钉在某个状态上，仅开发构建渲染，数据只用 `generated.ts` 类型构造。

| 组件 | 职责 |

## 13. 硬性约束

- 承载不定长正文的文本框一律 `AutoTextarea` 按内容增高；聚焦阅读里用无边框文本域。
- 所有类型来自 `src/lib/api/generated.ts`，不写第二套 DTO。
- 页面只调本 Feature 的 Service；Service 只调 `lib/api/client`。
- 新增控件先看 `src/components/ui/` 有没有；重复第二次就抽成组件。
- 新增装饰性图标/徽记前先问是否必要——历史反馈：符号要少、胶囊禁用、文字优先。
- **文字预算（§4）是硬约束**：改页面时数一遍说明句，超了先删再加。
- **开发/验收辅助信息不得出现在面向业务老师的界面**：Stub 标记说明、`GET /api/...` 合同原文、
  `retryable` 原始值、完整 UUID 等，一律用 `PREVIEW_ENABLED` 门控，生产构建不渲染；
  同一语义用中文人话常显（如 `private` → 「私有」）。错误码（`403 · FORBIDDEN`、
  `PARSED_CONTENT_EMPTY`）是可上报的标识，保留 mono 原样展示。
- 全站验收：搜索 `卷宗|收件|校样|校订|落章|案号|审校台|原件|追问单|候选标准案例|确认收录` 必须为 0 结果。
