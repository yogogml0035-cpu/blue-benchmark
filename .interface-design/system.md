## 1. 方向与语气

**标准工作台**：业务老师把一次真实交付沉淀成一条白纸黑字的题。核心叙事——
「我在把我们『什么算好』写成题」；平台自述——「用你的题，验证 Skill 每次改版」。

- 使用者：PR/传播口的业务老师，不是开发者。刚做完一次真实交付，想把「什么算好」固定下来。
- 老师是**出题人**，不是档案管理员。界面每一屏都应让她觉得「我在写我们业务的题」。
- 核心动词：**定稿**。老师是权威，AI 是必须给出处的整理者。
- 语气：安静、清晰、可信。像读一份写好的题，不像聊天工具，更不是配置台。
- **只做浅色**。`color-scheme: light`。

反面清单（刻意避开，不要退回去）：

- 纸墨隐喻的任何残留：卷宗、校样、落章、印章、牛皮纸标签、楷体、墨线、引注边栏、案号、第 N 校；
- 通用 SaaS 仪表盘、卡片墙、永久第三列和按后端实体拆出的页面；
- 生产界面的 JSON 编辑器；JSON 只允许出现在开发 Preview 或独立调试工具；
- 居中转圈的加载态（用撑住最终版面的骨架）；
- 装饰性图标、胶囊圆角（999px）、处处显示的状态徽记；
- **把合同说服力写成页面文案**——「逐条审阅，可直接修改」「AI 只能提出带出处的草稿」这类话不出现在界面上；
- **一屏叠多个卡片容器**——详情页聚焦模式下每一屏只有一张卡。

界面用词与代码/API 词分两层：**API 契约词永远不动**，界面说人话。

| 题稿 | draft | AI 整理的待确认草稿 |
| 需要补充 | pending_question | AI 向老师提的唯一问题 |
| **题** | candidate_case | 定稿后的产出物；API 字段名不动 |
| 题 v N | draft_revision | 版本号 |
| 案例编号 | case id | 地址栏与验收用 |
| 场景标准 | scenario contract | 同场景所有题共享的任务边界与判断标准 |
| 下一版 | working evaluation set draft | 从最新冻结版本派生的唯一工作草稿 |
| 历史版本 | evaluation set version | 已冻结、不可变、可下载的版本 |
| 给 Skill 的材料 | runtime | 被测 Skill 未来可以读取的输入分区 |
| 评分依据 | judge | 参考结果、规则、硬门和最低质量线 |

生命周期：资料批次 → 任务确认 → 场景标准共创 → 题稿共创/审改 → 定稿为题 → 评分规则审阅 → 发布题目修订 → 加入下一版 → 冻结为历史版本。

八个状态的界面标签：parsing=解析中 · parse_failed=解析失败 · ready_for_ai=待整理 ·
generating=AI 整理中 · waiting_for_input=需要补充 · waiting_for_confirmation=待你定稿 ·
ai_failed=整理失败 · confirmed=已定稿。

评分规则状态的界面标签：not_started=尚未生成 · queued=等待开始 · processing=规则处理中 ·
review_ready=待审阅 · confirmed=待发布 · published=已发布 · stale=规则已过期 ·
projection_pending=等待恢复 · failed=规则失败。

关键动作：创建场景 · 上传资料 · 确认任务 · 提交回答 · 定稿 · 检查并冻结。

## 3. 颜色

中性灰骨架 + 唯一强调色。语义色只表达状态，不做装饰。

```
底色     --bg        #f5f5f7   页面
         --surface   #ffffff   卡片
         --surface-2 #f5f5f7   卡片内嵌区域/输入底
文字     --text      #1d1d1f
         --text-2    #6e6e73
         --text-3    #86868b
发丝线   --hair      rgba(0,0,0,0.10)
         --hair-soft rgba(0,0,0,0.06)
主操作   --action    #1d1d1f
当前态   --accent    #0066cc
语义     --amber     #b25000   需要补充/证据缺口
         --red       #d70015   失败
         --green     #1d8a4b   已定稿/成功
```

规则：

- 主操作（创建场景、上传、提交回答、定稿、冻结）一律中性深色 `--action`；页面上同时只有一个主按钮。
- `--accent` 只用于链接、焦点环、文字导航当前态和进度刻度，不铺大面积主按钮。
- 提示卡用语义色 8–10% 透明度做弱底色，文字用上表深档；全站禁用大面积饱和色块。
- 输入控件底色 `--surface-2`，比卡片暗一档。
- 顶栏与画布同色（`--bg`），只用一条发丝线分隔。
- 全部文字色对白底满足 WCAG AA；新增文字色先算对比度。
- 维度类型（hard_gate / required_quality / diagnostic）**不用颜色区分**，用纯文字后缀（见 §8）。

```
--font-mono "SF Mono", ui-monospace, Menlo, Consolas, monospace
```

```
分组标题   13 / 600 / --text-2    仅在需要分组处使用

阅读正文   17 / 1.75 / 400        聚焦阅读时的题稿正文
次要说明   13 / 400 / --text-2
mono       12 / tabular-nums      ID、编号、时间戳、错误码、数字
```

所有动态数字加 `tabular-nums`。

### 文字预算（按上下文）

- 页面副标和被动 hint 仍以 30 字左右为上限；标题能表达时不写副标。
- 当前问题必须允许一段“为什么问”；任务分组、标准升级、合同影响和冻结确认可以用简短多行后果说明。
- 长解释默认收进“标准与依据”、技术详情或确认步骤，不在主画布常驻。
- 合同保证优先由状态、差异、来源和确认动作表达，不用自我宣传式文案说服老师。
- 副标、页脚注释、字段 hint 三处同屏最多出现两处。

## 5. 密度、间距、圆角、深度

- 间距基准 4px：控件内 8–16px，相关组 24px，章节 32–64px；聚焦阅读的节之间 40px。
- 圆角（连续圆角矩形，**不是胶囊**）：普通控件 6–8px · 焦点面/弹层 10–14px · 小徽标 6px。全站禁 999px。
- 页宽：`.page-narrow 480` 登录 · 场景工作台主画布 660–720px · 聚焦题稿 640–700px。
- 深度：默认靠发丝线 + 灰阶分层；卡片允许 `0 1px 2px rgba(0,0,0,0.04)` 极浅影；
  弹层 `--lift-pop`。按钮、卡片内部一律不加阴影。

## 7. 场景工作台

`/workspaces/{id}` 是场景唯一工作台，稳定信息架构只保留三个文字导航：

```text
当前 · 题 · 版本
```

- **当前**：唯一 `next_action`、正在处理的后台工作、任务边界确认和一次一个问题的共创。
- **题**：题稿、已定稿题、待复核题；不按上传批次或后端实体拆页。
- **版本**：唯一下一版和不可变历史；不把“下一版 / 历史”拆成两个导航。
- 主画布 660–720px；每个状态只有一个主动作和一个焦点面。
- 场景标准、判定依据、缺口和问答过程默认关闭。桌面右侧 sheet，窄屏全屏 sheet；关闭后焦点返回触发器。
- “问题 → 回答 → 本轮更新 → 唯一下一步”是 M0 的形成链。刷新后仍回到同一业务节点。
- 后台状态只显示老师能理解的阶段；不显示 thread/checkpoint/interrupt、Graph node、raw messages、token/tool stream 或 private reasoning。
- Agent resume 失败时保留已保存答案，只提供唯一“重试整理”。

## 8. 签名元素 ①：题卡与聚焦阅读

案例详情的「待你定稿」状态是**一张题卡，分节阅读**：

```
┌──────────────────────────────┐
│ ▪▪▪▪▪▪▷  进度刻度（已读灰/当前蓝/未读浅） │
│                              │
│  3 / 7                       │
│  判定维度 · 事实准确性        │
│  文中每个产品参数都能在        │
│  素材包参数表中找到完全一致的数值 │
│                              │
│  上一节           下一节 →    │
└──────────────────────────────┘
最后一节是定稿卡：以上 N 节，题 v N · 签名行 · [定稿]
```

- 一屏一节。刻度可点击跳节；`→/空格` 下一节，`←` 上一节。
- 节的正文按 §4 的阅读正文规格（17/1.75）；节标题 20/650。
- 当前节内的字段可直接修改（无边框文本域，hover/focus 时才出现弱底）。
- 每张题卡的最后一节永远是**定稿卡**：一句「以上 N 节，题 v N」+ 签名行（用户名纯文本 + 时间）+ 唯一主按钮 `定稿`。
- 完整度检查项**不陈列**：只在「定稿」不可点时，按钮下方写一句缺什么（「还差：参考结果」）。
- 生产定稿卡不提供 JSON 编辑；开发 Preview/调试工具可独立查看机器合同。
- 出处（evidence_refs）不在正文里占行：节正文末尾一个安静的 `原文` 文字链，点击展开行内的 locator + quote，再点收起。`evidence_refs` 永远只读。

维度类型用**文字后缀**表达（`事实准确性 · 硬门槛`），不做徽标。

## 9. 签名元素 ②：来源分组

题稿按来源分四个分组，老师一眼看清「是谁说的」——这是老师行使定稿权的信息基础：

```
事实（输入里明确存在）
你的判断（你已表达的）
AI 推断的候选条款
证据缺口
```

- 分组标题纯文字（13/600/--text-2），不用彩点不用线——分组本身就是来源信号。
- 每个条目只有一句正文；行号、摘录、引注边栏一律不要。
- 出处细节收进条目末尾的 `原文` 行内展开（§8 同一规格）。
- AI 不得把候选条款伪装成事实——四分组正是这条合同的前端执行。

## 10. 签名元素 ③：追问卡

「需要补充」是 AI 和老师的唯一对话接口，任一时刻只允许一个待答问题。单行提示卡，琥珀弱强调：

```
┌────────────────────────────────────────────┐
│ ● 需要补充                                  │
│ 这份案例里，哪一个结果是你最终认可的？        │
│ 为什么问：缺少参考结果，无法形成可验证的通过条件 │
│                                            │
│ ┌────────────────────────────────────────┐ │
│ │ 你的回答…                                │ │
│ └────────────────────────────────────────┘ │
│                          [提交回答并继续]    │
└────────────────────────────────────────────┘
```

- 琥珀 8% 底 + `--amber` 文字点；提交期间输入和按钮一起禁用。
- 不做对话气泡；建题会话使用正文式 transcript 和经过安全投影的进度事件，这是形成题目的工作台，不是 Agent 控制台。

## 11. 动效

- 时长一律 < 300ms。按钮 110–140ms，入场 220ms，聚焦卡换节 260ms。
- 只用 `cubic-bezier(0.23, 1, 0.32, 1)`；不用 ease-in，不写 `transition: all`。
- 只动 `transform` / `opacity` / 颜色。
- `.enter` = opacity + translateY(4px)。聚焦卡换节用同一 `.enter`，**切换本身不另外加动画**。
- 骨架用 1.5s 横扫；`generating` / `parsing` 的圆点用 1.4s 脉冲。
- `prefers-reduced-motion` 下全部退化为近零时长。

## 12. 状态是一等公民

每个页面必须覆盖 loading / empty / success / error / unauthorized：

- 加载态用**撑住最终版面**的骨架，不用转圈。聚焦阅读的加载态 = 一张刻度骨架 + 一张节卡骨架。
- 空态要有设计：场景列表为空时创建表单**升为这一屏的焦点**；有内容时退回成可展开的动作。
- 报错/越权/不存在共用安静面板：一个语义色圆点 + 一句原因 + 唯一下一步。
- 机器码、Manifest hash 和 Schema 默认隐藏在“技术详情”或“复制问题编号”中；业务老师主画面只显示可行动的人话。
- 会话没读完之前不显示任何身份信息（用户名纯文本 ≥14px，不用 chip 包裹）。
- 状态预演：`?preview=` 把页面钉在某个状态上，仅开发构建渲染，数据只用 `generated.ts` 类型构造。

| 组件 | 职责 |
|---|---|
| `DraftEditor.tsx` | **聚焦阅读器**：分节、刻度、定稿卡、完整度 gating；生产不提供 JSON 编辑 |
| `DraftView.tsx` | 节的正文渲染（读/改同构），被 DraftEditor 与已确认快照共用 |

| `QuestionCard.tsx` | 追问卡（§10），形制不变 |

route family：`/workspaces` = 场景列表 · `/workspaces/{id}` = 场景工作台 · 聚焦题详情 · 只读版本详情。旧 cases 路由只做重定向，不保留第二套编辑页。

第一阶段建题会话实际入口：`/workspaces/{id}/authoring/new`（手动或绑定上传批次）与 `/workspaces/{id}/authoring/{conversationId}`（transcript、候选题轨、题目输入和标准答案确认）。旧工作台仍保留资料/版本兼容链路，不能把它的轮询状态冒充为新会话事实。题目边界确认后，每道题使用独立的题级安全追问；处理中仍显示本地可编辑草稿，但保存/确认动作关闭，完成后再由服务端快照恢复。

第二阶段规则审阅入口：`/workspaces/{id}/authoring/{conversationId}/rubric`。页面保持单一焦点：左侧是已确认题目输入和标准答案，主区是评分项连续审阅；生成中的状态通过服务端 GET 轮询恢复，投影待恢复和失败分别提供“恢复规则快照”和“重新生成规则”，不把两者伪装成普通处理中。每项以正文展示满分、给分点、扣分点、关键项判定和标准答案期望得分；确认与发布均使用 `ConfirmSheet`，发布后只显示去版本组集的下一步。

## 14. 硬性约束

- 承载不定长正文的文本框一律 `AutoTextarea` 按内容增高；聚焦阅读里用无边框文本域。
- 所有类型来自 `src/lib/api/generated.ts`，不写第二套 DTO。
- 页面只调本 Feature 的 Service；Service 只调 `lib/api/client`。
- 新增控件先看 `src/components/ui/` 有没有；重复第二次就抽成组件。
- 新增装饰性图标/徽记前先问是否必要——历史反馈：符号要少、胶囊禁用、文字优先。
- 已发布题目修订在版本工作台中与旧任务并列显示；加入动作使用同一 `WorkingSet`，但成员明确携带题目修订号和内容 hash，不能伪装成 `TaskPackage`。
- 含已发布题目修订的混合版本包使用 v2 schema；`runtime`、`judge`、`provenance` 的信息边界由包 builder 的 allowlist 执行，前端不展示或拼接包内容。
- **文字预算按上下文执行**：副标/hint 保持短；高后果确认必须说清影响，再通过渐进披露收起。
- **开发/验收辅助信息不得出现在面向业务老师的界面**：Stub 标记说明、`GET /api/...` 合同原文、
  `retryable` 原始值、完整 UUID、内部 ID、hash 与 Schema 一律用 `PREVIEW_ENABLED` 或折叠技术详情门控；
  同一语义用中文人话常显（如 `private` → 「私有」）。
- 全站验收：搜索 `卷宗|收件|校样|校订|落章|案号|审校台|原件|追问单|候选标准案例|确认收录` 必须为 0 结果。

## 15. 人工评分工作台

已发布题目修订进入人工评分后，评分页只有一个业务焦点：读完一份独立答卷，并按同一份不可变规则完成一次评分。

- 路由：`/workspaces/{id}/question-revisions/{revisionId}/submissions/new` 是粘贴/单文件入口；`/workspaces/{id}/submissions/{submissionId}` 是答卷详情、评分和历史。入口挂在已发布题目修订上，不新增工作台第四个导航。
- 桌面布局：左侧按“答卷 → 题目标准”阅读，右侧 400px 连续评分区吸附在顶栏下；窄屏按答卷 → 标准 → 评分 → 历史单列展开。
- 评分项：连续堆叠而非指标卡墙；每项显示名称、满分、标准答案期望得分、标准理由、给/扣分点、关键项规则和待评分数。低于锚点或关键失败时理由框变为必填；hard-fail 使用原生 radio/fieldset。
- 结果：总分、通过线、关键项结论和整体理由由服务端计算后展示；提交结果只读，重新评分必须从最新记录建立 parent-linked 历史。历史展开显示每项分数、满分、关键项及 hard-fail 结论，不显示内部 criterion ID、用户 UUID、存储键或运行元数据。
- 交互：评分输入和单选标签最小 44px 命中区；校验失败焦点落到实际错误控件；提交成功焦点回到结果；失权/资源消失时清空旧答卷快照；状态预演只在开发构建可见。
