# Skill Eval Platform 初始化项目开发规格

状态：已对齐，供初始化骨架开发使用
目标读者：不了解前序讨论的初级工程师
当前阶段：只搭建干净、可运行的本地项目骨架和最小纵向闭环，不实现完整 Benchmark 产品。

## 1. 背景与目标

### 1.1 要解决的业务问题

业务老师通常需要反复把同一个真实任务交给 Skill，自己查看结果、指出问题、要求修改，再重新试用。结果是：

- “什么算好”停留在老师经验里；
- Skill 版本之间无法在同一组任务上比较；
- 已修复的问题可能再次退化；
- 业务老师和开发者之间需要反复人工沟通。

本项目最终要形成一个由业务老师自建、自评、持续维护的 Skill 回归工作台。平台不在线运行 Agent/Skill，而是接收外部运行后的、带版本信息的候选结果，依据业务老师确认的回归集进行评测和版本比较。

### 1.2 AI Native 的核心含义

平台的 AI Native 不是让 AI 代替业务老师决定标准，而是：

1. 业务老师提供真实业务案例、输入材料和结果；
2. 平台 AI 将隐性经验整理成场景、维度、标签和判定标准草案；
3. AI 发现证据缺口时，一次只向老师追问一个关键问题；
4. 业务老师确认后，草案才成为正式业务资产；
5. 后续业务老师可以自己新增场景和用例，不需要开发人员为每个客户写专属规则。

AI 只能提出有证据来源的草案，不能自动冻结标准、确认交付或把一次偏好升级为长期规则。

### 1.3 初始化阶段目标

先完成以下 Walking Skeleton：

```text
注册/登录
  → 创建私有客户/场景空间
  → 上传 TXT/Markdown 案例
  → 保存附件和业务记录
  → LangGraph 调用模型生成标准草案
  → 暂停等待老师输入/确认
  → 使用同一 thread_id 恢复
  → 保存已确认的候选用例
  → 前端展示全过程状态
```

只有这条链路在浏览器中真实跑通，项目骨架才算完成。空页面、目录存在、服务启动或健康检查通过，都不算完成。

## 2. 已确认的业务决策

### 2.1 首批验证场景

第一版用两个差异明显的场景验证通用内核：

1. **单一客户的文案/新闻稿**：主观判断为主，业务老师盲评最终产物是否满足 Brief、事实、品牌要求和禁用项。
2. **媒体名单/RSVP 衍生表**：规则相对明确，依据冻结的原始数据和业务规则客观核验人员、数量、航班、酒店、重复和遗漏。

两类场景都应能走通：

```text
固定评测集 → 上传带版本的候选结果 → 评测 → 版本比较 → 交付判断
```

### 2.2 测试任务包

固定评测集中的每条用例必须是完整任务包，而不是孤立的最终文件。至少包含：

- 真实任务和业务目标；
- 原始 Brief、输入文件、数据和允许使用的素材；
- 输出格式及必须满足的要求；
- 明确禁止出现的错误；
- 业务老师认可的结果及认可/否定原因；
- 主要保护的业务能力或失败模式；
- 适用维度、证据来源和通过条件。

脱离原始任务条件的 Good/Bad Case 只能做展示，不能作为正式回归门禁。

### 2.3 用例和回归集

- 一条用例 = 一个完整真实任务 + 一个主要能力或失败模式 + 直接相关的全部约束。
- 一条用例可以选择多个维度，但必须标明主要保护能力。
- 只替换名称、日期或车型且没有新能力/风险的，不算新用例。
- 任何经业务老师确认、能稳定区分合格与不合格的用例，都可立即加入有效回归集。
- 不设固定数量门槛，也不设“必须 20 条”的要求。
- 重大交付前可增加一个尚未针对性优化的新鲜真实案例；检查完成后并入同一回归集。
- 不建设永久隐藏门禁集。

回归集是不可变版本。新增、修改、停用用例或调整标准，都生成新的回归集版本；历史批次永远绑定当时的回归集版本，不得静默改写。

### 2.4 评测通过规则

正式回归要求当前有效回归集中的所有用例全部达标。不能用 80% 通过率、平均分或其他用例高分抵消失败。

每个维度在具体用例中必须属于以下一种：

| 类型 | 含义 | 规则 |
|---|---|---|
| 硬性门禁 | 事实、隐私、名单错漏、客户禁用项等 | 失败一次，用例失败 |
| 必达质量 | 品牌表达、结构、完整性等 | 达到该维度预先冻结的最低标准 |
| 诊断标签 | 创新度、精炼度等尚未稳定的观察项 | 只用于解释和趋势，不影响门禁 |

不同维度不能通过加权平均互相补偿。

文案用例通过条件：

- 硬性要求全部通过；
- 达到业务老师设定的绝对可用线；
- 本次目标用例新版优于旧版；
- 其他回归用例新版不得实质退化，允许打平。

RSVP 用例优先使用确定性核验。输入缺失或冲突时，正确行为是明确暴露缺口，不能擅自补全。

### 2.5 运行批次和盲评

正式外部运行批次开始前必须声明：

- Skill 版本；
- Prompt 版本；
- 模型和相关配置版本；
- 回归集版本；
- 每条用例的运行次数。

运行时必须使用同一版冻结回归集，并一次性提交所有结果，包括失败、空结果和异常结果。禁止人工润色、替换、挑选最佳结果或临时增加运行次数。

来源不完整、经过人工修改或只提交部分结果的批次只能标记为“探索结果”，不能产生可交付结论。

业务老师盲评时看不到版本身份、开发者解释或本次修改意图。候选结果顺序应随机化。

运行次数按用例风险在批次前冻结：单次运行只能证明本次通过；多次运行必须全部通过，才能证明该用例在本批次中稳定。

### 2.6 评审和标准权力

每个业务场景只有一名业务老师，且该老师同时是：

- 场景所有者；
- 自己业务 Skill 的开发者；
- 标准和用例确认人；
- 主观评审人；
- 最终交付决定人。

第一版不做成员邀请、共享、角色分级、交接和多人校准。

正式批次开始前冻结标准。评审中出现的新判断只能进入下一版并重新评测，不能当场移动本批次门槛。

平台报告必须标明“场景负责人自评”，不能写成独立第三方认证。

### 2.7 信息视图和数据隔离

账号识别人，客户/场景空间隔离数据。第一版支持多个独立本地账号，但每个空间仍是单人私有。

三种信息视图必须严格隔离：

1. **标准共创视图**：老师和平台 AI 可看完整案例、老师结果、Good/Bad 标注和评语。
2. **正式运行视图**：被测 Skill 只能看到真实任务本来允许看到的输入，不能看到老师结果、标签、评分标准或历史评语。
3. **业务盲评视图**：老师看到冻结标准、客观检查证据和匿名的新旧候选结果，不能看到版本身份。

原始案例默认只在当前空间可见。只有老师明确发布的不含客户信息的通用模板才可跨场景复用。数据默认最小化、脱敏。

## 3. 初始化阶段范围

### 3.1 必须实现

- 本地多账号注册、登录、退出和当前用户查询；
- 服务端 Session Cookie；
- 单人私有客户/场景空间；
- TXT、Markdown 案例上传；
- 本地附件保存和 PostgreSQL 元数据；
- LangChain 模型调用；
- LangGraph 状态流、PostgreSQL Checkpoint、暂停和恢复；
- AI 生成场景/维度/标签/判定标准草案；
- AI 对证据缺口的单问题追问；
- 老师确认后保存候选用例；
- FastAPI OpenAPI；
- Next.js 基础页面和状态展示；
- Fake Model 自动测试；
- 真实模型手动 Smoke Test；
- 本地启动说明和成功标志。

### 3.2 明确不实现

- Skill 触发、误触发和漏触发评测；
- 平台在线运行 Agent/Skill；
- 完整回归集管理、版本比较、Good/Bad 展示和评测报告；
- 自动评判文案主观质量；
- 自动修改 Skill；
- 自动发布文案、自动排车或改变真实业务状态；
- 多用户协作、成员管理、邀请、交接和权限分级；
- JWT、Refresh Token、Auth.js、OAuth、SSO、邮件验证和密码找回；
- Celery、Redis、RQ、独立 Worker 或任务队列；
- MinIO、S3、云对象存储和完整容器化部署；
- 多模型供应商、模型注册中心和动态路由；
- OCR、图片理解、音视频理解和复杂 PDF 排版还原；
- 为某个客户硬编码专属评测程序。

## 4. 技术架构决策

### 4.1 运行时和目录组织

采用“Runtime-first 外壳 + Feature-first 内核”：

- 顶层按运行时分为 `frontend/` 和 `backend/`；
- 两边内部各自按业务 Feature 组织；
- 不把 TypeScript 与 Python 的 Feature 代码揉成一套跨语言目录；
- 不使用全局 Layer-first 的 `routers/`、`services/`、`repositories/` 大目录。

### 4.2 前后端边界

```text
Next.js app
  → frontend feature service
  → same-origin /api/*
  → Next.js Rewrite
  → FastAPI feature router
  → business service
  → repository / ORM
  → PostgreSQL
```

- FastAPI 是唯一业务和数据事实源；
- Next.js 不安装 ORM、PostgreSQL 驱动或数据库客户端；
- Next.js 不直接访问数据库；
- `app` 页面只调用对应 Feature Service；
- 不使用 Route Handler 或 Server Action 做通用代理；
- Next.js 只通过 Rewrite 将同源 `/api/*` 透明转发给 FastAPI；
- FastAPI OpenAPI 是唯一接口契约来源；
- 前端根据 OpenAPI 生成 TypeScript 类型，使用轻量 `fetch` 客户端；
- 不引入 tRPC、GraphQL 或重复手写 DTO。

### 4.3 AI 框架边界

- LangChain：模型、结构化输出和通用工具抽象；
- LangGraph：唯一的流程编排层，负责分支、循环、暂停和恢复；
- Deep Agents：第一版暂缓；只有未来出现长时间规划、子 Agent 委派、跨会话文件工作区等真实需求时再引入；
- AI 逻辑只在 FastAPI 后端运行，Next.js 不编排 Agent。

### 4.4 数据库和迁移

- PostgreSQL 通过 Docker Compose 在本地运行；
- SQLAlchemy 2 是唯一 ORM；
- Alembic 管理业务 Schema 迁移；
- Psycopg 3 作为 PostgreSQL 驱动；
- Pydantic 请求/响应模型与 ORM 模型分开；
- LangGraph Checkpoint 使用 PostgreSQL 持久化，但其执行状态不代替业务表；
- 不使用 LangGraph Store；
- 长期业务事实写入业务表，AI 暂停/恢复状态写入 Checkpoint。

### 4.5 认证

- FastAPI 负责注册、登录、退出和当前用户；
- 使用用户名或邮箱 + 密码；
- 密码只保存安全哈希；
- 服务端 PostgreSQL 保存 Session；
- 浏览器只持有随机 HttpOnly Session Cookie；
- 本地 Cookie 可配置 `Secure=false`，生产规则不在本阶段处理；
- 所有资源访问都校验当前用户对场景空间的归属。

### 4.6 文件存储和解析

- PostgreSQL 保存附件元数据、归属、解析状态和摘要；
- 原始附件保存在本机 `storage/` 目录；
- 不把大文件二进制写进 PostgreSQL；
- 文件路径由服务生成，不能使用用户输入直接拼接路径；
- 平台首版允许的解析范围是 TXT、Markdown、JSON、CSV、XLSX、DOCX 和文字型 PDF；但初始化 Walking Skeleton 只要求先实现 TXT/Markdown，其他格式在后续解析扩展中接入；
- XLSX 只读工作表、单元格值和基础结构；
- DOCX 只读正文和表格；
- PDF 只做文字提取；
- 图片、音频、视频、扫描件和需要 OCR 的文件不参与首版分析；
- 解析失败或解析为空时必须明确失败，不能把空内容交给 AI 猜测。

### 4.7 模型配置

第一版只支持一个 OpenAI-compatible 模型协议：

```text
LLM_BASE_URL=<已确认的兼容接口地址>
LLM_API_KEY=<本地注入，不写入仓库>
LLM_MODEL=gpt-5.6-luna
```

- 使用 `langchain-openai`；
- 不建设模型供应商表、探测接口或动态路由；
- 不预装其他 Provider；
- LangSmith 依赖可保留，但默认关闭追踪；
- 真实 Key 不得进入 Git、代码、日志、测试报告或截图。本文档不记录该 Key。

### 5.1 后端依赖规则

```text
router → feature service → feature repository → SQLAlchemy
                         ↘ case workflow → LangChain/LangGraph
```

- `router.py` 只处理 HTTP、认证依赖和参数校验，不写业务规则；
- `service.py` 编排业务动作和事务边界；
- `repository.py` 只负责本 Feature 的数据访问；
- `models.py` 定义本 Feature 的 ORM 模型；
- `schemas.py` 定义 Pydantic 输入/输出；
- `workflow.py` 定义本 Feature 的 LangGraph 状态和节点；
- `lib` 只放跨 Feature 的通用能力；
- 一个 Feature 不得绕过另一个 Feature 的 service 直接读其 Repository；
- 不在前端复制后端业务判断。

### 5.2 前端依赖规则

- `app/` 只负责路由、页面组合和布局；
- 页面和组件只能调用对应 Feature Service；
- Feature Service 只能调用 `frontend/lib/api/client.ts`；
- `generated.ts` 由 FastAPI OpenAPI 生成，禁止手改；
- 不在前端导入 SQLAlchemy、Psycopg 或任何后端文件；
- 不创建 `app/api` 代理目录。

## 6. Walking Skeleton 的业务和 API 行为

具体字段可由工程师按下列行为定义，但不能改变状态语义。

### 6.1 认证和空间

- 未登录用户只能访问登录/注册页面；
- 登录成功后可以创建和查看自己的场景空间；
- 访问其他账号的空间或案例必须返回未授权；
- 空间必须记录所属用户；
- 第一版不提供共享入口。

### 6.2 案例上传

- 用户在指定空间创建案例；
- 案例可以同时包含文字描述和附件；
- 服务端验证文件类型、大小、路径和空间归属；
- 附件保存成功后，案例进入待分析状态；
- 解析失败必须进入明确失败状态，并向前端返回可理解的原因。

### 6.3 LangGraph 流程

最小流程如下：

```text
load_inputs
  → analyze_case
  → inspect_evidence
      ├─ 缺关键证据 → interrupt(question) → 等待老师回答 → 回到 analyze_case
      └─ 证据足够   → prepare_draft
                         → interrupt(draft_for_review)
                         → 老师确认/修改
                         → persist_confirmed_case
                         → END
```

AI 草案至少应区分：

- 输入中明确存在的事实和约束；
- 业务老师已经表达的判断；
- AI 推断的候选标准；
- 当前未知和证据缺口。

Graph 通过 PostgreSQL Checkpoint 保存状态，每个案例共创会话使用稳定的 `thread_id`。恢复必须使用相同 `thread_id` 和 LangGraph 的 resume 机制。

在 `interrupt()` 前不能执行不可幂等的新增写入；节点恢复时，`interrupt()` 前的代码会再次执行。业务持久化应放在老师确认之后，或使用幂等 Upsert。

### 6.4 前端展示

无需精细视觉设计，但必须能清楚显示：

- 当前用户和空间；
- 案例上传状态；
- AI 正在分析、等待补充信息、等待确认、已确认或失败；
- AI 草案中的事实、判断、未知、候选维度和判定标准；
- 老师可回答 AI 的问题并确认/修改草案。

## 10. 常见错误和禁止事项

- 不要把“首页能打开”当成服务跑通；必须验证 API、数据库和浏览器闭环；
- 不要把 LangGraph Checkpoint 当作业务表；
- 不要在 `interrupt()` 前做不可幂等写入；
- 不要为未来的回归集、评测报告、协作权限提前建立空模块；
- 不要为了让测试通过，把真实模型 Key 写进 `.env.example`；
- 不要打印或提交用户在对话中提供的 Key；
- 不要把解析失败转换为空文本继续调用模型；
- 不要把 AI 建议直接标记为已确认标准；
- 不要在 Next.js 再实现一份 FastAPI 已有的业务判断；
- 不要用 `docker compose down -v` 清理数据库，除非明确获得删除授权。
